# LA — each fix validated and applied on its own (2026-10-29)

docs/status.md, "Missing before complete", item 2. `ludion patch --apply` no longer writes every planned fix into the working tree at once. Each fix is validated alone against one baseline and, with `--apply`, committed on its own branch. Receipts carry `fix_published_at`, `found_at` and `applied_at`. Nothing opens a PR yet; that is the next stage (the scheduled Action).

Start: main 2cce104. Branch `lane/la-per-fix-apply`.

## What changed

- **A fix.** Every planned change of one package (`fixesOf`), or PHP's one image update. Its candidate is the baseline with only that package moved: the manifests, `changedManifest`, `unplannedRemovals`, the time cap (`candidateTimeCap`, called with the fix's changes and otherwise untouched) and the compatibility check all see that fix's changes only.
- **One baseline.** The baseline is built and tested once per run. Each candidate is acquired, checked, built and tested on its own.
- **A failing fix stops no other.** Its receipt entry is `failed` with the reason, and the loop goes on. A run-level failure (the baseline's test, the tool image, the acquisition policy, an incomplete inventory, cancellation) fails every fix not yet decided, each with `Not validated: <reason>`.
- **MAL- records.** An OSV MAL- record (by id or alias) on an installed package stops the whole run before any Docker work, as main did. Nothing is installed or tested.
- **After the candidate.** The OSV re-scan must show no finding left on the fix's own package, and no finding on a package version the baseline did not have. Findings the baseline already had, on the same versions, are other fixes. This holds in every ecosystem, so a fix that passes only together with another is not applied (Maven's commons-text, below). The PR first compared by package and advisory, for every ecosystem and then for Maven only. The cloud review of 19b7376 (comment 6496845752) and the review of 9e7ca6d (comment 6498219754) showed that this let through what main stopped: an npm candidate could add a second copy of a package under the baseline's MAL- record and still be committed (docs/mistakes/2026-10-29-a-fix-carried-a-mal-record.md). A package with a finding that has no supported fix (`scan.blocked`) does not get a fix branch.
  - The first Maven run, with version-keyed findings, failed commons-text's fix: alone, commons-text 1.10.0 brings commons-lang3 3.12.0, under GHSA-j288-q9x7-2f5v, the advisory commons-lang3's own fix removes. The PR then compared by package and advisory to let it pass. That was undone, as above, so commons-text fails again until the commons-lang3 branch is merged (`logs/e2e.log`).
- **The branch** (`packages/cli/src/security/branch.ts`). Branch names are `ludion/<ecosystem>/<package>-<version>` and `ludion/php/<version>`; a project in a subfolder of its repository gets the folder in the name.
  - Before any build or test (for Maven, after its dependency graph is resolved), `gitBase` checks that the validated copy of the project has exactly HEAD's files (CRLF line ends alone are allowed in a text file; the executable bit must match, except on Windows). Files the snapshot leaves out, and the top-level names the application image's .dockerignore leaves out, are not compared.
  - `fixBranch` makes one commit on that HEAD, with only the changed files replaced, using a temporary index. It refuses a path HEAD does not have, and a symbolic link (or junction) inside `.git` on the paths Git writes for the branch: the ref, its reflog folders, the objects folders and every loose object file in them, and `reftable`; it refuses a reflog the branch already has, and a repository whose refs are not in the files storage (docs/mistakes/2026-10-29-git-writes-through-links-in-dot-git.md). Before the ref is made, it reads back the commit's tree and only parent, the paths the commit changes, and each changed file's bytes, so an object the repository already holds at the new content's id cannot stand in for it. It refuses a repository that borrows objects from other folders (alternates). It commits a file the working tree has only with CRLF ends with HEAD's LF ends. It creates the ref only if it does not exist (`update-ref` with an all-zero old value), and refuses a symbolic ref at that name; `--no-deref` alone does not, since Git before 2.5x replaces a dangling symbolic ref. The working tree, the index and HEAD are not touched, and nothing is pushed.
  - A fix whose branch exists, with this fix's subject on its tip commit, is `skipped`: it is not validated again, and the branch is not changed. A branch of that name holding another change stops the fix. When a skipped branch starts from another commit than HEAD, the reason says so: nothing makes it again until it is merged or deleted. When no fix is left to validate, no Docker work runs. Two fixes of one run whose names clean to the same branch name: the second stops before validation. A branch-name part over 200 characters keeps its first 180 and a hash of the whole.
- **Git runs only plumbing.** The commands are `rev-parse`, `config --get-regexp`, `config --file <common dir>/config --no-includes --get`, `symbolic-ref --quiet`, `cat-file commit`, `cat-file blob`, `diff-tree -r -z`, `ls-tree`, `read-tree`, `hash-object --no-filters`, `update-index --cacheinfo`, `write-tree`, `commit-tree --no-gpg-sign`, `update-ref` and `check-ref-format`. Every call passes `--no-replace-objects` with `GIT_NO_REPLACE_OBJECTS=1`, so HEAD's own commit and tree are read, and sets `core.hooksPath` to an empty temporary folder, `core.fsmonitor=` (empty: before Git 2.36, `false` names a program; `logs/fsmonitor-probe.log`, docs/mistakes/2026-10-29-fsmonitor-false-is-a-program.md), `commit.gpgSign=false`, `core.splitIndex=false`, `gc.auto=0`, `maintenance.auto=false`, `protocol.allow=never` and each `protocol.<name>.allow=never` (a repository's own `protocol.file.allow=always` would win over `protocol.allow`), with `GIT_NO_LAZY_FETCH=1` and `GIT_ALLOW_PROTOCOL=none` (Git versions before 2.44.0 that lack the 2024-05-14 security releases ignore `GIT_NO_LAZY_FETCH`; the environment variable wins over any `protocol.*` setting). The configuration checks run again before each branch, and a `git config` failure other than "no match" refuses. A partial clone, which could fetch a missing object through the repository's own transport command, is refused (`logs/transport-probe.log`, from `scripts/transport-probe.sh`). Git starts in that temporary folder and is given the repository with `-C`, because Windows looks for `git.exe` in the child's working directory before PATH (docs/mistakes/2026-10-29-git-found-in-the-project-folder.md). It drops every `GIT_*` variable from the environment and sets the author and committer to `Ludion <ludion@ludion.invalid>`. A repository whose configuration names hooks (`hook.*`), which newer Git runs whatever `core.hooksPath` says, is refused. The tests run Git 2.39.5, which has no such hooks, so they check the refusal, not the hook. A project's Git configuration is data: in the tests none of its hooks, fsmonitor, signing program, filter drivers or transport command runs (branch.test.ts, with controls showing that plain Git does run the hook and the transport command).
- **Timestamps** (`packages/cli/src/security/exposure.ts`). Reading them never stops a fix.
  - `fix_published_at` is the fix's official publication. For PHP, it is php.net's release day of the first security release newer than the Dockerfile's version, at 00:00 UTC, because php.net gives a day only. For npm, it is the registry's publish time of the fixed version. For Composer, it is Packagist's release date, which the author sets. When a fix has several changes, it is the latest of their times. It is null, with `fix_published_note` saying why, for Maven (not read yet) and whenever the time cannot be read.
  - `found_at` is this run's advisory or release lookup (`scan.checked_at`). A fix found in an earlier run is found again, so detection time is not measured yet.
  - `applied_at` is when the branch was made. It is null when no branch was made.
- **The receipt.** Dependency receipts are `schema: 2`: the run's baseline, plus `fixes[]`, one entry per fix, with its own outcome, branch, commit, timestamps, candidate image, after-scan, files, changed packages, time cap and reason. The run's `outcome` is `partial` when some fixes failed, or some findings have no supported fix, while others did not, and `skipped` when every fix already had its branch. PHP receipts stay `schema: 1`, with the timestamps, `base_commit`, `branch` and `commit` added and a `skipped` outcome.
- **The CLI.** It prints one line per fix and exits 2 on `failed` or `partial`.
- **Removed.** `applyFiles`, the in-place multi-file write with its journal, and its test. `privateState` still refuses to run while an earlier version's unfinished journal is there.

## What `--apply` no longer does

`--apply` on a project that is not in a Git repository used to edit the files in place. Now it refuses before any build or test (for Maven, after its dependency graph is resolved), and only validation (without `--apply`) runs. This is the one sentence for the owner's OK (CLAUDE.md, How we work, Scope): "Ludion will no longer write fixes into a project's files: `--apply` (and `watch --apply`) only commits each fix that passes on its own to its own new Git branch, so fixes that pass only together are not applied, a fix whose branch name already exists is not applied again, and a project is only validated unless it is a Git repository whose files are byte for byte those of its last commit (not with uncommitted, untracked or ignored files, files Git stores through a filter such as Git LFS or git-crypt, a sparse checkout, a symbolic link or submodule in the commit, no commit, a work tree Git places elsewhere, a partial clone, Git configuration that names hooks, refs kept in reftable storage, objects borrowed from other folders, an executable bit other than the commit's, or a symbolic link inside `.git` where Git would write the branch); an installed package with an OSV MAL- record stops every fix of the run, and `--apply` needs `git` on PATH."

## Git by absolute path (LA6, 2026-10-30)

Main 3b22d2a (#208: `findProgram` in packages/sandbox/src/docker.ts) was merged in with `git merge`. The review of 89fd0c8 (comment 6503011718) asked for changes: branch.ts started `git` by name, from an empty folder but through PATH, and `npx`, `npm exec` and package scripts put the project's `node_modules/.bin` first on PATH (a Composer script can add `vendor/bin`, an activated venv `.venv/bin`). The reviewer's probe ran a planted `node_modules/.bin/git` on the host.

- **The lookup** (`gitProgram` in branch.ts). Every Git call starts the program `findProgram("git", PATH, cwd, platform, top)` returns: PATH's absolute folders only, skipping the working directory, any folder with a `node_modules` segment, Yarn's `BERRY_BIN_FOLDER` and anything inside `top`. `top` is the nearest folder at or above the project with a `.git` entry, where Git itself looks, so for a project in a subfolder the whole repository is skipped, not only the project (`useProject`'s root, which findDocker uses, is the project). packages/sandbox/ was read, not changed.
- **No git found.** `--apply` refuses at the first Git call, which comes before any Docker work (for Maven, after its dependency graph is resolved): "--apply needs git, and none was found in PATH's absolute folders (the working directory, the repository, node_modules folders and Yarn's shim folder are skipped). Run without --apply to validate only. Nothing was validated or changed." This is the same refusal as for a project outside Git; without `--apply` Git is not used.
- **Tests.** branch.test.ts, "never runs a git from a PATH folder inside the repository or a node_modules folder, and needs one outside": a project at `apps/web` of a repository, with a planted `git` in `apps/web/node_modules/.bin`, `apps/web/vendor/bin` and the repository's `.venv/bin`, all first on PATH; the fix branch is made and none of them runs; with only those folders and an empty one on PATH, `gitBase` refuses and none runs; the control starts `git` by name with each folder first, and each one runs. dependencies.test.ts: a committed project with no git on PATH ends `failed` with that reason, every fix "Not validated:", and no Docker command. The earlier test with "." on PATH stays.
- **The review's other items.** docs/status.md: the MAL- stop is "before any Docker work (for Maven, after its dependency graph is resolved)", Git is "started by absolute path", and "`--apply` needs `git` on PATH" now says which PATH folders count. apps/site/src/pages/start.astro: ignored files refuse "other than node_modules and .env files, and for npm, Composer and Maven a top-level vendor or target" (PHP's `gitBase` call leaves out no top-level name, so its `vendor` is compared), and "--apply needs git installed outside the project". Both READMEs (still byte copies): the run-wide MAL- stop, and how git is found. dependencies.test.ts, "stops a fix whose candidate has an entry without a supported fix the baseline did not have, on any package": the candidate's OSV scan returns a `blocked` entry for another package with no finding (as a Composer dependency with unreadable Packagist advisories would), and the fix fails; with the same entry in the baseline the fix is applied and the run is `partial`. Item 6 (a skipped branch is not re-scanned) is for the PR stage and was not changed.
- **The owner's sentence** above still says "`--apply` needs `git` on PATH". It is quoted as approved and was not edited; git found by these rules is a narrower reading of "on PATH", and refusing when it is missing applies nothing more.
