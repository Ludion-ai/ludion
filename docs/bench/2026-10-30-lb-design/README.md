# LB — Ludion runs by itself and opens one PR per fix (design, 2026-10-30)

docs/status.md, "Missing before complete", items 1 (runs without being asked) and 2 (delivers each fix as a PR). Stage 1: this design and the smallest form that works. Start: main fcbff49. Branch `lane/lb-scheduled-pr`.

Today Ludion does nothing unless someone types `ludion patch`. `patch --apply` already validates each fix on its own and commits it on its own branch (LA, #204), and nothing pushes the branch or opens a PR. This stage adds both, as a workflow in the user's repository.

## Shape: two more modes of the root action

The workflow lives in the user's repository and uses this repository's root action (`action.yml`), pinned by a release commit's full SHA, with two new modes:

- `mode: patch`, the validation job;
- `mode: pull-request`, the PR job.

Why modes of `action.yml` rather than a second action:

- **One pin, one bundle.** CLAUDE.md wants workflows written for users to pin actions by commit SHA and to ship the CLI inside the action. `action.yml` already checks that the pinned commit carries the bundled CLI (`packages/cli/dist/cli.js`) and stops otherwise. A second action would need its own copy of that check and a second pin that could drift from the first.
- **Same split as today.** `action.yml` already splits a read-only job (`judge`) from a job that writes (`comment`) and checks what crosses between them as untrusted data. The new pair follows the same pattern, and the same review of `action/` covers both.
- **Cost.** The action's name and description now cover more than the judge. `action.yml` and `action/` are protected only against deletion (docs/protected-paths.md), so adding modes is an ordinary PR.

The logic is TypeScript in the CLI (`packages/cli/src/security/deliver.ts`, `ludion deliver pack` and `ludion deliver open`), not shell, so that it is tested with vitest like the rest of the CLI and reuses branch.ts's Git rules. The action's shell only checks the event and passes paths.

The workflow file a user adds is `action/patch-workflow.yml` (a template; the action's own tests check its permissions).

## Two jobs (CLAUDE.md, "Ludion must not become the attack path")

"A job that runs candidate code has no write permission and no secrets; a job that writes runs no dependency code."

### Validation job (`mode: patch`)

- **Runner:** GitHub-hosted only. The split below holds only when each job gets a fresh machine: on a persistent self-hosted runner, a sandbox escape in this job could stay for the PR job, which holds a write token. Both modes refuse to start when `RUNNER_ENVIRONMENT` is not `github-hosted` (action/start.sh). The template also turns setup-node's npm cache off in both jobs (`package-manager-cache: false`), so no cache is restored in the job that writes and saved by the job that runs candidate code (review 6516135819, N5 and N8).
- **Permissions:** `contents: read` only. No secret is passed, and none of this mode's steps names `github.token`. The job refuses to start when it can request an OIDC token (`id-token: write`).
- **Checkout:** the action checks out the run's commit (`github.sha`) itself. actions/checkout fetches with the job's read-only token and, with `persist-credentials: false`, leaves no credential in `.git/config`, before any candidate is built.
- **Run:** `ludion patch --apply --json` in the project folder (input `dir`). Candidate code runs only inside packages/sandbox's Docker (no network, read-only root, non-root user). On the runner itself only Ludion's bundled CLI and Git run. Each fix that passes becomes one commit on the checked-out commit, on its own branch (`ludion/<ecosystem>/<package>-<version>`, `ludion/php/<version>`, with a hash at the end when two fixes' names could be alike; see "A fix that already has a PR"), as `--apply` does today.
- **Result:** `ludion deliver pack` writes the artifact `ludion-fixes`:
  - `receipt.json`, the run's receipt;
  - `fixes.bundle`, a Git bundle holding the applied fixes' branches and nothing else, with the run's commit as its only prerequisite.
- **Failures:** a fix that fails is in the receipt with its reason, and the job fails after the artifact is uploaded, so a failed or partial run shows red. The receipt is uploaded on every run that wrote one, also when no fix was applied, so the reasons stay with the run. The PR job runs only when at least one fix was applied. A run that finds nothing to fix uploads the receipt `null` and no bundle.
- **A waiting or stopped fix keeps the job red.** `patch` exits 2 for a fix that waits (the judge's wait table) as for one that fails, so the job fails every 6 hours, with GitHub's failure notice, until the wait ends or the fix is applied or dropped. Before LV (#209), examples/npm-security's lodash fix (4.18.0, deprecated, stopped by the judge) would have kept it red indefinitely; `patch` now takes 4.18.1, but any fix the judge stops for good keeps the job red the same way. Telling a wait from a failure in the job's result is not built.

### PR job (`mode: pull-request`)

- **Permissions:** `contents: write` and `pull-requests: write`. `needs:` the validation job, same workflow run, so `github.sha` is the same commit.
- **Runs no dependency code.** It checks out the same commit (`persist-credentials: false`, depth 1), downloads the artifact, and runs only Ludion's bundled CLI and Git plumbing. Nothing from the project or its dependencies is installed or run.
- **The artifact is untrusted data.** A candidate that escaped the sandbox could have written it. Before anything is pushed, `ludion deliver open` checks, and refuses the whole artifact on any failure:
  - the receipt's size (at most 8 MiB) and shape, field by field; every name, version, advisory ID, hash and time it uses must match a strict pattern, so nothing in it can become Markdown or a mention in the PR; an advisory ID must be one a receipt can hold (OSV's GHSA, CVE and MAL, Packagist's PKSA), since it goes into the commit's "Fixes …" line, where `GH-1` would link issue #1;
  - the bundle's size (at most 64 MiB) and its heads: exactly one branch per fix the receipt says was `applied`, no other ref;
  - each branch's name, recomputed from the receipt's package and versions, and its commit, equal to the receipt's;
  - the commit's only parent is the commit this run checked out (the validated base, taken from the run, not from the artifact), as Git reads it (`git rev-list --parents`), and its tree is Git's (`rev-parse <commit>^{tree}`); its raw headers are exactly `tree`, `parent`, `author`, `committer`, in that order (Git counts only the `parent` lines right after `tree`, so a `parent` after `author` is no parent); and `git fsck` finds no error in it or anything it reaches;
  - its author and committer (Ludion's fixed identity), and its whole message, rebuilt from the receipt as `patch` writes it (so no `Closes #1` or trailer rides along);
  - the files it changes: exactly the receipt's files for that fix, each one a file the plan may change (for npm `package.json` and `package-lock.json`, for Composer `composer.json` and `composer.lock`, for Maven `pom.xml`, for PHP the Dockerfile named by `ludion.security.json` at the base commit), each already in the base commit with the same mode, nothing under `.github/`, each at most twice the base's file plus 1 MiB and never over 50 MiB (sizes as Git stores them, read before any blob; a lockfile padded with 40 MB of spaces packs into a 41 KB bundle), and each file's new bytes hashing to the receipt's `after_hash`;
  - **what the files say** (the receipt's hashes come from the same artifact, so they prove nothing alone), from the base commit and the fix's commit, by Git:
    - the manifest (`package.json`, `composer.json`, `pom.xml`) is exactly what `changedManifest` (inventory.ts, as `patch` calls it) makes from the base's files for the receipt's changes, so a new install script, dependency, Maven plugin or looser range is refused;
    - the Dockerfile changes only its FROM image, to the official PHP image of a newer release of the same branch and flavor, pinned by digest;
    - composer.lock changes no top-level key but its content hash and package lists, moves only the planned package and to the fix's version, keeps every other package as at the base apart from descriptive metadata (`time`, `published-time`, `support`, `funding` and the like), removes none, keeps the planned package's archive repository, source URL and type, adds only packages the fixed version (or a package it newly brings) requires, each from a pinned public archive (acquisition.ts's `publicArchiveUrl`) and none a Composer plugin or installer; `notification-url`, which Composer calls on install, may not change or appear;
    - package-lock.json, by install path (review 6518582507, B1 and N-a): every key is the root or an install path, read by the judge's own `lockKey`, and any other key (a project folder, or `aaaaaaaaaaaaminimist`, which npm installs nothing at) refuses the artifact rather than being skipped; at each install path where the base has the receipt's package (named by the path, never by an entry's own `name`) at a change's `from`, the fix has it at that change's `to`, under no other name, and each change has such a path; no install path still has it at a `from`; every added path is installed (not a link) and is what a moved or added path resolves, by Node's lookup, for one of its own requirements, and is the package that requirement names (no alias) at a version its semver range takes, as Composer's walk from the fixed version (gate 4: one fix per PR); every other entry is exactly as at the base, the root's apart from the fix's package's requirement; and the root and every entry the fix does not move resolve each of their requirements to the same path as at the base, so an added copy cannot shadow another package's dependency. The requirements walked are the lock's own, so the PR job then compares, per fix, each moved or added entry's requirements (`dependencies` with `optionalDependencies`, which the registry lists together, and `peerDependencies`), `os` and `cpu` with the registry's manifest for that name and version (`npmAgain`, only the package's name is sent), as `composerAgain` does with Packagist; a version the registry does not list, or a registry that cannot be read, fails that fix. `bin` and `hasInstallScript` are not compared. So a real fix that also changes another entry (a `dev` flag, a copy npm moved or deduplicated) is refused, which fails closed. `patch` does not fix workspaces, so no project folder belongs in a fix's lock. The judge runs again in the PR job (below);
    - Composer and Maven: each change goes to a higher version (osv.ts's `comparableVersion`), and for Composer from the version the base's lock has. npm's downgrades stop at the judge, and PHP's at the newer-release rule. In the PR job, OSV must list no advisory for the version a Composer or Maven fix moves to (below). Composer's added and moved entries and PHP's digest are checked against Packagist and Docker Hub in the PR job too (below).
- **Then, one fix at a time:**
  1. Is there already a PR for this fix? The fix's branch name names it (package and fixed version). An open PR from that branch: not opened again. A closed one, merged or not: not opened again either, and said in the job summary (someone closed it on purpose, or merged it). Every fix the PR job sees was applied again to this run's commit, so the default branch still lacks it: each run also prints a `::warning::` annotation for it (on stderr, so the step summary stays plain), and the run stays green. A closed PR therefore silences that version for good; reopen the PR or apply the fix by hand.
  2. Does the branch exist on GitHub? At the same commit: no push. At another commit whose tree is this commit's and whose only parent is the same base (an earlier run pushed it and could not open the PR, for example while the repository did not let Actions open PRs): no push, and the PR is opened from it. At any other commit: not changed (no force push, ever), and the fix fails, saying to delete the branch.
  3. npm: the judge again (candidate-judge.ts) on package.json and package-lock.json at the base and at the fix's commit. Anything but `ready_except_build` (a stop, a wait, undecidable, a lookup that fails) fails that fix, and nothing is pushed. It sends and downloads what `patch` does (package names and versions to OSV and the npm registry; CISA's catalog and FIRST's EPSS list whole). This checks the lockfile's entries against the registry (gate 4's tarball and integrity, gate 2's provenance and install scripts) independently of the artifact. Composer: each composer.lock entry that differs from every base entry (apart from descriptive metadata) must say what repo.packagist.org lists for that name and version in every key Composer installs or runs from (`dist`, `source`, `require`, `conflict`, `replace`, `provide`, `autoload`, `autoload-dev`, `bin`, `include-path`, `target-dir`, `extra`, `transport-options`, `type`). So neither another repository's archive, nor a fork's commit served through the upstream's URL, nor an added autoload file or requirement passes, and the "required by the fixed version" walk rests on Packagist's requirements. A lock entry with a key outside a fixed list, or a name listed twice (in either list), is refused. PHP: the digest the Dockerfile pins must be the one Docker Hub gives for the tag now (auth.docker.io's anonymous pull token, then the manifest's digest); a tag rebuilt between the two jobs fails the fix, to be made again on the next run. A lookup that fails fails the fix; nothing is pushed.
  4. Push the commit to the new branch, never forced: `git push` of `<commit>:refs/heads/<branch>` (no `+`, no `--force`) to the repository's own HTTPS URL, with the job's token passed to Git through its environment (`GIT_CONFIG_*`), not in its arguments or `.git/config`.
  5. Open one PR to the default branch. Title: the commit's subject. Body: built from the checked receipt fields only: the package and versions, the advisories, the base commit, that the project's own tests passed on the base and on this change alone in Docker, what the PR job checked again, the npm judge's verdict, the exposure-time timestamps (`fix_published_at` with its source, `found_at`, `applied_at`), and what was not checked. If GitHub refuses the PR after the push, the fix fails, and the next run opens the PR from the pushed branch (step 2) while the default branch has not moved.
- A fix that cannot be delivered stops no other fix. A failed fix or a branch Ludion will not move fails the job.

### What these checks do not cover

- **Composer archives' contents and Maven's transitive graph.** The PR job checks where composer.lock takes each package from, not what the archive holds, and Maven has no lockfile: what the build resolves is what the validation job tested, not something the PR job can see again.
- **A sandbox escape in the validation job.** The candidate runs in Docker with no network and no forwarded environment, but if it escaped to the runner, it would be on a runner that holds the job's read-only token and the runner's own `ACTIONS_RUNTIME_TOKEN`, which can write Actions caches for the default branch that other workflows of the repository restore (cache poisoning). The template uses no cache, but the repository's other workflows may. The PR job's checks bound what such an escape can get into a PR; they do not bound the cache.
- **A branch created between the check and the push.** The PR job asks GitHub whether the branch exists, then pushes without force. A branch someone creates in between at an ancestor of the fix's commit would be fast-forwarded. A lease that requires the branch to be absent would close this; it is not used, because every force flag is kept out of Ludion's push.
- **npm entries.** Since LB2a's second round every entry the fix does not move must be exactly as at the base, so a changed `dev`, `optional`, `bin`, `os` or `cpu` on such an entry is refused (until then they were not compared; review 6513705802, non-blocking 2). A moved or added entry's requirements, `os` and `cpu` are compared with the registry; its `bin` and `hasInstallScript` are not.
- **The PR body's facts.** The times and advisory IDs in the PR body are the receipt's, checked for form only; the body says so.
- **fsck covers the fix commits, not the unbundling itself.** The bundle is unpacked without Git's object checks; then, after each fix's parents and header order are checked, `git fsck` runs once, with the fixes' commits as the roots to trace from, before anything is pushed. It reads every object in the repository whatever roots it is given, so running it per fix only repeated it (review 6518582507, N-c). For the same reason an fsck error in the base checkout itself (an object a project's own history holds) refuses every artifact of that repository until the history is repaired: that fails closed, which is the side to fail on here. Until LB2a, fsck was not run, on the ground that every object the PR job acts on is read back and checked; review 6516135819 (N1) built a commit whose raw `parent` line Git does not read as a parent, which those checks accepted, so that ground did not hold. GitHub also checks objects it receives on push. fsck reads every object in the depth-1 checkout, under the 60 s limit of each Git call (branch.ts); a checkout too large for that refuses the artifact (nothing is pushed), and has not been measured.

## Trigger

`schedule` and `workflow_dispatch`, on the default branch only (both modes refuse any other event and any other ref).

- **The schedule can be hours late or not come.** In Ludion-ai/ludion-shadow, GitHub's hourly schedule did not fire once between 12:17Z and 17:17Z on 2026-10-29 (commit ec61bf9 there), and runs had to be started by hand until each run started the next one. GitHub's documentation says scheduled runs "can be delayed during periods of high loads" and, in a public repository, are disabled after 60 days without repository activity.
- **What this does to exposure time.** A late run adds its delay to the time from a published fix to its PR. The wait table's shortest wait is 12 hours, so a delay of a few hours is not hidden by it. The template runs every 6 hours at minute 23 (away from the top of the hour), so one missed run costs 6 hours, not a day. Each receipt's `found_at` is the run's own lookup, so a late run shows as a later `found_at`, not as a hidden gap.
- **Not chained.** The shadow's fix (each run dispatches the next) is not copied: a validation run builds and tests in Docker and can take many minutes, and a chain that fails stops silently. Whether to add it is for later, with measurements.
- `concurrency: ludion-${{ github.workflow }}`, not cancelled in progress, so two runs of the workflow never push the same branch at once, and another workflow that copies the template does not share its queue.

## A fix that already has a PR (gate 4)

"One fix per commit or PR." A fix is identified by its branch name: the ecosystem, the package and the fixed version (and the project's folder in its repository). branch.ts's cleaning merges names (`@foo/bar` and `foo-bar` both become `foo-bar`), and `-` joins the package and its versions, so the name stays as it was only when it can be read back in one way: no folder, every part unchanged by cleaning, one version, and no `-` in it. Otherwise it ends with 12 hex characters of a SHA-256 of the folder, ecosystem, package and versions (`fixBranchName`), so one fix's PR never silences another (review 6516135819, N9). The PHP and npm examples' names (`ludion/php/8.4.28`, `ludion/npm/lodash-4.17.21`) do not change; scoped npm names, Composer and Maven names, and projects in a folder get the hash. A branch made under the old name is not found under the new one: that fix is validated again and gets a new branch, and if the old name is now another fix's (as `@a/b`'s old `ludion/npm/a-b-1.0.1` is `a-b`'s), that fix stops with "holds another change" and the old branch is left alone (dependencies.test.ts). Nothing is released and the workflow has not run on GitHub, so no PR exists under an old name. If a PR from that branch is open, Ludion opens no second one, and does not move the branch to a newer base (no force push). When the default branch moves on and the open PR's lockfile conflicts, the PR stays as it is; rebuilding it is not built. A later fix of the same package at a newer version has another branch name, so it gets its own PR while the older one is still open; the older PR is not closed or marked as replaced (not built).

Each scheduled run validates every fix again, including ones whose PR is open: the validation job has no branches but the checked-out commit, so `patch`'s "branch exists, skipped" does not apply. That costs runner minutes, not correctness, since the PR job does not open a second PR.

## What is not built (matches docs/status.md)

- **Automatic merge.** Nothing merges a PR. Automatic merge needs (a) and (b) (CLAUDE.md, Product), and neither is met.
- **The exposure-time end.** When a fix reaches the project's configuration is the merge, and nothing records it. The PR shows `fix_published_at`, `found_at` and `applied_at` only. `found_at` is still the run's own lookup, not the first run that saw the fix.
- **A project apply setting.** Adding the workflow is the only switch.
- **Gates beyond today's.** The PRs carry what `patch` checks today, no more. The npm judge's gates 1, 2 and 4 and its waits apply to npm fixes only; Composer, Maven and PHP fixes do not go through them; gate 1's OS/SAPI/configuration matching, gate 2's code inspection, gate 3's load check and the re-query when a wait ends are not built anywhere. The PR body says so and does not call the fix gated, waited or "passed the four gates".
- **CI on the PR.** GitHub starts no workflow for a PR or push made with the job's own token (`GITHUB_TOKEN`), so the project's CI does not run on Ludion's PRs by itself. Someone must start it (close and reopen the PR, or push), or the workflow must use a GitHub App's token, which needs an app and a secret. Not built.
- **Repository setting.** `GITHUB_TOKEN` can open PRs only when the repository allows it ("Allow GitHub Actions to create and approve pull requests", off by default). Ludion does not change the setting; the PR job pushes the branch, fails with GitHub's answer, and opens the PR from that branch on a later run once the setting is on, if the default branch has not moved; once it has moved, the fix fails until someone deletes the branch.
- **Superseded and stale PRs.** Closing a PR whose fix a newer one replaces, or rebuilding one whose base moved, is not built.
- **Not run on GitHub.** This stage runs both jobs' commands locally in Docker (below). Nothing has run on GitHub, and nothing is placed in any user repository or in ludion-sandbox. In particular, whether GitHub accepts the push and the PR exactly as the local stand-in did is not known until it runs there.
- **Release.** None (CLAUDE.md, Goal). The template pins a placeholder SHA, because no release commit exists.
