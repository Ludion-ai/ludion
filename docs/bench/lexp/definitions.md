# LEXP: the end of exposure time, and found_at from the first run that saw the fix — definitions (2026-11-01)

Committed before the tests, the code or any run, so that no definition is loosened after a result is seen (git history shows the order). These are definitions of what the scheduled workflow records and how it is tested; nothing here changes a gate, the wait table or a rule of CLAUDE.md. Starting point: main 10e5963892f63733489eca97f4eeb4dcc88deb3b.

What it builds (docs/status.md, "Missing before complete", item 2: "the exposure-time end (the merge is not recorded), found_at from the first run that saw the fix rather than the run's lookup"):

1. the merge of a PR Ludion opened is recorded, on that PR, with GitHub's merge time: the end of that fix's exposure time;
2. the PR's "Found" time is the time of the first run, of an unbroken row of this workflow's runs, whose check saw the fix, instead of this run's lookup.

Neither needs a state ref (LB2b-next(2)'s), a new secret, a server or a store of Ludion's: both are read from and written to GitHub, in the user's repository.

## 1. Exposure time, and which time is its end

- Exposure time of a fix = its end − `fix_published_at` (CLAUDE.md, Product: "the time from a published fix to it being in the project's configuration").
- **The end** = `merged_at` that GitHub gives for the PR Ludion opened for that fix, when that PR is merged into the repository's default branch. At that time the fix is in the project's configuration on its default branch. It is not a deployment: when production gets the fix is not recorded, and the record says so.
- A fix with no `fix_published_at` (none, or not read, as the PR body says) has no exposure time; its merge is still recorded. An image move with no newer security release is not counted in exposure time (docs/decisions/2026-10-31-limgv-image-newest-built-release.md), and its record says so.
- **Not an end, so not recorded:** a PR closed without merging; a merge into another branch; the fix reaching the default branch by any other way (applied by hand, by another tool's PR, a cherry-pick); a merge whose `pull_request` event starts no workflow run (for example a merge made with a workflow's own token, for which GitHub starts no workflow). These fixes have no recorded end.

## 2. Where and how the merge is recorded (the template's fourth job)

- The template (action/patch-workflow.yml) also runs on `pull_request` of type `closed`. A fourth job, `merged` (action.yml `mode: merged`), runs only when that PR was merged and its head branch starts with `ludion/`; the three scheduled jobs do not run on that event.
- The job has `pull-requests: write` only (no contents, no secret), checks out nothing and runs only the bundled CLI: `ludion deliver merged`.
- It reads the PR through the API and records only when all of these hold: merged is true; `merged_at` is a time and `merge_commit_sha` a full SHA; the PR's author is `github-actions[bot]`; its head is in this repository and its head ref matches Ludion's branch names; its base ref is the default branch; its body starts with Ludion's marker line `<!-- ludion-fix -->`. Otherwise it records nothing and says why (exit 0). A failing API call fails the job.
- **The record** is one comment on that PR, by the job's token, whose first line is a marker `<!-- ludion-merged {…} -->` holding the record as JSON (schema 1: the PR number, head ref, `merged_at`, `merge_commit_sha`, and `fix_published_at`, `found_at`, `applied_at` as the PR body gives them, or null; then `recorded_at`, `answer_date` and `merged_at_doubt`, below), then a table for people: the times, the hours from published to merged (exposure time), from published to found, and from found to merged.
- **GitHub's clock** (section 7): before `merged_at` is used as the end, it is compared with two other clocks: the Date header of the same answer of GitHub's API, and this job's runner's clock. When `merged_at` is at least one second later than that Date (the Date header is in whole seconds, so a time before the answer is less than one second past it), or later than the runner's clock, GitHub cannot have merged the PR then. The merge is still recorded, once, with `merged_at` as GitHub gave it, but `merged_at_doubt` says why and by how many minutes, and the hours that end at the merge (exposure time, found → merged) are not computed. With no doubt, `merged_at_doubt` is null. The record also keeps `recorded_at` (the runner's clock when the job read the PR) and `answer_date` (that Date header as a time, or null when it is absent or not a date), so that a reader can count apart a record whose merge time is far from the time the job ran (the job starts after the merge, so the gap is normally small).
- The three earlier times come from the PR body that Ludion's PR job wrote. The body can be edited by anyone who can edit the PR, so the record says that they are the body's, checked for form only (as the body already says of the receipt's). `merged_at` and the merge commit are GitHub's.
- **Once per PR:** when the PR already has a comment by `github-actions[bot]` starting with `<!-- ludion-merged`, nothing is posted again (a re-run of the job). At most 1,000 comments are read for this; with more, it posts.
- A negative duration (a body time later than `merged_at`) is shown as not computed, with the reason.

## 3. found_at: the first run that saw the fix

- **What a run saw** is recorded by its check job (it runs no dependency code and holds `contents: read` and `pull-requests: read`): whenever `ludion check` decides, it writes `seen.json` and the job uploads it as the artifact `ludion-seen` (retention 90 days, or the repository's limit when that is shorter). The record: schema 1, `checked_at` (the check's own time), the run's commit, the policy's ecosystem, and per key (definitions of LB2b-next(1), item 3) the advisory IDs of its findings (npm, Composer), or, for an image, the newer security releases the scan lists and the candidate version. An undecided check writes no record. The check's answer (`work`) does not read any record; this changes nothing in how it decides.
- **The fix's identity** across runs: npm and Composer: the same ecosystem and package, and at least one advisory ID the fix's changes name; an image move with a newer security release: at least one of the security releases the fix's receipt lists; an image move with none: the same candidate version.
- **The walk** (the PR job, `ludion deliver open`, only for a fix it is about to open, once per run): from this run back, newest first, through this workflow's runs on the default branch started by `schedule` or `workflow_dispatch`, at most 100 runs:
  - a run whose record is readable and valid (below) and lists the fix: the fix was seen then; go on to the run before it;
  - a run whose record is readable and valid and does not list it: the row ends; stop;
  - a run with no record (the check did not decide or failed, the artifact expired or was not uploaded, it cannot be read or is not valid): passed over; it neither lists the fix nor ends the row;
  - a run whose times do not agree (section 7): its live artifact's `created_at`, or the run's `run_started_at`, is at least one second later than the Date header of the GitHub answer that gives it, or its record is valid but its `checked_at` does not lie between GitHub's `run_started_at` of its run and GitHub's `created_at` of its artifact: the walk stops there. Its record is not used, the runs before it are not read, and a row that has not ended there is left open (an earlier run may have seen the fix first).
- **found_at** = the earliest `checked_at` among the runs of that row that list the fix, or the receipt's `found_at` (this run's lookup) when that is earlier or when no record lists the fix.
- **A record is valid** when it is at most 1 MiB, a zip whose `seen.json` entry is stored or deflated, at most 1 MiB once inflated, JSON of the shape above, every value matching the PR job's strict patterns (advisory IDs as `ADVISORY`, versions as `VERSION`, keys as `ludion check` writes them), the ecosystem is the policy's at this run's base, and its `checked_at` is a date (section 6). A valid record is used only when its run's times agree (above).
- **This run's own time** (section 7): before any record is read, this run's `run_started_at` is compared with the runner's clock (the PR job's, which runs after the run started) and with the Date header of the answer that gives it. When it is later than the runner's clock, or at least one second later than that Date, GitHub's times and the runner's do not agree, and the walk is not done (Without state, below).
- The artifact's download is GitHub's API (`actions: read`, which the PR job gets in the template), then the address GitHub redirects to, fetched over https without the token.
- **Without state** (the definitions of LB2b-next(1), item 1: no state ref yet): this walk is the stand-in for one. When it cannot be done — the PR job's token cannot read the runs (no `actions: read`), GitHub's API fails, this run's own run cannot be read, or the walk has taken longer than 5 minutes (each request also has its own 30-second limit; added after the review, section 5), or this run's own time does not agree with the runner's clock (added in section 7) — found_at is the receipt's (this run's lookup), the PR body says that and why, and the fix is opened as before. The walk never stops a fix.
- **What the PR body says** in its "Found" row: the time; which run's check saw it first; how many records were read; when the walk stopped at the limit or at the oldest run GitHub listed while the row had not ended, that an earlier run may have seen it first; and, when the walk stopped at a run whose times do not agree while the row had not ended, which run, which times disagree and by how many minutes (section 7). Both clocks' times are kept in the row (section 8). The receipt keeps its own `found_at` (that run's lookup), unchanged.
- **What found_at can be wrong about, stated:** a record is data written by the run's check job, but the same run's patch job, which runs candidate code, holds the run's artifact token, so a candidate that escaped the sandbox could replace or delete its own run's record. A deleted record makes the walk pass over that run, and a replaced one may list the fix or not, so the row can end early at that run, or be carried past it where its true record would have ended it. found_at can then be later than it should be, or earlier: as early as that run's start (the bound on `checked_at` keeps a forged time inside that run's span), or the time of an earlier run past it whose own record lists the fix (section 5). A run GitHub did not start saw nothing. found_at is a measurement: it decides nothing (no wait, no gate, no PR).

## 4. Tests (written first; each must fail on 10e5963)

In packages/cli/test, run in Docker (node:24 pinned by digest, a copy in the volume ludion-lexp-w, `npm ci --ignore-scripts` with the network, everything after it with `--network none`, no Docker socket, `--memory 4g`, the worktree mounted read-only). GitHub's API and the artifact download are stand-ins; no test reaches the network.

- X1: `deliver merged` on a merged Ludion PR posts one comment whose first line is the marker with the JSON record (merged_at, merge commit, the body's three times) and whose table gives the exposure hours; a second call posts nothing.
- X2: it records nothing for a PR that is not merged, not by `github-actions[bot]`, from another repository, from a branch that is not Ludion's, into another branch, or without the marker; a failing API call throws; an image move with no newer security release is recorded with "not counted"; a body time later than merged_at is not computed.
- X3: `ludion check --seen <file>` writes the record of section 3 when it decides (advisories per dependency key; releases and candidate for an image) and writes nothing when it does not.
- X4: the walk: found_at is the earliest run of the row that lists the fix; a run whose valid record does not list it ends the row; a run with no record, an expired one, an invalid one (wrong ecosystem, a time outside its run, a bad advisory, not a zip, too large) is passed over; another advisory of the same package does not match; the limit of 100 runs is kept and the body says an earlier run may have seen it; runs of another event or branch, or later than this run, are not read; the download goes to the redirect without the token.
- X5: when the runs cannot be read (403, an error), found_at is the receipt's, the body says why, and the PR is still opened; the walk is not done for a fix whose PR exists.
- X6: the template and action.yml: on `pull_request` `closed` too; the `merged` job has `pull-requests: write` only, runs only for a merged PR from a `ludion/` branch, and checks out nothing; check, patch and the PR job do not run on that event; the PR job has `actions: read` added and nothing else; the check job uploads `ludion-seen` and still downloads no artifact; the concurrency group keeps a merge's run out of the scheduled runs' group; every action is pinned by a full SHA; start.sh accepts mode merged on `pull_request` only and refuses it elsewhere.

## 5. Changed after the review of b5097c2 (2026-11-01)

- **found_at** (its N4): no change to the text of section 3. The code had taken the record of the lowest run id of the row, which is later than the earliest `checked_at` when an older run was re-run; it now takes the earliest, as written.
- **Without state** (its N7): a fourth case, the walk taking longer than 5 minutes, was added. Before: "When it cannot be done — the PR job's token cannot read the runs (no `actions: read`), GitHub's API fails, or this run's own run cannot be read — found_at is the receipt's (this run's lookup), the PR body says that and why, and the fix is opened as before." In that case found_at is this run's lookup, which is not earlier than what the walk would give.
- **What found_at can be wrong about** (its N5): the bound was stated too narrowly. Before: "the bound on `checked_at` keeps a forged time inside that run's span, so the effect is at most a found_at moved to another run of the row, or a row ended or passed over early." - **Tests added** (its N1, N2, N3): a deflated zip under 1 MiB whose valid record inflates past 1 MiB is passed over (X4); a deliver test in which every record that lists the fix is later than the receipt's lookup keeps the lookup (X5); a body time with the form of a time but no date (`2026-13-45T00:00:00Z`) is recorded as unknown, and a `merged_at` like it is not recorded (X2; before, both threw).

## 6. Changed after the review of 620aeae (2026-11-01)

A fresh-context review of the fix at 620aeae (PR comment 6554998194) asked for main to be merged (docs/status.md conflicted) and listed five more items. What changed here, with the text before:

- **A time that is a date** (its N9). Section 5 and the code took a time with the form of one (`TIME`) as a date when `Date.parse` gave a number. `Date.parse` rolls a day past the month's end and the hour 24 over to another date (`2026-02-30T00:00:00Z` is read as 2026-03-02, `2026-10-31T24:00:00Z` as 2026-11-01), so such a time was recorded as that other date. Now a time is a date only when it reads back the same: `new Date(t).toISOString()` equals it with its milliseconds written out to three digits. This holds for a PR body's time in the merge record (otherwise unknown, as before), for `merged_at` (otherwise not recorded, as before) and for a record's `checked_at` (otherwise the record is not valid, and its run is passed over, as for any record that is not valid). This is stricter than before; nothing that was refused is now accepted. Section 5's "a body time with the form of a time but no date (`2026-13-45T00:00:00Z`)" is still true; the rolled-over times are now in the same case.
- **The PR body after the walk's limit** (its N13). Before: "earlier runs' records were not read: …". Some records may have been read before the limit and then not used, so it now says "earlier runs' records were not used: …". Nothing else in what the body says changes.
- **Tests added** (its N10, N11): the walk's limit holds while the runs are listed, before any record is read (a stand-in whose list pages take 3 minutes each stops at the third page); the record is inflated with a limit of 1 MiB (a pass-through stand-in for `inflateRawSync` records the options it is given). Both pass on the code before this change, which was right; the review's mutations Q6 and Q9, which survived before, are caught by them.
- **Section 5's count** (its N12): section 5 said "a fifth case"; the list of cases in section 3 has four (no `actions: read`, an API failure, this run not readable, the 5-minute limit), and section 5 now says "a fourth case".

## 7. Changed after an audit of GitHub's clocks (2026-11-01)

An audit of this PR at e623489 reported that on 2026-11-01 GitHub's API gave some stored times (a PR's `created_at` and `updated_at`, workflow runs' `run_started_at` and `completed_at`) exactly one hour later than the Date header of the same answer and than other clocks, from some time between 07:45 and 08:01 UTC. Whether `merged_at` was later too, why it happened and how long it lasts were not checked here. Sections 2 and 3 compared the runner's clock (a record's `checked_at`, from the check job's runner) with GitHub's times (`run_started_at`, an artifact's `created_at`, `merged_at`) as one clock, with no check that they agree:

- while GitHub's run times were an hour later, every record's `checked_at` lay before its run's `run_started_at`, so every record was not valid and its run was passed over, and the PR body said "no record of this workflow's runs lists this fix; `0` records read", with nothing about the clocks;
- a `merged_at` an hour later would have been recorded, once, as the end, and the exposure time an hour longer.

What changed, with the text before:

- **Section 2, GitHub's clock** (new): `merged_at` at least one second later than the Date of the same answer, or later than the runner's clock, is recorded with `merged_at_doubt` and its hours to the merge are not computed; `recorded_at` and `answer_date` are kept in the record. Before, the record held only the fields listed in section 2, and every `merged_at` that was a date was the end. Nothing that was recorded before is now not recorded; a record now says when its end cannot be used.
- **Section 3, the walk** (new case): a run whose times do not agree stops the walk there, and the PR body says which run, which times and by how many minutes. Before, a record whose `checked_at` was outside its run was not valid, so its run was passed over, with no word in the body. "A record is valid" before: "… and its `checked_at` is a date (section 6) and lies between GitHub's `run_started_at` of its run and GitHub's `created_at` of its artifact." Stopping, rather than passing over, means such a record can no longer carry the row past its run (its true record might not list the fix), so found_at can only be later than, or the same as, what passing over gave; the body says an earlier run may have seen it first.
- **Section 3, this run's own time** (new): the walk is not done when this run's `run_started_at` is later than the runner's clock or at least one second later than the Date of its answer; the body says why, with the minutes, and keeps this run's lookup. This run's lookup is never earlier than what the walk gives, so found_at cannot move earlier by this.
- **The one second** is not a margin added to a definition: the Date header is in whole seconds, so an answer made at 08:32:10.9 says 08:32:10, and a time before that answer can be up to 0.999 seconds past its Date. GitHub's `merged_at`, `run_started_at` and `created_at` are in whole seconds, so for them "at least one second later than the Date" is the same as "later than the Date". The comparisons with the runner's clock and the window of `checked_at` have no margin.
- **Not covered:** GitHub's times earlier than they should be, by less than the time between the event and the answer, look like a normal answer here; a merge record keeps `recorded_at` so that a reader can count apart one whose `merged_at` is far before it. A Date header that is absent or not a date is not compared (`answer_date` is null); the runner's clock still is.
- **Tests added** (X7): a stand-in whose run times are an hour later than the runner's clock, or later than the Date of the same answer; a run, earlier than this one, whose record's time lies an hour before its run's `run_started_at`, or after its artifact's `created_at`, or whose artifact's `created_at` is later than the Date of its answer; a `merged_at` later than the Date of its answer, or than the runner's clock. Each fails on e623489, and a mutation that removes each check is caught.

## 8. Both clocks' times are kept (2026-11-01)

A rule was set for this lane after section 7: times of different clocks are not compared with no margin; a comparison takes the Date header of the same answer as its upper bound; a record keeps both times, GitHub's and the runner's `now()`; and when they disagree, it says so and drops nothing in silence. At 1ac44e8 the merge record kept both (`merged_at`, `answer_date`, `recorded_at`), but the walk's only record, the Found row, kept one clock or a difference: the row named a run and a `checked_at`, and a disagreement gave only its minutes. What changed, with the text before:

- **The Found row, a walk that was done** (new): it also gives this run's times, GitHub's start of this run, the Date of GitHub's answer that gives it (or says there was none) and the PR job's runner's clock; and, when a run's record gave found_at, GitHub's start of that run beside its `checked_at`. Before: none of these.
- **The Found row, a run whose times do not agree:** it gives both times as well as the difference. Before: "its record's time is `60.0` minutes before GitHub's start of that run". Now: "its record's time `<checked_at>` is `60.0` minutes before GitHub's start of that run `<run_started_at>`", and likewise for the artifact's upload time and for the Date of an answer.
- **The Found row, a walk not done because this run's own time does not agree:** the reason ends with GitHub's start and this runner's clock, and the Date when that is the comparison that failed. Before: only the difference.
- Every such time is written from the parsed number as an ISO time, so no text from GitHub or a record reaches the row.
- **What decides is unchanged.** No comparison, no window, no stop and no case of section 3 or section 7 moves: found_at, the row's end and the walk's stop are the same as at 1ac44e8. This only adds what the row keeps.
- **No margin on the runner's clock, still** (section 7, "The one second"): this run's start against the runner's clock, the window of `checked_at` and `merged_at` against the job's clock are compared with no margin, as the rule's first line asks not to do. They are left so, because a margin is a looser definition: a record up to that margin outside its run would be used, and the bound of section 3 on a forged `checked_at` would widen by it. The difference between the runners' clocks and GitHub's has not been measured, so no width could be justified. What such a comparison gets wrong is a small difference taken as a disagreement. It errs on one side: the walk stops or is not done, so found_at is later or the same, or a merge's hours are not computed while `merged_at` stays in the record, and each says so with both times.
- **Tests:** X7's tests give both clocks' times in the Found row, for every kind of disagreement and for a walk that agrees. They fail on 1ac44e8's code. X7 already holds a shifted and an unshifted time in the same test (this run's start an hour past the runner's clock, then a second before it; `merged_at` an hour past the Date, then the same second).

## Not done here

- No run in a GitHub repository (the action has no release commit with its bundle; the template keeps a placeholder SHA). Whether GitHub starts the `pull_request` `closed` run for a PR opened with a workflow's token, when a person merges it, is not tested on GitHub here.
- The median exposure time and human minutes per fix are not computed: the records they need now exist on each merged PR; a reader that collects them is a later lane.
- The state ref, notification, the ignore list, the hourly cron and the push trigger (LB2b-next(2) and (3)).
