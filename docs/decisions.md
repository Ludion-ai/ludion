### 2026-10-13: Counting index requests (Analytics Engine)

- **Why.** Nothing says how many people use `ludion sync`. npm's download counts include CI and mirrors, and the CLI sends no identifier. The owner asked (2026-10-13) for the Worker to count distinct clients of `/index/*.json`. This is server-side counting of requests the CLI already makes; the CLI sends nothing new except the `User-Agent: ludion-ai/<version>` from 0.1.4, which names only its version. "No telemetry" in the README and on `/start` is about the CLI and stays true; both now also say what the server counts.
- **What.** For each successful `GET` of `/index/<name>.json`, one Analytics Engine data point (dataset `ludion_index_hits`, binding `INDEX_HITS`): `index1` = the key, `blob1` = UTC day, `blob2` = the path, `blob3` = `ludion-ai/<version>` or `other` (the CLI's own User-Agent is stored whole, which is only its name and version; any other User-Agent is stored as `other`); Analytics Engine adds an exact timestamp to each point. The key is the first 128 bits of HMAC-SHA-256, under the Worker secret `ANALYTICS_SALT`, of the day, the `CF-Connecting-IP` address and the User-Agent. The address, the secret and any User-Agent other than the CLI's are never written. Code: `apps/worker/src/index-counts.ts`, route in `apps/worker/src/app.ts`.
- **Why a keyed hash, and a secret.** The request was a daily-salted hash. A salt that is public (the date) leaves an IPv4 address recoverable by trying them all, so "no raw IP is stored" would be true in letter only. A secret key makes the hash unrecoverable **by anyone without it**, and the day inside the input makes it a different key every day. **Whoever holds the secret can compute any known address's key for any past day, and can recover IPv4 addresses for the CLI's User-Agent by trying them all**: the secret never changes, and Analytics Engine keeps the points for months. So the value is generated, set with `wrangler secret put`, and not kept anywhere. After that, only code deployed to the Worker, and whoever controls the deploy or the Cloudflare account, can read it. **`apps/worker/src` is not a protected path, so a pull request that reads the secret would auto-merge on green CI**; whether to protect that folder (a CLAUDE.md change) is the owner's call. A random key thrown away each day would need storage (another protected change); not done. **The path is not in the hash** (the request listed UA, path and address): with the path inside it, one client asking for `subjects.json` and `vitest.json` would count as two. The path is its own field.
- **Fails closed.** No secret, a secret shorter than 32 characters, no client address, no dataset binding, a non-`GET`, or a path that isn't a shard: nothing is written and the shard is served as before. The write happens in `waitUntil`, after the response is built, and a failure is caught: counting can't break `sync`. So after this merges nothing is counted until the owner sets the secret.
- **What the number means.** Per day, a client is an (address, User-Agent) pair: people behind one address count once, someone whose address changes counts more than once. Because the key rotates daily, **a week is client-days, not people**: the same machine on three days is three. A weekly distinct count needs a key that lasts a week, which is a stronger kind of tracking; not done, and the owner's call. The SQL and a script are in `docs/bench/2026-10-13-index-counts/`, with no results yet: there are no data points until the secret is set. Retention and sampling are Analytics Engine's, not ours.
- **Cost of the route.** `/index/*` is added to `run_worker_first` in `wrangler.jsonc` so the Worker sees the request; static assets alone don't run it. So every shard request is now a Worker invocation instead of a free asset request; how many that is hasn't been measured, and it counts against the plan's Worker request limits. Cloudflare's documentation says requests matching `run_worker_first` get a 429 once the plan's limits are exceeded, instead of falling back to the static file, and `sync` treats that as a failure (it keeps its old lessons file); which plan the account is on isn't known here. It also puts the Worker in the path of `sync`; the handler is a pass-through to `ASSETS` and the tests check that a missing secret, a failing dataset, and a 404 all leave the response alone.
- **Cloudflare's own logs.** `wrangler.jsonc` has `observability.enabled`, so every shard request, now a Worker invocation, can get a Workers Logs entry. Cloudflare's documentation says those hold the request, the response and related metadata for a few days, and doesn't say whether the address or the User-Agent is in them; not verified. `/start` says Cloudflare keeps its own request logs. Turning off invocation logs (`observability.logs.invocation_logs: false`) would also drop them for `/mcp` and `/@*`, which are the only diagnostics those routes have; left on, and the owner's call.
- **Not decided here, left to the owner:** whether to count weekly (above); whether to count `/index.json` (the whole index, which the CLI doesn't use) or the MCP route; any retention shorter than Analytics Engine's.

### 2026-10-12: The seed pipeline (`tools/seed`)

- **What it does**, one step per command, each reading and writing JSON in one folder so any step can be rerun and a stopped run resumes:
  1. `collect`: the package's stable versions in a range (or published since a date) from the npm registry, and each version's GitHub release notes, split into entries (top-level list items with their indented lines; "Updated dependencies" dropped).
  2. `triage`: a model with no tools (Sonnet) sorts each entry: a lesson candidate with a first guess at kind and signal, or a skip with a reason (internal, a fix that makes the docs true, docs, experimental, another package, unclear). The prompt carries the added-vs-default check ("does code that doesn't use the new thing behave differently?").
  3. `draft`: one agent per candidate (Sonnet by default; the agents and vitest runs and the first 20 wrangler drafts were Opus, before the spending rules), in a folder with the entry, the pull requests it links (description, files, diff), the pages it may quote with their URLs (the package's CHANGELOG.md section at the release tag, and docs files the PRs changed, all raw from GitHub), both published package versions, and lessons on main as examples. It can read and write in that folder only: no shell, nothing runs. It writes a format 1 draft with a differential test pair (same code, the release and the one before) and a quote, or skips with a reason. Order: default, behavior, deprecated, renamed, removed, then added; silent before loud.
  4. `check`: every check this machine can run without Docker: the schema, `lessonProblems`, and the quote found on its page through the guarded fetch. The lesson is signed by @Ludion-ai (the account that opens seed PRs) with `drafted_by: "agent"`; the draft can't set id, author or time.
  5. `review`: a fresh-context model with no tools (Opus; wrangler's first two rounds were Sonnet, under the spending rules, before the owner fixed the reviewer as Opus) reviews each lesson against the seed checklist (`docs/decisions.md`, "Seed lessons") plus "the claim is true as an assistant would read it".
  6. `revise`: first the local-check problems alone go back to the drafting model (`--scope check`); after the review, the findings go back once, to Opus for content findings (`--scope findings`; see "Revising seed drafts"). The agent fixes or skips. Then `check` and `review` again (`--round`).
  7. `lessons`: lessons with no problems and no findings are written as files for a PR, one PR per subject. One that repeats a lesson already on main (same versions, same or overlapping symbol) is listed as a duplicate and not written.
  8. `ci` and `fix`: CI's `verify` runs the tests in Docker on the PR; `ci` reads its results, and `fix` gives each failure back to its agent once with CI's reasons.
  9. `bench`: per kept lesson, a question and key written from the changelog entry and the primary source (never from the lesson's wording), each measured model answering once with no tools (the `models` labels), and the harm check (Opus with the lesson in context vs without; every loss is read by a person). **Paused** by the spending rules: new lessons get no `models` entry.
- **Lesson code never runs on this machine.** The drafting agents can't run anything; tests run only in CI's Docker.
- **The reviewer was calibrated** on the 30 accepted seeds on main (`calibrate.ts`): its finding rate on lessons people accepted is the baseline for reading the pipeline's counts.

### 2026-10-12: Revising seed drafts: machine-check fixes first, then Opus for content, once

The owner's decision on who revises (a spending question that `docs/bench/2026-10-12-seed/README.md` left open):

- **Machine-check problems go back to the drafting model first** (Sonnet, `revise --scope check`): a quote that doesn't name the symbol, no evidence that names it, a detail with words no quote holds, a quote not found on its page, a schema error. The agent gets only those, with how each check judges (`CHECK_RULES` in `tools/seed/src/ci.ts`), and is asked to change nothing else. These failures are mechanical, and the drafting agents can't run the checker (no shell), so they learn of them only afterwards; that doesn't need a stronger model.
- **Then the review, by Opus, always** (`REVIEW_MODEL`): the hand-made seeds' baseline (10 of 30 with no finding) was measured with Opus, so a pipeline count compares only under the same reviewer. A draft unchanged since the previous round keeps that round's review by the same model (`reusableReview`): reviewing it again would only reroll the reviewer until it passes. Review files now record their reviewer (`model`); the earlier files got it added from the run notes (agents and vitest Opus, wrangler Sonnet).
- **Only content findings go to Opus** (`CONTENT_MODEL`, `revise --scope findings`): a lesson with a finding under checklist rule 1 (says more than the evidence), 7 (kind, symbol, versions, or replacement don't match the entry), or 8 (would mislead an assistant) is revised by Opus, with all its findings. A lesson with only other findings (rules 2 to 6) or only local-check problems goes to Sonnet. **One round**, then `check` and `review` again, and what is clean is written for a PR. Why Opus here: with Opus revising, agents reached the hand-made seeds' clean rate; one Sonnet round on wrangler moved nothing.
- **Machine-check problems the Opus round brings in go back to Sonnet once more** (`revise --scope check` again), then the Opus review of what changed. The Opus round stays one. Why: in vitest, Opus's revisions broke the local checks in 5 of 28 (4 gave more than 3 pieces of evidence), which is the drafting model's kind of fix. The drafting rules and `CHECK_RULES` now say evidence holds at most 3 pieces.
- **Drafting and triage stay Sonnet.**
- **Lessons already kept for a PR** (`kept.json`) are left out of later rounds and never written twice; `lessons` adds the new ones to `kept.json` with their round.
- Replaces, in "Spending": revising on Sonnet, and the per-lesson review on Sonnet.

### 2026-10-12: Unverified lessons in the personal ledger

- **`ludion teach` accepts a draft with no evidence** (no `evidence`, or an empty list) and saves it to the ledger as **unverified** (`"unverified": true` in the entry). People correct their assistants every day, mostly without a test or a quote at hand; refusing those corrections loses them.
- **"No evidence" means no `evidence` key or an empty list** (`hasNoEvidence`). Evidence in any other shape is checked as evidence and gets the schema's error, never quietly dropped.
- **Checked anyway** (`unverifiedProblems` in `packages/core`): every field but the evidence, against the format 1 schema (`validateUnverified`, which drops only the evidence errors); the subject, reserved names, and range; and **the detail stays grounded**, in the fields alone (package, versions, symbol, replacement), as for any lesson whose evidence grounds nothing. CLAUDE.md's grounding rule holds for every lesson, including a ledger one: an assistant can run `ludion teach` without `--public` (no confirmation), so ungrounded free text would be a way to put arbitrary sentences into every later session. Nothing is fetched and nothing runs.
- **Shown only to its teacher**: sync writes it in their own projects as "Taught by you (in your ledger, not public); unverified, yours only." (with ", drafted by an agent" for `--drafted-by-agent`). It never enters the index: the schema needs at least one piece of evidence, so `verify` refuses it.
- **`--public` still needs evidence**: with no evidence, `teach --public` stops before calling `gh` and says to add a test or a source. `ludion_teach` accepts such a draft too, returns the command with `"evidence": []`, and says it stays unverified in the user's ledger.

### 2026-10-11: Nightly reverify

- **`reverify.yml`** runs at 04:23 UTC every night and by hand. It has two jobs, so lesson code never runs next to a write token:
  - `check` (`contents: read`, no secrets, checkout without credentials) runs `npm run verify -- lessons/ --run --evidence-only` on main.
  - `report` (`contents: write` for branches, `issues: write`, `actions: write`) reads those results and runs only main's own `tools/verify/src/reverify-cli.ts`.
- **Evidence only, active lessons only**: format rules, paths and `replaces` were checked when a lesson merged, and a later rule change must not withhold lessons that still hold. A file today's schema can't read is skipped, not failed. Replaced lessons aren't served, so they aren't checked. Images are pulled before the timed runs.
- **What counts as failing**: a test that ran and failed counts at once. A failure that could be an outage counts only if the same lesson also failed the night before: every reason is a source check, a failed install, Docker not starting, exit 125, or a timeout. "The night before" is the newest completed run of this workflow on main from `schedule` or `workflow_dispatch`, at least 12 hours older. A pull request's run of an edited workflow never counts.
- **Too many at once means the check broke**: when more than 3 lessons and more than a fifth of all fail in one night, tonight changes nothing: last night's list stands (lessons already confirmed failing stay withheld, no new ones are), nothing new is reported, and the run fails so a person looks.
- **Failing lessons leave the index at once**: `report` uploads `failing.json` (lesson ids and when). It starts `deploy.yml` with its run id when the list differs from the newest list (the one production uses), and every night while the list isn't empty, so a failed deploy is retried.
  - `deploy.yml` accepts that run only if the runs API says it is a `schedule` or `workflow_dispatch` run of `.github/workflows/reverify.yml` on main from this repository, and fails if its list can't be downloaded. Without a run id, it uses the newest such run that has a list; with none, nothing is withheld (with a warning).
  - `buildIndex` takes failing lessons out after computing the active set, so a failing correction never brings back the lesson it corrected. They leave `index.json`, the shards, search, and the lists.
  - Their pages stay, with a banner: the lesson failed its nightly check, and Ludion stopped serving it until it passes its check again or is retracted. Main stays the truth: the lesson is only withheld.
- **Retractions are prepared, and a person opens them**: GitHub Actions can't open pull requests in this repository. Turning that on would also let workflows approve PRs, so it stays off.
  - For each failing lesson still on main, `report` pushes `retract/<id>` (deleting the file) and opens an issue labeled `retract`. The issue fences what failed as text, because it comes from lesson output, and links the one-click compare page to open the PR. A PR a person opens runs CI, which a PR opened by Actions wouldn't.
  - An issue that exists for the lesson, open or closed, isn't opened again: closing it is a person's decision. Ids and paths read back from the artifact are checked, and `git rm` gets `--`.
  - Upload and deploy come first, so a reporting error never stops withholding.
- **Accepted limits**:
  - If the example lesson (distutils) ever fails, deploys fail at the Worker tests and `check-production.ts` until it passes its check again or is retracted, and production keeps serving the last index. The fact is a removal from a released Python, so this is unlikely, and the failure is loud.
  - A deploy started by a push uses the newest reverify run that has a list, including one still going (its list is uploaded before it dispatches). Reverify also deploys every night while the list isn't empty, so a missed or failed deploy is caught up within a day.

    - AGENTS.md, if present, gets a block that names the file.
    - If `.cursor/` exists, `.cursor/rules/ludion.mdc` gets the lessons inline, because Cursor rules can't include files.
    - Every sync rewrites its own block and leaves the rest of the file alone.
  - **Writes stay inside the project**: sync will run on its own at session start in projects someone else prepared, so it refuses to write through a symlinked target or parent (checked with lstat, never existsSync, so a dangling link is caught too), checks that the real path is inside the project, and writes a temporary file in that folder and renames it over the target (a rename replaces a link instead of following it). CLAUDE.md and AGENTS.md are read only if they are real files.
  - **When the index can't be fetched** (no answer within 5 seconds, any error status, **404 included**), sync never blocks the session. If `.ludion/lessons.md` exists, it is left exactly as it was, with a warning on stderr: a rewrite would drop every public lesson the project has. With no lessons file yet, it writes the ledger's lessons. It exits 0 with `--quiet` (the hook) and 1 when run by hand. (Changed in 0.1.1, 2026-10-12. Before, a 404 counted as "no lessons", and any failure rewrote the file with the ledger's lessons only.)
  - **A wiring file that is a link or not a regular file** (`CLAUDE.md -> AGENTS.md`, or a folder) is skipped with a warning, not a failed sync. `.ludion/lessons.md` itself is never written through a link.
  - **package-lock**: only paths under `node_modules/` are packages (workspace folders aren't), an alias is recorded under the real name it installs, and lockfile v1's nested `dependencies` are read too.
  - Each sync finds its own end marker after its begin marker, so a stray marker elsewhere in the file doesn't make blocks pile up.
- **`ludion teach`**:
  - Takes a draft (a file, `-` for stdin, or `--draft <base64url>` from `ludion_teach`) and builds the lesson: a new id, the subject from the package, the author from the teacher's own `gh` (asked only with `--public`). A draft can't set its own id, author, or time.

  - It saves only if nothing failed.
  - `--public` needs `gh` signed in and **a person at a terminal**: it shows the whole lesson (including `replaces`, with control characters made visible so nothing can hide a line) and asks for confirmation. There is no flag to skip that, so an assistant can't confirm on the person's behalf. Then it opens the PR from the teacher's own account: a branch in the upstream repo when they can push, otherwise in their fork after syncing it.
  - The PR body says what changes (one new file) and how to undo it (delete the file).

### 2026-10-11: Lesson format 1

- **Two schemas.** `lessons/lessons.schema.json` is format 1, the only format a new lesson may use: `verify` checks added lessons against the base branch's copy of it. `lessons/lessons-v0.schema.json` is format 0, frozen, so the lessons already on main stay valid (lessons are immutable). Code reads either one (`validateLesson` dispatches on `format`). A format 0 lesson is corrected by a format 1 lesson that `replaces` it.
- **Fields** (canonical order): `format: 1`, `id`, `subject`, `package {ecosystem: npm | pypi | runtime, name}`, `versions` (semver range where the fact holds), `kind` (removed | renamed | deprecated | added | default | behavior), `symbol`, `replacement?` (required for renamed), `signal` (loud | silent), `detail?`, `evidence`, `author`, `author_id`, `drafted_by?: "agent"`, `replaces?`, `created_at`.
  - `subject` must equal the directory derived from the package: npm `@scope/name` → `scope.name`; anything else lowercased.
- The site's design samples include a format 1 lesson, and `test` builds them, so a page that only handles format 0 fails CI.
- **The claim is generated** (`packages/core` `generateClaim`): `<package> <versions> <removed|renamed … to|deprecated|added|changed the default of|changed what> \`<symbol>\` [; use \`<replacement>\` instead]. <Detail.> [Silent: code written for older versions still runs, without an error.]`, except that `kind: added` ends with "Older versions don't have it." instead, whatever its `signal` (changed 2026-10-12; 11 of the first 30 seeds are additions). "Silent" misled for an addition. "Nothing changes for code that doesn't use it" was considered and refused: the evidence (a test passing on the new version, failing on the old) shows only that older versions lack it, and an addition can bring a new default (`--durable-objects-code-update-mode`'s detail says what happens when it is unset) or react to an environment variable people already set (`DO_NOT_TRACK`). Same fields, same sentence. The index's `claim` holds it, so search, the site, and `ludion_ask` need no special case.
- **`symbol` and `replacement`** look like code: up to 6 space-separated tokens of identifier, path, flag, and call characters; no quotes, backticks, or angle brackets; no invisible characters, URLs, command lines, or instructions to an AI (unlike `detail`, `//` and square brackets are allowed, which is harmless inside a code span). The symbol must also appear in the evidence: in a test's code or a quote. Backticks are also stripped when the claim is built, so no field can end a code span early. This came from a security review: these fields go into the sentence assistants read.
- **`detail`**: at most 160 characters, **printable ASCII only, without backticks, `<`, or square brackets, and with no `//`** (so no markdown links or protocol-relative URLs). A lone `>` is allowed (changed 2026-10-11; it was refused before): vitest names a nested test `math > adds`, and without `>` a lesson about `-t` couldn't say the separator. In a bench run an assistant then guessed spaces, the old behavior. A lone `>` opens no tag or autolink, can't start a line in `lessons.md` (the detail follows the claim's first sentence), and claims already show ranges like `>=5.0.0`. Shell redirection (`>>`, `2>&1`, `> /path`) is refused with the command-line guard. The text guards come from #21: no invisible characters, URLs, command lines, or instructions to an AI. ASCII-only means lookalike characters (fullwidth letters, for example) can't slip past those guards, and no markup reaches the generated claim. Lessons are written in English.
  - It must be **grounded**: every meaningful word, lightly stemmed, must appear in a **source quote** or in the fields (package, versions, symbol, replacement).
  - Only articles, basic prepositions, and forms of "be" are ignored. Negations (not, no, never, without), comparatives (only, more, before, after), modals, and numbers all count, so a detail can't say the opposite of its quote.
  - Test code and expected errors don't ground anything: the teacher writes them, so they would ground any word. A lesson whose only evidence is tests can still have a detail made of its fields' words; anything more needs a source.
  - `verify` fails a detail that isn't grounded and names the missing words.
- **What the schema can't say** is checked by `lessonProblems` in `packages/core`, which `verify` and `ludion teach` both run:
  - the subject matches the package;
  - `versions` is a real range: `semver.validRange` accepts it, it doesn't mean every version (`*`, `x`, `||||`), and it has no empty `||` alternatives;
  - the detail is grounded;
  - every quote names the symbol, and at least one piece of evidence (a quote or a test's code) names it.
- **Follow-up**: a test that prints a `skip:` line still counts toward the derived label. The PR gets the `skipped` label for the maintainer; making the label depend on CI's result needs results stored with the index, which can come with reverify.
- **Evidence** is a test or a source.
  - **Test**: `{runtime, packages?, code, expect?, error?}`.
    - `runtime` is one of `node@18`/`20`/`22`/`24` or `python@3.9`–`3.14`.
    - `packages` holds at most 5 exact versions.
    - `expect: fail` needs `error`, and `error` goes only with it.
  - **Source**: `{url, quote}`. The quote is 40 to 300 characters, so a sentence rather than a headline, and **must name the symbol**, which `verify` checks; together that is how "states the fact itself" is enforced by machine.
- **Labels**:
  - `differential` (shown as "Verified across versions"): the **same code**, on the **same runtime with the same other pins**, passes on a version of the lesson's own package **inside** `versions` and fails as expected on a version **outside** it. So only the lesson's package differs. An npm pin counts only on a node runtime, and a pypi pin only on python. A runtime pin (node@22) names a whole release line, so it counts only when the entire line is inside (`semver.subset`) or entirely outside (`!semver.intersects`) the range; a range with a gap that cuts the line says nothing. A prerelease pin says nothing either, because ranges leave prereleases out. Anything less is labeled `test`;
  - `test`: any test;
  - `source`: sources only;
  - `proof`: format 0 Lean runs.
- **Running tests with pinned packages** (`tools/verify/src/docker.ts`), in separate containers. Every container is built by `buildDockerRunArgs` and gets the same hardening (see Runners). The network is the difference:
  1. Install is never the run container. Node uses two install containers. The lock step runs `npm install --package-lock-only --ignore-scripts --no-audit --no-fund --loglevel=error` and writes `package-lock.json` from the host-written `package.json`. The host then runs `checkNpmLockfile`: `lockfileVersion >= 2`, every non-root `packages` entry has `integrity` starting with `sha512-` and `resolved` starting with `https://registry.npmjs.org/`, no `link: true`, no git/file/http(s) spec outside that registry, and each pin is at `node_modules/<name>` with that exact version. The ci step runs `npm ci --ignore-scripts --no-audit --no-fund --loglevel=error`, which fails when a tarball does not match the lockfile. The lockfile is resolved from the registry at verify time (trust on first use). A lesson does not carry a lockfile; that would be a schema change, and it is not done here.
  2. Python is not installed. No current lesson uses pypi. Lessons carry a name and a version and no hashes, and there is no trusted hash source. `runInDocker` returns `pip install needs --require-hashes; the lesson gives no hashes` and does not start pip. `buildRequirementsTxt` writes `name==version --hash=sha256:<64 hex>` for a caller that already has hashes. The pip argv, when built, is `pip install --require-hashes --only-binary :all: --no-cache-dir --target /w/site -r /w/requirements.txt`.
  3. Before each install container, `assertInstallWorkDirClean` allows only the files that step needs (`package.json`, plus `package-lock.json` for ci, or `requirements.txt` for pip) and, for ci, the `.home` and `.npm` directories the lock step may have created. `.npmrc`, `.pypirc`, `pip.conf`, lesson or recipient code, anything else, and any symlink are rejected. `node_modules` must not exist yet. `buildDockerRunArgs` runs that check for an install work directory and throws before it returns argv.
  4. The install environment is an explicit allowlist (`HOME=/w/.home`, `npm_config_cache=/w/.npm`, `npm_config_userconfig` and `npm_config_globalconfig` pointing at paths inside `/w` that are not created, or `PIP_CONFIG_FILE` for pip). No `--env-file`, and no `-e NAME` without a value. Docker does not forward the host environment by default.
  5. The lesson code runs in a fresh container that always passes `--network none`. `/w` is a tmpfs (`--tmpfs /w:rw,noexec,nosuid,nodev,size=128m,mode=1777`), not a bind of the work folder: lesson code can create files there (for example `mkdir /w/proj`) and those writes are not stored on the host. Install results are bind-mounted read-only beneath it when the directory exists: `-v <workDir>/node_modules:/w/node_modules:ro` for node, and `-v <workDir>/site:/w/site:ro` for python. `buildDockerRunArgs` appends the `:ro`. Nothing else from the work folder is mounted. After npm ci succeeds, empty real directories `node_modules/.vite-temp` and `node_modules/.vite` are created on the host (a symlink or a file at either path is rejected), and the node run then adds `--tmpfs /w/node_modules/.vite-temp:rw,noexec,nosuid,nodev,size=32m,mode=1777` and `--tmpfs /w/node_modules/.vite:rw,noexec,nosuid,nodev,size=32m,mode=1777` immediately after the read-only bind so Vite's scratch writes stay off the host. The run phase never emits a writable bind of the work folder. `HOME=/tmp`, `NODE_PATH=/w/node_modules`, `PYTHONPATH=/w/site`, `LUDION_PACKAGES=/w`.
  - Timeouts: 30 seconds, 90 with packages (tests that start a tool such as vitest need longer), and 180 for each install. Containers are named, so a timeout kills the container itself, not just the Docker client.
  - Pinned packages are written in code-point order, so the canonical file doesn't depend on the machine's locale.
- **Removed with #13's teaching path**: the App bot rule in `verify` (any bot now fails: lessons come from the teacher's own account), and `/api/*`, `/auth/*`, and the `SOURCE_CHECK_LIMITER` binding in `wrangler.jsonc`.
- Not here yet: seed lessons, which will carry `drafted_by: "agent"`. Before the first one merges, the site, `ludion_ask`, and `ludion sync` must show that label wherever the lesson appears.
### 2026-10-11: Deploy safety (from #20)

- **Only main's newest commit deploys.** Right before `wrangler deploy`, `deploy.yml` fetches `origin/main` and fails if `HEAD` is older: "This run is for an old commit (…); main is now at …. Deploy main's newest commit with: gh workflow run deploy.yml --ref main". A rerun of an old run can't put old code over newer code, and a queued run whose commit was overtaken fails while the newer run deploys.
- **HSTS**: `Strict-Transport-Security: max-age=31536000` on every Worker response and every static asset (`_headers`). No `includeSubDomains` or `preload`, because both are hard to undo. Together with Always Use HTTPS on the zone, plain HTTP isn't served.
- **The command guard for Claude Code in this repo**:
  - `.claude/settings.json` denies, in Bash and PowerShell forms: `wrangler deploy`, `wrangler versions deploy`, `wrangler secret`, `gh secret`, force pushes, `gh repo delete`, bare shells, and `Invoke-Expression`.
  - A deny rule can't make an exception for `--dry-run`, and rules see each side of a pipe separately. So a PreToolUse hook (`.claude/hooks/guard.mjs`) sees the whole command line.
    - It splits the line into commands and pipeline stages, respecting quotes, and judges each command by the program it runs: through `npx`, `node …/wrangler.js`, `sudo`, and env assignments, and into `bash -c "…"` payloads.
    - Blocked: `wrangler deploy`, `versions deploy`, `versions upload`, `rollback`, and `delete` unless that command has `--dry-run`; `wrangler secret` and `versions secret`; `gh secret`; force pushes (`--force`, `--force-with-lease`, any short flag containing `f` such as `-uf`, and `+refspec`); `gh repo delete`; a download piped into a shell or interpreter that reads its program from stdin; and `iex` on a download.
    - Words that merely appear (a commit message, a grep pattern, a PR body) don't count.
    - Tests list what it blocks and what it lets through.
  - If `node` can't be found, the hook fails without blocking, and the deny rules still apply.
  - It backs up the rule that production changes only through `deploy.yml`.

## Carried over from v0

### Conventions

- TypeScript strict, Node 24 LTS (`.node-version`, used by CI and the deploy job), npm workspaces.
- Vitest 4 everywhere, pinned until `@cloudflare/vitest-plugin` supports a newer major, so Worker tests run inside workerd with the real `ASSETS` binding over the built site.

- Code outside `tools/` and build scripts uses only web-standard APIs (fetch, Web Crypto, Streams); Node-only APIs are allowed in `tools/` and build scripts.

- Small functions; no abstraction before the third use.
- Errors say what happened and what to do next, in plain words.
- Names in user language: teach, ask, lesson, teacher, sign, verified, checking.

### Infrastructure

- One Cloudflare Worker, `ludion` (Hono), serving the prerendered Astro site from `apps/site/dist` as static assets, `/index.json`, and `/mcp`. Custom domain `ludion.ai` in `wrangler.jsonc`. `run_worker_first` covers `/mcp`, `/mcp/*`, and `/@*`; `/@<login>` serves `/teachers/<lowercase login>/` from the assets, or the 404 page. (`/api/*`, `/auth/*`, and the `SOURCE_CHECK_LIMITER` binding were removed with format 1.)

The check needs the new `built_at` within 2 minutes, `/mcp` initialize answering 200, and `ludion_ask` about distutils returning "Taught by @"; any failure fails the job.

  - Administrators are included; force pushes and deletion are blocked.
  - Squash merge only, auto-merge on, head branches deleted after merge.

### Lessons and the index

- One file per lesson: `lessons/<subject>/<id>.json`, id a ULID, subject `^[a-z0-9][a-z0-9.-]{0,63}$` (also the directory). Canonical JSON (`formatLesson`: keys in schema order, absent optional fields omitted, 2-space indent, trailing newline); CI rejects anything else.
- The active set: all lessons on main minus every id named in another lesson's `replaces`.
- `index.json` (`{version: 1, built_at, lessons, teachers}`) is built from the active set at site build. Each lesson carries:
  - `teacher`: the current login for `teacher_id`, looked up by numeric id with `GET /user/{id}` once per id per build, falling back to the login stored in that teacher's newest lesson;
  - `verified_by`: `proof` if any Lean run, else `test` if any run, else `source` (format 1 adds `differential`; see "Lesson format 1");
  - `verified_at` and `pr`: from the git commit that added the file, where `pr` is parsed from the squash message's `(#n)` and a shallow clone is unshallowed first;
  - the lesson's GitHub URL.
- `teachers` is keyed by `teacher_id` (as a string). Lessons are sorted newest first, and the build warns above 5 MB. `index.json` is open to every origin (`Access-Control-Allow-Origin: *`), on purpose: the lessons are a commons.
- The Ajv validator is compiled ahead of time into `packages/core/src/generated/validate-lesson.js` (`npm run gen:validator`), because Workers forbid runtime code generation; a test fails if it is stale.

### CI (`verify.yml`, `test.yml`, `reverify.yml`)

- `verify` runs on every PR. It never uses `pull_request_target`, and it has no path filter, because a required check that never runs would leave PRs waiting forever.
  - It runs with `contents: read`, no secrets, and checkout with `persist-credentials: false` and `fetch-depth: 0`.
  - A PR that touches no lesson passes at once.
  - A lesson PR may change only `lessons/<subject>/<id>.json` files:
    - added ones are validated against the **base branch's** schema (read with `git show origin/<base>:…` and compiled at run time, so a PR can't loosen what it is checked against) and canonical form; their path is checked, `replaces` is checked against the base branch's active set, `run` evidence runs in Docker, and `source` evidence is checked;
    - deleted ones are retractions (label `retract`);
    - modified ones fail ("Lessons are immutable").
- **Trust boundary**: `verify.yml` checks the base commit out to `.verifier` and runs `node .verifier/tools/verify/src/pr-cli.ts`, so the checker is the base's `tools/verify`, not the PR's copy. (Replaces: verify ran the PR's own checker.) Lesson files are still read from the PR checkout. A human reviews before merging.
- **Isolated verifier deps** (`verifier-deps.ts`): `verifierDepsDir` is `ludion-verifier-deps-<first 16 hex of the lockfile sha256>` under a caller-chosen directory, and `buildVerifierDepsInstall` is `npm ci --ignore-scripts --no-audit --no-fund` there. That directory is isolated only when it and the recipient tree do not contain each other. On a run, `buildDockerRunArgs` bind-mounts it at `/verifier:ro` (the `:ro` is literal, not an option). The install phase refuses `verifierDeps`, and the mount may not overlap the work folder. `runInDocker` does not set it. Every bind-mount source (the install work directory, a run-phase `node_modules` or `site` directory, and the verifier deps) is realpath'd and must sit inside `realpath(os.tmpdir())` or, when that variable is set, `realpath(RUNNER_TEMP)`. The run phase does not bind-mount the work directory itself. `/w` there is a tmpfs, and the only work-folder binds are those install-result directories, read-only, when they exist. A source with a top-level `.git`, or one inside a git work tree below that root, is rejected, so `.git` is never mounted. That is the primary control. The write-check `.git` patterns are a secondary layer. `verify.yml` still checks the base out to `.verifier` inside the PR checkout and runs `npm ci --ignore-scripts` on the base lockfile there, so `results.json` reports `verifier.isolation.isolated: false` and `trusted: false` until a separate `.github` change moves that checkout (for example to `runner.temp`).
- **`results.json`** (`pr-cli.ts`) gains `verifier` beside `results` and `labels`, which are unchanged. `verifier` is `node_version`, `isolation` (a boolean and a fixed reason, with no path), `trusted`, and either `verifier_runtime` or `unavailable_reason`. When isolation fails, `trusted` is false, `verifier_runtime` is null, and `unavailable_reason` is `not_isolated`: the loaded vitest is not recorded. When isolation holds, `trusted` is true only if `verifier_runtime` validates. That object is exactly `vitest_location: "verifier_store"`, `vitest_realpath` (`/verifier/` plus the path under the verifier store, forward slashes, no host path; the rest is non-empty, has no empty segment and no trailing slash, is well-formed, and has no `\`, `%`, `//`, control character, or `.` or `..` segment; at most 400 characters), `vitest_version` (SemVer 2.0, including a prerelease), `vitest_integrity` (`sha512-`, 86 base64 characters, and `==`), and `lockfile_sha256` (64 lowercase hex, no `sha256:` prefix). The expected hash is `git show HEAD:package-lock.json` in the verifier checkout (an argv array, shell off), so a dirty working tree does not match. A read failure is a fixed code (`vitest_unreadable`, `lockfile_sha256_mismatch`, `vitest_integrity_missing`, and the others in `verifier-deps.ts`), never a filesystem message. `validateVerifierRuntime` copies the checks from `packages/capability/src/schema.ts` at `078f89d6254d1428e95c973bffacf7b474f47ac8` and does not import that package. The object has exactly those five keys.

## 2026-10-28 — The smallest fix for npm and Composer

`docs/design.md` (and #138's review) found that npm and Composer candidates ran `npm update` and `composer update --with-all-dependencies` with no package name: every dependency could move, which is the opposite of a minimal fix and an entry point for an unrelated new (possibly malicious) version.

- **Requirements keep the project's style.** A direct requirement is raised with the same operator: exact stays exact, `^` stays `^`, `~x.y.z` stays `~` (Composer's two-part `~1.2` would narrow, so it is not touched), with the fixed version as its floor. Any other style stops for review. Before, every requirement became `>=fixed <next-major`.
- **npm records exactly the fixed version.** npm always picks the newest version a range allows, so the candidate resolves twice, lockfile-only: first from a manifest that pins direct fixes exactly and transitive fixes as `overrides`, then from the final manifest, where npm keeps the recorded versions because they satisfy it. Then `npm ci` installs that lockfile. A project that already overrides a planned package stops for review. A transitive fix outside its parent's range is undone by the second step, and the candidate's advisory recheck then stops the update.
- **Composer updates only the named packages**: `composer update <name>:<fixed> --with-dependencies --minimal-changes`, scripts and plugins off.
- **The package manager may not rewrite the manifest.** The exported manifest must equal the one Ludion wrote.
- **Nothing installed may disappear unplanned (npm and Composer).** A transitive npm fix is pinned with an override scoped to the vulnerable version (`name@from`), so another installed version of the same name keeps its own resolution (#142 review: a global override moved semver 6.1.1 to 6.3.1); several vulnerable versions of one transitive name get one scoped override each. After resolution, every baseline version that no planned fix replaces must still be there, or the update stops for review. Added versions (a fix's new dependencies) are allowed and listed. Known cost: a fix that drops one of its own old dependencies (debug 2.2.0 → 2.6.9 drops ms 0.7.1) stops too. Stops for review: two vulnerable versions of a direct name, a vulnerable nested copy of a direct dependency, and any existing project override of the name at any depth. Maven is exempt from the removal check: nearest-wins mediation changes its transitive graph whenever a direct version moves, so the check would stop every Maven fix; its candidate inventory is still rechecked. Composer gets the package arguments after `--`.
- **Receipts list every changed package** (`changed_packages`: name, versions before, versions after), planned or not, for the judge's lockfile-diff checks.
- **Maven's online model keeps only the properties its dependency model uses** (#138 review, item 3). A used property named like a dependency-plugin parameter (`excludes`, `scope`, `mdep.*`, ...) stops for review, since Maven would read it as a plugin parameter and could hide part of the tree.

That is the intended fail-closed result; a later planner should read Packagist's advisories too.

## 2026-10-28 — The judge v0 (npm)

Design weeks 1–2, "判定役 v0". `ludion judge --before <dir> --after <dir>` judges an npm dependency update between two checkouts (an existing PR from Dependabot, Renovate or a person) and prints a comment; it changes nothing. The rules are one pure function (`packages/cli/src/security/judge.ts`) fed with facts (`npm-facts.ts`), so the live command and the backtest run the same code.

- **Every install path that changes is judged**, not only the target: each against what that path held before (else the highest version of the same name and major line), so a path that moves to a version already installed elsewhere, a downgrade say, is judged too. A path that now installs a different package (an alias) stops, and so does a dependency turned into a link to a local directory or a link that points elsewhere. Also, for every dependent (the root, a workspace, or an installed package), each package it declares is resolved before and after (Node's nearest node_modules): a copy at a path that held the same package (whatever its version) is compared with what that copy loaded; a copy at a new path is unchanged only if every earlier copy of that package loaded the same target, and otherwise is compared with each earlier target that differs (the same name as an earlier version, another name as a replacement). A package it did not load before is judged as a change from what it loaded, however the tree moved to get there (#143 rounds 4–8: removed copies, shadowing copies, moved and upgraded dependents, aliases). A requirement nothing satisfied before is not compared; a newly installed target is still judged by the lockfile diff, and the comment says so. A copy that only moved to a new path, with the version and hash of one already installed, is not a change to judge; gate 4 still checks it. Lockfile keys that are not plain install paths, or that differ only in case, are refused, and a changed bundled dependency stops (it has no registry tarball of its own).
- **package.json may change only dependency specs**, and only to registry ranges or npm: aliases (overrides likewise): any other field, such as scripts that run on install, or a git, URL or file: spec stops.
- **Gate 2 stops** on lost provenance, a different provenance repository or workflow, a new install script (preinstall/install/postinstall), an OSV MAL- record, deprecation, or a version the registry no longer lists. A new package (no earlier version) that runs install scripts also stops.
- **Gate 2 extends the wait** on a publisher change, new dependencies, or a package new to the project: the wait doubles, to at least 72h. The design says "extend" without a number; doubling keeps the urgency order and 72h is the normal wait.
- **Urgency** (from the production packages a fix applies to; a dev-only fix does not hurry other packages): exploited when a fixed advisory's CVE is in CISA KEV; high when it is CRITICAL or its EPSS is at least 0.1; normal otherwise; low when every changed version is dev-only. EPSS 0.1 is a starting threshold for the backtest to adjust.
- **The wait** counts from the newest publish among all changed versions. An exploited fix waits 12h only when provenance is comparable on both sides, else 24h. A stricter project wait wins.
- **Gate 1 in the judge**: a downgrade stops, and so does a version with known advisories that the replaced version did not have; advisories both share are shown.
- **Gate 4**: only package.json and package-lock.json may change (the caller passes the PR's changed files; without them the judgement is undecidable), and every lockfile entry that changed at its install path (every copy, including a re-pointed unchanged version) must resolve to the registry's own tarball URL for exactly that name and version, with the registry's own sha512 integrity (#143 review: a lockfile entry could otherwise name lodash but point at another package's tarball and hash).
- **Undecidable is never a pass**: a missing fact, a failed lookup, a missing publish time or unknown changed files gives "undecidable". A predecessor the registry no longer lists, or provenance that names no repository or workflow, is treated as not comparable.
- **v0 never says "apply"**: gate 3 is not run, so the best verdict is "ready except build". The comment lists what was not checked (gate 3, code inspection, OS/SAPI conditions, Sigstore verification of the provenance record, and the hijacked-publisher limit).
- Provenance is read from the registry's attestation record; its Sigstore bundle is not verified in v0.
- Exit codes: 0 ready except build, 3 wait, 1 stop or undecidable, 2 when the inputs cannot be read.

## 2026-10-28 — Moving dependencies are capped at the fix's publish time

The rerun did not meet the malicious gate (docs/bench/2026-10-28-backtest-rerun). The owner keeps the wait table and changes how the dependencies that move with a fix are chosen instead. Three rules, for npm first and then Composer and pnpm:

**Rule 1: nothing in the change may be newer than the fix.** T is the publish time of the fixed version A@x; when one change fixes several packages, the latest of their publish times. A change that fixes no advisory takes the project's changed direct dependencies as its targets. Every other version the change installs must either already be in the current lockfile (the same name and version anywhere in it) or have been published strictly before T. A version published at or after T stops the change. An unknown T, no target, or a version with no publish time makes it undecidable.

- npm, first as a check on the lockfile diff after the fact: in `ludion judge`, and on the candidate lockfile in `ludion patch`. Preferring the locked version when it satisfies the range is left to npm, whose lockfile-only install keeps such versions; the check enforces the cap. Publish times come from the registry.
- Composer: the candidate `composer.lock` against the baseline in `ludion patch`, with release times from Packagist's metadata (`https://repo.packagist.org/p2/<name>.json`). Limit: Packagist's `time` is the release's commit or tag date, which the author sets, not a registry publish time. A backdated release is not caught by this rule.
- pnpm: Ludion has no pnpm fix path. `ludion judge` reads a `pnpm-lock.yaml` change as the name@version set it adds and applies rules 1–3 and the registry checks. Gate 4 and the per-path resolution diff are not implemented for pnpm, so a pnpm judgement is at best undecidable, never ready.

**Rule 2: a young new dependency stops.** The dependencies are the names a changed version declares that the version it replaces did not, plus packages new to the lockfile. For each, its package's first publish is read: npm `time.created`, Composer the earliest release time. The change stops when that first publish is later than T minus the base wait of the change's urgency (the table's wait before any extension). An unknown first publish makes the change undecidable. Older new dependencies still extend the wait as before. `ludion patch` computes no urgency for Composer, so it uses the longest wait, 168h.

First publish is the earliest of `time.created` and every version's publish time. An unpublished and re-created package gets a new `created` while its old versions keep their times (found while writing backtest v3, before it ran).

**Rule 3: the judgement always shows the count.** The comment always shows T and the number of versions published at or after T, including when it is 0. The `ludion patch` receipt records the same.

## 2026-10-28 — Rule 1's same-release exception, and backtest v4's definitions

**When it was decided.** The owner set this exception after backtest v3's genuine-fix results and before looking at its malicious results (the owner's task, 2026-10-28 14:53 JST). In the genuine results, rule 1 stopped 29 of the 200 sampled fixes, 14 of them for no other reason. Nearly all were monorepo siblings published seconds after the fix in the same release: next, then `@next/env` 5 to 11 seconds later. Disclosure: v3's malicious run had already been committed (ac4e1bf, 14:50 JST) and summarised in PR #149's description when the task was written. This session read that description (7 of 1,148 versions selected, 1 missed, 156 unknown at 24h) before writing this entry. It has not read v3's per-version malicious results. The exception's terms are the owner's. The details marked "chosen here" were chosen from the rule's purpose, the code and the genuine results.

**The exception.** Rule 1 stops a version that is not in the lockfile and was published at or after T. Such a version is allowed when it belongs to the same release as a target A@x of the change:

- with provenance: A@x and the version both have build provenance, naming the same source repository and the same source commit;
- without provenance: neither has build provenance, and all three hold: the same publisher, the same version number as A@x, and published at most 15 minutes after T.

Chosen here:

- When only one of the two has provenance, or a provenance record names no repository or no commit, the exception does not apply and rule 1 stops the change. The release cannot be compared, and what cannot be judged stops.
- The publisher is the registry's `_npmUser` name. An unknown publisher on either side never matches. The version number is compared as a string. "At most 15 minutes after T" is 0 ≤ publish − T ≤ 15 min.
- The provenance branch has no time limit.
- The commit is the one the provenance statement records for the source: SLSA v1 `buildDefinition.resolvedDependencies[0].digest.gitCommit`, v0.2 `invocation.configSource.digest.sha1`.
- Where it applies: npm in `ludion judge` and `ludion patch`, and pnpm in `ludion judge` (the same registry facts). Not Composer: Packagist's metadata has neither a publisher nor provenance, so Composer keeps rule 1 without the exception.
- Rule 2 is unchanged: an allowed sibling that is a young new dependency still stops the change.
- The wait counts from the newest version in the change, siblings included. The judge already does this ("The wait counts from the newest publish among all changed versions").
- Rule 3: the judgement and the receipt list each allowed version and the branch that allowed it, next to the count of versions at or after T.

What the exception gives up: an attacker who holds the publisher's account and publishes a malicious sibling with the fix's version number within 15 minutes of the fix passes rule 1. The wait and the re-query still apply to it. A sibling built by the same workflow from the same commit is trusted as much as the fix itself.

**Backtest v4.** Backtest v3's definitions (the entry above) apply unchanged, except where noted below. The data is the same: the OSV export (sha256 `8b3170a6…`), with registry packuments, attestations and deps.dev read on the run date. v3's registry cache (read 2026-10-28) is reused, and anything it lacks is read on the run date. Also unchanged: the malicious denominator (the 1,148 versions), the fixes, the genuine sample (the first 200 by hash), scenarios (a) and (b), the gate 2 signals and their sources, the outcomes (missed, unknown, stopped) and the gates.

1. **Resolution** (v3 section 3). Each requirement resolves to the highest non-prerelease version satisfying its range, among the versions that rule 1 with the exception allows. Those are the versions published before T, and those published at or after T that the exception allows against A@x. If there are none, rule 1 stops the update. Chosen here: the backtest looks for allowed versions among those published before T + 24h. That bounds the search for same-commit siblings; the no-provenance branch has its own 15 minutes. Candidates above the highest version published before T are tried from the highest down. Publisher and provenance are read from the registry for both A@x and the candidate.
2. **Unreadable facts.** A candidate the registry no longer lists has no readable publisher or provenance. The exception could still allow it when its version and time meet the no-provenance conditions, or when A@x has provenance. In that case its check is unverified. If the candidate is a malicious V, that fix's selection of V is unknown. Otherwise the tree has an unknown branch, and resolution continues with the next allowed version. An unverified check is never counted as allowed or as stopped.
3. **Judgement time** (v3 section 4). The change is judged at its newest publish + w. The newest publish is the latest of T and the publish times of the allowed versions in A@x's tree. The genuine-fix delay (v3 section 6) uses the same newest publish: added delay = max(0, newest + w − advisory publish).
4. **Both ways in one run.** Every result is computed with the exception and without it (v3's rule, recomputed on the same data), so the exception's effect is shown on the same facts. The result with the exception is the primary one and is used for the gates.
5. **Outputs.** For each side:
   - the gates;
   - stops per signal, counted as the versions (malicious) or updates (genuine) where the signal fires, and those it stops alone;
   - how many the exception allowed something in;
   - how many of those would have been stopped without it.

   On the malicious side, listed one by one: every V the exception allowed, or whose selection it made possible through a tree it unblocked; every V selected by a fix published after V; and every V whose exception check was unverified.

**Amended before backtest v4 ran.** These come from the independent review of #151 (2026-10-28), and each makes the exception stricter:

- **The publisher must be an account.** npm trusted publishing records one shared user, "GitHub Actions" (`npm-oidc-no-reply@github.com`, with `trustedPublisher`), for every package published that way. Such a publisher counts as unknown and never matches. Gate 2's publisher comparison is unchanged.
- **With provenance, the workflow must match too**: the repository, the workflow and the commit. This is what "built by the same workflow from the same commit" above says. A different workflow in the same repository, a `pull_request_target` job say, could otherwise publish from the fix's commit.
- **Without provenance, the 15 minutes also count from the matched target's own publish.** With several targets, T is the latest one. A version published 5 minutes after T is no sibling of a target fixed a month earlier.
- **The provenance statement's subject must name the version and its tarball**: `pkg:npm/<name>@<version>` with the registry's sha512 integrity. Otherwise the lookup fails, which is undecidable. The Sigstore signature, and the repository and commit in its certificate, are still not verified. So the exception rests on the registry's checks at publish time, as gate 2's provenance comparison does.
- **A failed read keeps the receipt's count.** If `ludion patch` cannot read a publisher or provenance, the receipt keeps T and the count, and the cap is undecidable.

Round 2 of the review approved. Its non-blocking findings were handled before the run as follows:

- **More publishers count as no account.** Besides `trustedPublisher`, so does any `npm-oidc-no-reply@` email. So does any name that is not lowercase letters, digits, `.`, `_` and `-` beginning with a letter or digit: uppercase or spaces, for example. Another CI's shared user then fails closed. The few real accounts with other lowercase characters (a leading `_` or `-`, or `!~*'()`) lose the publisher branch too; that also fails closed.
- **`ludion patch`'s targets are the plan's own versions** (name and fixed version). Another added copy of a planned package can neither set T nor anchor a sibling.
- **A v0.2 source URI's ref starts at the first `@` after the host.** A tag such as `@scope/pkg@1.2.3` no longer leaves part of the ref in the repository.

Two limits are kept:

- **A statement that does not name its version makes the whole judgement undecidable**, because the subject check also covers gate 2's comparison of every changed version. That happens with a qualified purl, or a subject formatted another way. On the registry, `next@15.2.3`, `@next/env@15.2.3` and `get-jwks@11.0.2` pass the check.
- **The ref and the triggering event are not compared.** A `pull_request_target` or `workflow_run` run of the same workflow records the base commit while it builds other code. So does a statement whose claims are not bound to its certificate. Comparing `externalParameters.workflow.ref` and the event, or reading the repository and commit from the certificate's extensions, is later hardening.

Backtest v4 uses the exception as amended here.

## 2026-10-28 — Noise measurement: definitions fixed before running it

Design, "ロードマップと検証ゲート", gate 2 (ノイズ測定), and the weeks 1–2 gate "通知3分の1以下". These definitions are committed and pushed before the run, and are not changed after seeing results. A later change is a new entry with a new run. The saved search answers are committed and pushed before the measurement runs. The first execution started at the registered commit is the result. If it stops before finishing, it is reported with its reason and its log (`run.log`, which keeps every printed line), and the next execution is the result. Any other execution is reported beside the result, never instead of it. The wait table, the backtest gates and how unknowns are counted are not changed by this entry.

**What is measured.** The judge's gate 1 today is: the installed version is in an advisory's range, and the package is production rather than dev-only. Its OS, SAPI and configuration conditions are not built. The production/dev split is the lockfile's `dev` flag: a version counts as dev-only only when every installed copy of it is dev (judge.ts). That is the same signal `npm audit --omit=dev` reads, so that count is recorded next to it.

**1. Sample.**
- **The search.** 24 GitHub searches, one per UTC hour of 2026-10-27, each `is:pr is:public author:app/dependabot label:javascript created:<hour> sort:created-desc`. Each takes the first 100 results, with the query in `tools/backtest/src/noise.ts` (`SEARCH`), run with `gh api graphql`. The raw answers are saved and committed.
- **The order.** Rank 1 of every hour (00 to 23), then rank 2 of every hour, and so on. Only PRs by the `dependabot` app whose branch starts with `dependabot/npm_and_yarn/` count. Each repository comes once, at its first position.
- **Inclusion.** In that order, a repository is included when all of these hold:
  - no repository of the same owner is in the sample yet;
  - it is not a fork and not archived;
  - its default branch's head has `package.json` and `package-lock.json` at the root;
  - the lockfile is at most 50 MB and is lockfileVersion 2 or 3;
  - both counts below can be computed. Each repository gets three attempts, so network errors, HTTP 429/5xx and timeouts are retried before it is left out;
  - npm audit or OSV names at least one installed package, so every repository has something to check.

  The first 100 included repositories are the sample. Every repository considered, and why it was left out, is recorded by cause. The exclusions by cause are reported next to the gates, including the judge's own failures (its lockfile reader, its OSV lookup).
- **The snapshot.** The default branch head the search returned (its commit SHA is recorded), root `package.json` and `package-lock.json` only. Workspaces are measured through the root lockfile. A Dependabot PR in a subdirectory does not change what is measured.

**2. The two counts, per repository.** Both are computed in Docker: node:24-slim@sha256:55fb5f5a527ea2c5c4a95f963e48ef90aa38c7b346054fdc8ee9957a2b55d205, with a read-only root, a non-root user and no forwarded environment. The command is in the script's header. The script refuses to run with any npm other than 11.19.1. Neither count runs project code.
- **npm audit's count.** `npm audit --package-lock-only --json` (npm 11.19.1) runs in a directory that holds only the two files. It has its own npmrc: the public registry, scripts off. The count is `metadata.vulnerabilities.total`, the number npm prints. That includes packages counted only because they depend on a vulnerable one. Also recorded, but not used for the gate:
  - npm's directly vulnerable packages (an advisory in `via`);
  - the same count with `--omit=dev`.
- **The judge's count.** The installed packages come from `lockEntries`, the judge's own lockfile reader. Each distinct name@version is looked up with `osvIds`, the judge's own OSV query (names and versions only). The count is the number of distinct package names that have at least one production version named by at least one OSV record (a vulnerability or a MAL- record).

**3. The count gate.** Over the 100 repositories, the sum of the judge's counts is at most one third of the sum of npm audit's counts. Fewer than 100 included repositories fails the gate.

**4. The check for misses.**
- **What is checked.** For each repository: every package that npm audit lists as directly vulnerable, or that OSV names, and that the judge's count leaves out. These are the "left out" list in the output. It gives every reason that applies:
  - OSV's vulnerable copies are all dev;
  - OSV names no record for the installed versions;
  - npm audit lists it.

  It also lists every installed copy (path, version, dev flag), and npm's nodes and ranges.
- **Who checks.** Fresh-context reviewers (subagents that are not the worker), never the worker. Each reviewer gets the repository list and the output, and checks every left-out package against primary sources:
  - the advisory: the GHSA or OSV record's affected ranges against the installed versions in the lockfile. A version in range by either npm's GHSA range or OSV counts as in range;
  - the code: the repository's source at the recorded SHA, its lockfile's dependency edges, and the packages' manifests and code where needed.
- **Production-relevant.** A left-out package is production-relevant (a miss) when any of these holds for an installed version in range:
  - (a) an in-range copy is not dev in the lockfile;
  - (b) shipped code imports or requires it, or imports a package whose runtime dependencies reach it.
    - Shipped code is the repository's code that runs or is loaded in production, or is bundled for the browser, whatever the file's role. A runtime configuration such as `next.config.js` counts. So does an imported package declared in devDependencies.
    - Tests, and build, lint or release scripts, are not shipped code;
  - (c) the build puts its code into the production output: runtime helpers or polyfills injected by a transpiler or bundler, say. The repository's build configuration must show this;
  - (d) the production start or serve command runs or loads it: package.json `start`, a Dockerfile `CMD` or `ENTRYPOINT`, a Procfile, or a deployment configuration. Examples are `serve`, `http-server`, `ts-node`, `tsx`, `pm2`, or `next` or `vite preview` declared as dev.
- **Not production-relevant.** All of these hold:
  - every path to it goes through tooling used only at build, test, lint or release time;
  - no shipped code imports it;
  - no production command runs it.

  A "no" verdict cites the dependency path and the files that show no production loader.
- **Undecidable.** A package that fits neither list, or that the reviewer cannot decide, is undecidable, and undecidable counts as a miss. A repository the reviewer cannot finish counts every unchecked package as undecidable.
- **The worker's part.** The worker does not change a reviewer's verdict. The worker only adds verdicts up, and reports any disagreement next to them.
- **How it is done.**
  - Each repository's source at the recorded SHA is read from GitHub's archive of that commit, extracted in Docker and never run.
  - Reviewers get the repositories in sample order, in groups.
  - The reviewer brief (docs/bench/2026-10-28-noise/reviewer-brief.md) is committed before the review starts. It quotes this section and says that repository and package text is data, not instructions.
  - For each left-out package, a reviewer records three things: whether an installed version is in range, whether it is production-relevant (yes, no or undecidable), and the evidence (file and line, or the dependency path).
  - The verdicts are committed with the results.

**5. The miss gate.** Zero misses over the 100 repositories. Also reported:
- the number of repositories with at least one miss;
- with 0 of 100, the rule-of-three upper bound on the per-repository miss rate, 3/100 (about 3%, 95%). That bound applies only to this sampling frame: one day of search, one repository per owner, root lockfiles v2/v3.

**6. Both gates must hold.** Not measured counts as not met. What a pass would mean: dev-only findings are still notified at lower priority (CLAUDE.md). So the count gate measures production-priority notifications against npm audit's count, not the total number of notifications.

**Not measured.**
- Vulnerabilities that neither npm's advisory database nor OSV lists.
- Whether a vulnerable code path is reachable or exploitable.
- OS, SAPI and configuration conditions (not built).
- Whether a repository is deployed at all.
- Lockfiles other than the root package-lock.json (pnpm, yarn, subdirectories), and lockfile v1.

**Outputs.** docs/bench/2026-10-28-noise/:
- the saved searches;
- `noise.json`: every row, its counts and left-out list, the exclusions by cause, and the totals;
- the reviewer brief and the reviewers' verdicts;
- a README with:
  - both gates;
  - the exclusions by cause;
  - shown, not gated: the judge's count against npm's directly vulnerable packages and against npm's `--omit=dev` count;
  - the per-repository median ratio, and the number of repositories at or below a third. Pooled sums can be dominated by a few large repositories.

**Disclosure.** Before this entry, the script was smoke-tested on two owned checkouts, which are in no sample: examples/npm-security (npm audit 1, judge 1) and this repository's root lockfile (0 and 0). The search query's syntax was checked on 2026-10-20, a day outside the window. That check printed 3 PRs' times, authors and branch prefixes, and the day's total of 49,629.

Every other amendment is stricter or changes no gate. The amendments:
