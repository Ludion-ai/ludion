### 2026-10-13: Counting index requests (Analytics Engine)

- **Why.** Nothing says how many people use `ludion sync`. npm's download counts include CI and mirrors, and the CLI sends no identifier. The owner asked (2026-10-13) for the Worker to count distinct clients of `/index/*.json`. This is server-side counting of requests the CLI already makes; the CLI sends nothing new except the `User-Agent: ludion-ai/<version>` from 0.1.4, which names only its version. "No telemetry" in the README and on `/start` is about the CLI and stays true; both now also say what the server counts.
- **What.** For each successful `GET` of `/index/<name>.json`, one Analytics Engine data point (dataset `ludion_index_hits`, binding `INDEX_HITS`): `index1` = the key, `blob1` = UTC day, `blob2` = the path, `blob3` = `ludion-ai/<version>` or `other` (the CLI's own User-Agent is stored whole, which is only its name and version; any other User-Agent is stored as `other`); Analytics Engine adds an exact timestamp to each point. The key is the first 128 bits of HMAC-SHA-256, under the Worker secret `ANALYTICS_SALT`, of the day, the `CF-Connecting-IP` address and the User-Agent. The address, the secret and any User-Agent other than the CLI's are never written. Code: `apps/worker/src/index-counts.ts`, route in `apps/worker/src/app.ts`.
- **Why a keyed hash, and a secret.** The request was a daily-salted hash. A salt that is public (the date) leaves an IPv4 address recoverable by trying them all, so "no raw IP is stored" would be true in letter only. A secret key makes the hash unrecoverable **by anyone without it**, and the day inside the input makes it a different key every day. **Whoever holds the secret can compute any known address's key for any past day, and can recover IPv4 addresses for the CLI's User-Agent by trying them all**: the secret never changes, and Analytics Engine keeps the points for months. So the value is generated, set with `wrangler secret put`, and not kept anywhere. After that, only code deployed to the Worker, and whoever controls the deploy or the Cloudflare account, can read it. **`apps/worker/src` is not a protected path, so a pull request that reads the secret would auto-merge on green CI**; whether to protect that folder (a CLAUDE.md change) is the owner's call. A random key thrown away each day would need storage (another protected change); not done. **The path is not in the hash** (the request listed UA, path and address): with the path inside it, one client asking for `subjects.json` and `vitest.json` would count as two. The path is its own field.
- **Fails closed.** No secret, a secret shorter than 32 characters, no client address, no dataset binding, a non-`GET`, or a path that isn't a shard: nothing is written and the shard is served as before. The write happens in `waitUntil`, after the response is built, and a failure is caught: counting can't break `sync`. So after this merges nothing is counted until the owner sets the secret.
- **What the number means.** Per day, a client is an (address, User-Agent) pair: people behind one address count once, someone whose address changes counts more than once. Because the key rotates daily, **a week is client-days, not people**: the same machine on three days is three. A weekly distinct count needs a key that lasts a week, which is a stronger kind of tracking; not done, and the owner's call. The SQL and a script are in `docs/bench/2026-10-13-index-counts/`, with no results yet: there are no data points until the secret is set. Retention and sampling are Analytics Engine's, not ours.
- **Cost of the route.** `/index/*` is added to `run_worker_first` in `wrangler.jsonc` so the Worker sees the request; static assets alone don't run it. So every shard request is now a Worker invocation instead of a free asset request; how many that is hasn't been measured, and it counts against the plan's Worker request limits. Cloudflare's documentation says requests matching `run_worker_first` get a 429 once the plan's limits are exceeded, instead of falling back to the static file, and `sync` treats that as a failure (it keeps its old lessons file); which plan the account is on isn't known here. It also puts the Worker in the path of `sync`; the handler is a pass-through to `ASSETS` and the tests check that a missing secret, a failing dataset, and a 404 all leave the response alone.
- **Cloudflare's own logs.** `wrangler.jsonc` has `observability.enabled`, so every shard request, now a Worker invocation, can get a Workers Logs entry. Cloudflare's documentation says those hold the request, the response and related metadata for a few days, and doesn't say whether the address or the User-Agent is in them; not verified. `/start` says Cloudflare keeps its own request logs. Turning off invocation logs (`observability.logs.invocation_logs: false`) would also drop them for `/mcp` and `/@*`, which are the only diagnostics those routes have; left on, and the owner's call.
- **Not decided here, left to the owner:** whether to count weekly (above); whether to count `/index.json` (the whole index, which the CLI doesn't use) or the MCP route; any retention shorter than Analytics Engine's.
