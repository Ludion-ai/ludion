## 2026-10-27 — Security commands own their Docker boundary

The legacy lesson/capability code is being removed in stages: first give the security commands their own Docker access, then stop the legacy assistant-context delivery, then delete the legacy packages. This step moves only what the security commands use into `packages/cli/src/security/docker.ts`: image pull/build/inspect/rm, the hardened test `docker run` argv (unchanged flag for flag), and the timed container runner with name-only kill. `patch.ts` no longer imports `packages/capability` or `tools/verify`. The old copies stay until the legacy code is deleted, so lesson verification and in-flight security branches keep working.

The repository guard that confines `docker run` construction now names each allowed file and its one builder function (`tools/verify/src/docker.ts` `buildDockerRunArgs`, `packages/cli/src/security/docker.ts` `runArgs`). Before, any file named `docker.ts` was exempt and its offsets were checked against the wrong file.

The independent review found that the move took the sandbox flags out of the review gate: they used to live under the protected `tools/verify/`, and the new file was not protected. So `packages/cli/src/security/docker.ts` is now a protected path (workflow pattern, docs/protected-paths.md, CLAUDE.md). We protect that one file, not the whole `security/` directory: it is the only place allowed to start a container, and protecting the whole adapter would put every product change behind an owner merge. `runContainer` now takes a name, image ID and test argv and builds the argv itself with `runArgs`, so the module cannot start an unhardened container. The guard also flags, inside a builder file, any `exec` of `docker run` and any literal docker argv other than kill, pull or version, and it ends a builder function at its own closing brace. When `tools/verify` is deleted, the guard must move to a path that is still protected.
