## 2026-10-28 — The judge v0 (npm)

Design weeks 1–2, "判定役 v0". `ludion judge --before <dir> --after <dir>` judges an npm dependency update between two checkouts (an existing PR from Dependabot, Renovate or a person) and prints a comment; it changes nothing. The rules are one pure function (`packages/cli/src/security/judge.ts`) fed with facts (`npm-facts.ts`), so the live command and the backtest run the same code.

- **Every install path that changes is judged**, not only the target: each against what that path held before (else the highest version of the same name and major line), so a path that moves to a version already installed elsewhere, a downgrade say, is judged too. A path that now installs a different package (an alias) stops, and so does a dependency turned into a link to a local directory or a link that points elsewhere. Also, for every dependent (the root, a workspace, or an installed package), each package it declares is resolved before and after (Node's nearest node_modules): a copy at a path that held the same package (whatever its version) is compared with what that copy loaded; a copy at a new path is unchanged only if every earlier copy of that package loaded the same target, and otherwise is compared with each earlier target that differs (the same name as an earlier version, another name as a replacement). A package it did not load before is judged as a change from what it loaded, however the tree moved to get there (#143 rounds 4–8: removed copies, shadowing copies, moved and upgraded dependents, aliases). A requirement nothing satisfied before is not compared; a newly installed target is still judged by the lockfile diff, and the comment says so. A copy that only moved to a new path, with the version and hash of one already installed, is not a change to judge; gate 4 still checks it. Lockfile keys that are not plain install paths, or that differ only in case, are refused, and a changed bundled dependency stops (it has no registry tarball of its own).
- **package.json may change only dependency specs**, and only to registry ranges or npm: aliases (overrides likewise): any other field, such as scripts that run on install, or a git, URL or file: spec stops.
- **Gate 2 stops** on lost provenance, a different provenance repository or workflow, a new install script (preinstall/install/postinstall), an OSV MAL- record, deprecation, or a version the registry no longer lists. A new package (no earlier version) that runs install scripts also stops.
- **Gate 2 extends the wait** on a publisher change, new dependencies, or a package new to the project: the wait doubles, to at least 72h. The design says "extend" without a number; doubling keeps the urgency order and 72h is the normal wait.
- **Urgency** (from the production packages a fix applies to; a dev-only fix does not hurry other packages): exploited when a fixed advisory's CVE is in CISA KEV; high when it is CRITICAL or its EPSS is at least 0.1; normal otherwise; low when every changed version is dev-only. EPSS 0.1 is a starting threshold for the backtest to adjust.
- **The wait** counts from the newest publish among all changed versions. An exploited fix waits 12h only when provenance is comparable on both sides, else 24h. A stricter project wait wins.
- **Gate 1 in the judge**: a downgrade stops, and so does a version with known advisories that the replaced version did not have; advisories both share are shown.
- **Gate 4**: only package.json and package-lock.json may change (the caller passes the PR's changed files; without them the judgement is undecidable), and every lockfile entry that changed at its install path (every copy, including a re-pointed unchanged version) must resolve to the registry's own tarball URL for exactly that name and version, with the registry's own sha512 integrity (#143 review: a lockfile entry could otherwise name lodash but point at another package's tarball and hash).
- **Undecidable is never a pass**: a missing fact, a failed lookup, a missing publish time or unknown changed files gives "undecidable". A predecessor the registry no longer lists, or provenance that names no repository or workflow, is treated as not comparable.
- **v0 never says "apply"**: gate 3 is not run, so the best verdict is "ready except build". The comment lists what was not checked (gate 3, code inspection, OS/SAPI conditions, Sigstore verification of the provenance record, and the hijacked-publisher limit).
- Provenance is read from the registry's attestation record; its Sigstore bundle is not verified in v0.
- Exit codes: 0 ready except build, 3 wait, 1 stop or undecidable, 2 when the inputs cannot be read.
