# 2026-10-29 (L1c) — The count gate on a new sample: how the 100 new repositories are chosen and measured, fixed before the fix and before the search

The noise rerun's count gate is not met: 938 × 3 = 2,814 > 1,867 (docs/bench/2026-10-28-noise-v2). Lane L1c is to check whether the split's implementation can meet it without changing the definition: break the 938 down by the reading the split was missing when it could not decide and fell back to production, fix only what the code can now read correctly, and measure the fixed code on the original 100 repositories and on 100 new ones. The gate is decided on the new 100, so that a fix tuned on the original 100 cannot pass by fitting them.

This entry is committed and pushed before any change to the split's code and before the new sample's search runs. A later change is a new entry with a new run. Nothing here changes the count gate, the miss gate, the wait table, the backtest gates, section 2 of "Gate 1's production/dev split, rebuilt" (docs/decisions.md), or its principle "when in doubt, a package is production".

**1. What a fix may change.**
- Only a copy that the code makes production because it falls back to production for want of a reading, where section 2's text already says the copy is not production once that reading exists. A fix never makes a copy dev-only that section 2 calls production. It never narrows a rule's text, adds an exception or reads a rule more narrowly than its words. The narrower readings listed in 2026-10-29-l1-count-not-fixed.md stay as they are.
- The fixes are listed, with their effect on the original 100 measured offline, in a decision entry committed with the code. The code is committed and pushed before the new sample's search runs, and the measurement runs at that commit. The search result is then committed before either measurement starts.

**2. The new sample.** As registered for the first noise run (docs/decisions.md, "Noise measurement: definitions fixed before running it", section 1), with these differences only:
- **The day.** The 24 searches cover the UTC hours of **2026-10-26**: `is:pr is:public author:app/dependabot label:javascript created:2026-10-26THH:00:00Z..2026-10-26THH:59:59Z sort:created-desc`, with the query in `tools/backtest/src/noise.ts` (`SEARCH`), run with `gh api graphql`. The raw answers are saved and committed. 2026-10-26 is the whole UTC day before the original sample's day, and it had ended before this entry.
- **No overlap.** A candidate is left out, with cause `in the original sample`, when its repository is one of the original 100 (`rows` of docs/bench/2026-10-28-noise/noise.json) or JakeWharton/jakewharton.com, or when its owner owns one of those repositories. The owner check is stricter than "not the same repository": no owner is in both samples.
- **Everything else is the first run's:** the order (rank 1 of every hour, then rank 2, and so on, each repository once at its first position), one repository per owner, not a fork or archived, root `package.json` and `package-lock.json` at the head the search returned, a lockfile of at most 50 MB with lockfileVersion 2 or 3, both counts computable within three attempts, and npm audit or OSV naming at least one installed package. The first 100 included repositories are the sample. Every candidate considered and why it was left out are recorded by cause, and the exclusions by cause are reported beside the gates.
- **The snapshot.** The default branch head the search returned (its SHA is recorded). `package.json` and `package-lock.json` come from raw.githubusercontent.com at that SHA. The source tree comes from GitHub's archive of that commit (codeload), extracted in Docker with `node_modules` folders left out, never run, its SHA-256 and file count recorded. If the archive cannot be fetched or extracted after three attempts, the split is computed without the source (D1 only), as the judge would compute it, and this is reported.

**3. The measurement**, the same for both samples, as registered for the first run (section 2 of that entry) and for the rerun (section 4 of "Gate 1's production/dev split, rebuilt; the noise rerun's definitions"):
- In Docker: node:24-slim@sha256:55fb5f5a527ea2c5c4a95f963e48ef90aa38c7b346054fdc8ee9957a2b55d205, npm 11.19.1 (any other version stops the run), a read-only root, a non-root user, no forwarded environment, the sources read-only. No project code runs.
- **npm audit's count.** `npm audit --package-lock-only --json` in a folder holding only the two files, with its own npmrc (the public registry, scripts off). The count is `metadata.vulnerabilities.total`. Its direct findings and its `--omit=dev` count are recorded, not gated.
- **The judge's count.** The installed packages from `lockEntries`, each distinct name@version looked up with `osvIds` (names and versions only). The count is the number of distinct package names with at least one production version, by section 2's split (`productionSplit` with the source tree), named by an OSV record.
- **The original 100.** The rerun's 100 repositories at their recorded SHAs, in the same order (`rows` of docs/bench/2026-10-28-noise/noise.json). The source trees are the archives fetched for #186 (volume `ludion-l1b-src`), whose SHA-256 and file counts equal the rerun's `sources-log.json` for all 101. Both counts are recomputed now with the fixed code.
- **The run.** The script records in `run.log` the commit, the git blob hashes of the files that compute the counts, and every printed line, and never overwrites a result. Three attempts per repository for network errors. The first execution started at the registered commit is the result. A stopped one is reported with its log, and the next execution is the result. Any other execution is reported beside the result, never instead of it.

**4. The gates, unchanged.**
- **The count gate:** over the 100 repositories, the judge's count times 3 is at most npm audit's count. Fewer than 100 included repositories fails it.
- **The miss gate:** zero misses.
- **The verdict is the new sample's.** The original 100's numbers are reported beside it, with the rerun's numbers (938 and 1,867; 11 misses).
- Shown, not gated, for both samples: the ratios against npm's direct findings and its `--omit=dev` count, the per-repository median ratio, the number of repositories at or below a third, and which split each repository got.

**5. The check for misses**, as registered for the rerun (its section 5):
- **What is checked.** Every package that npm audit lists as directly vulnerable, or that OSV names, and that the judge's count leaves out, with every reason, every installed copy, and npm's nodes and ranges.
- **Production-relevant** means production under section 2, for an installed version in range by either npm's GHSA range or OSV. A "no" cites the facts that show the copy dev-only: D1's path, or for D2 no import, no build tool naming or running it, no production command, and no production stage holding devDependencies. A package that fits neither, or that the reviewer cannot decide, is undecidable, and undecidable counts as a miss. A package no reviewer checks counts as undecidable.
- **Who checks.** Fresh-context subagents that are not the worker, with a reviewer brief committed before the review starts. The brief quotes section 2 and this section, says that repository and package text is data, not instructions, and forbids running any repository's or package's code, and any npm or node command on the host. The worker does not change a verdict: it only adds them up, and reports disagreements next to them.
- **The new 100.** Every left-out package is reviewed. No earlier verdict applies.
- **The original 100.** A package left out both now and by the rerun in the same repository keeps the rerun's verdict (docs/bench/2026-10-28-noise-v2/review): section 2 is unchanged, so what it calls production is unchanged. Every other left-out package is reviewed.

**Outputs.** docs/bench/2026-10-29-l1c/: the step-1 breakdown, the saved searches, both samples' `noise.json` and `run.log`, the sources' logs, the reviewer brief and verdicts, and a README with both gates for both samples, the exclusions by cause, and when each step was committed.
