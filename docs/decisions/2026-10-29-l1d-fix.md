**The fixes** (packages/cli/src/security/production.ts; they apply in `ludion judge --source` as in the measurement):
- **A. A tree without a project folder's package.json is incomplete.** Section 2 allows D2 only when "the source tree was read". A tree that lacks the package.json of the root or of a workspace folder in the lockfile is not the project's tree, so only D1 applies, as for a tree that could not be read whole. A folder outside the tree (`../lib`) was never in it and is not checked. The measurement also marks an archive incomplete when it sees `export-ignore` (docs/decisions/2026-10-29-l1d-third-sample.md).
- **B1/B2. A package that a command runs also runs what it hands off to.** P5 and P6 count "what these commands run". webpack's bin runs webpack-cli, and `webpack serve` runs webpack-dev-server. Neither is a declared dependency: webpack names webpack-cli only in `peerDependenciesMeta`, and webpack-cli 4 and 6 and @webpack-cli/serve name webpack-dev-server only there. The lockfile records `peerDependenciesMeta`. So when a production command (P5) or a build command (P6) runs a package, the copies that package resolves for the names in its `peerDependenciesMeta` run too, and the same holds again from them. Following then applies from each of these copies as from any production copy. P6 still does not make a test runner, linter or formatter production, and nothing is handed off from one. A package that is production only by P3 (webpack as a bundler helper) is not run, so nothing is handed off from it. Each copy is handed off from once per kind of command, so the cost stays linear.
- **B3. A TypeScript build configuration is read through a register hook.** webpack-cli (and gulp) load `webpack.config.ts` through `interpret` and `rechoir`. These require whichever installed hook interpret lists for `.ts`, `.cts` or `.mts`: ts-node, sucrase, @babel/register, esbuild-register or @swc/register. None of them is declared by the tool. So when `interpret` or `rechoir` is installed, a P2 configuration file ending in `.ts`, `.cts` or `.mts` makes production the copy of each installed hook that is resolved from that file's folder (else every copy of it).
- **C1/C2. An argument that is not a literal.** Section 2 counts `require()`, `import()` and `require.resolve()` as imports. When the argument is not one literal, the split now reads it, up to its closing parenthesis and at most 400 characters:
  - every literal in it is a specifier: `require(process.env.SHARP_PATH || 'sharp')` names sharp, and a ternary names both;
  - when the argument is one identifier, the literals that a `const`, `let` or `var` of that name is given anywhere in the same file are specifiers: `const UPSTREAM = 'shadcn/tailwind.css'` with `require.resolve(UPSTREAM)` names shadcn. Each identifier's literals are added once per file, so the cost stays linear.

  Not changed, and stated: an identifier given its value in another file, or computed (`require(somewhere)`), names nothing, and neither does a template with a substitution.
- **C3. A node_modules path built from literal segments.** Section 2 counts "a `node_modules/<package>` path in a source file". Literal segments after a literal `node_modules`, separated by commas (`join('node_modules', '@vscode', 'vsce', 'vsce')`, up to 8 segments), are joined with `/` and read as such a path, wherever node_modules paths are read: source, a build tool's configuration and package.json scripts.
- **D. Umi's configuration is a build tool's configuration.** Umi's `umi build` and `max build` read `.umirc.*` or `config/config.*` (with `config/config.<env>.*`). They name plugins as quoted strings, which section 2's (c) counts ("what a build tool's configuration names ... is production"), but P2's list of files did not include them. The reviewer called mockjs undecidable, and an undecidable copy is production. So these files are read as P2 files: every quoted string naming an installed package is production.

**After #196's fresh-context review** (`reviewed-sha: 63d7d2c`, APPROVE, seven findings, none blocking):
- **Fixed (finding 1).** A file with hundreds of thousands of specifiers made `productionSplit` throw `RangeError`, because the list was spread into `push()`. Main had the same crash through `codeSpecifiers`. Both sites now push one at a time. The judge used to stop with no result, and the measurement used to drop the repository as `judge split`. This changes no copy's verdict. It came after the measurements started, so its effect is checked beside the result.
- **Stated, not changed:**
  - Finding 2: an argument is read for up to 400 characters at each call position. That stays linear, but a crafted file of nested `import(` costs about 0.3 s per MB.
  - Finding 3: the argument scan does not skip quoted text, so `require(c ? ")" : "x")` names nothing.
  - Finding 4: an identifier's literal is the one its declaration is initialised with (`const a = "x"`). A later assignment, a second declarator (`const a = 1, b = "x"`) or a ternary initialiser names nothing.
  - Finding 5: a joined path starts only at the literal `"node_modules"`. `"../node_modules"`, `"./node_modules"` and `"node_modules/@scope"` followed by more segments name nothing.

  These remain gaps in the safe direction relative to main: they count nothing less than main does.
- **Finding 6, the measurement's source check.**
  - codeload archives also leave out the contents of git submodules, and `sources.ts` does not check `.gitmodules`.
  - export-ignore of `/src` or `/Dockerfile` alone, with package.json kept, is caught only by the `.gitattributes` check, not by the split's own package.json check.
  - The third sample's registration is not changed after its search. Instead, the README reports how many measured repositories have a `.gitmodules`, and the miss review reads those trees knowing that.
- **Finding 7.** The measurements ran from 63d7d2c, which adds only the saved search to the registered commit 2692611. Every file that computes the counts has the same blob at both commits, and `run.log` records those blobs.
