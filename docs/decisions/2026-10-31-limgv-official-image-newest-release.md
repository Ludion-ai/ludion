# 2026-10-31 — An official PHP or Node.js image moves to its line's newest release (LIMGV)

**Lane LIMGV.** Decided by the coordinator's brain in ludion-ops#1, comment 6540818608, item 1 (option (a) of the audit in comment 6540622832, item 1). It replaces item 1 of docs/decisions/2026-10-31-lphpv-php-security-release.md and item 5 of docs/decisions/2026-10-31-lnode-node-image.md. Those two took the newest *security* release of the line. Written and committed before the code, as the lane rules require.

## Why

- **Only the newest tag of a line is rebuilt.** docker-library's FAQ (github.com/docker-library/faq, README.md, read by the audit in a container): "once 2.5.7 is released, 2.5.6 is no longer considered supported, but the Docker Hub tag is typically left available for pulling -- it will simply never get rebuilt after that point given that it is unsupported". An official image carries fixes in two places: the runtime, and the OS packages. OS-package fixes reach only the tags that are still rebuilt, and a line has one such tag: its newest release.
- **How often the old rule landed on a tag that is no longer rebuilt.** The audit counted, for each day from 2025-10-31 to 2026-10-31, whether the line's newest release published by that day was a security release. It was not on 216 of 366 days for PHP 8.4 (59%) and on 297 of 366 for Node.js 24 (81%). On those days, the newest security release that LPHPV and LNODE took was already a tag that Docker no longer rebuilds. These are the audit's numbers; this lane did not recount them. Example from nodejs.org's index on 2026-10-31: 24.22.1 (2026-10-20) is marked security and 24.22.2 (2026-10-27) is not, so the old rule moved a project to `node:24.22.1-<variant>`, a tag that has had no rebuild since 24.22.2 came out.
- **How the Goal's "smallest fixed version" reads for an official image.** The fix is in the runtime and in the OS packages, and the OS fixes arrive only in the line's newest tag. So the smallest image that holds every fix is the line's newest release. Taking the oldest version that holds every fix is right for a package, whose contents never change after it is published. It does not hold for an image, whose tag gets new OS packages until a later release replaces it. The sentence for CLAUDE.md ("For an official image, the smallest fixed version is its line's newest release, because only that tag gets OS-package rebuilds.") goes in LC0a, a protected PR that the owner merges. It is not part of this lane.
- **What LPHPV and LNODE missed.** PHP's choice before LPHPV (the newest release of the branch) was right for this reason, but no record said why. LPHPV and LNODE's item 5 applied the package reading to images (docs/mistakes/2026-10-31-image-took-a-tag-no-longer-rebuilt.md).
- **The cost.** More PRs. Over the past 365 days, by the audit's count: PHP 8.4 6 → 13 and Node.js 24 5 → 17. Decision 3 (docs/decisions/2026-10-31-gate-3-official-image-same-series.md, proposed and not yet in effect) would make gate 3 lighter for patches within the same line. Until then gate 3 stays as CLAUDE.md has it, the project's test included.

## Decided

1. **The version taken.** The newest release of the Dockerfile's line in the official list (PHP: the same `X.Y` in php.net's JSON; Node.js: the same major `X` in nodejs.org's index), whether or not it is marked security, whenever it is newer than the Dockerfile's version. This is the image move in both of the brain's cases:
   1. A newer security release is published. The line's newest release is then that release or a later one.
   2. The Dockerfile's tag is no longer the line's newest release, because a later release of any kind is out and the official image has stopped rebuilding that tag.

   Examples from the official lists on 2026-10-31: `node:24.20.0-alpine` moves to 24.22.2, where it moved to 24.22.1. `node:24.22.1-alpine` moves to 24.22.2, where it did not move. `php:8.4.25-cli` moves to 8.4.27, as before, because 8.4.27 is both the newest release and a security release.
2. **No move.** When the Dockerfile's version is the line's newest release, there is no candidate. The status `no_newer_security_release` keeps its name and now also says that the tag is the line's newest release.
3. **A missing list stops.** When the Dockerfile's version is newer than every release of its line in the official list, the list lacks at least the release the project uses. Ludion then cannot tell whether the tag is still the newest, so the lookup fails and no update decision is made, as for incomplete metadata. Before, this case gave `no_newer_security_release`, which looks like "no update". The other stops are unchanged: no release of the line, an incomplete entry of the line, and, for Node.js, a version listed twice. A Dockerfile version below the newest release that is missing from the list is not a stop, because the newest release is known to be newer. php.net's lists skip versions: its 8.4 list on 2026-10-31 has no 8.4.0 and no 8.4.9.
4. **The security mark.** Unchanged in meaning. `security_releases` is still every release of the line newer than the Dockerfile's version that is marked security (PHP: `tags` includes `"security"`; php.net also writes `[]` and `[""]`; Node.js: `security: true`), newest first. `fix_published_at` is still the day of the first of them.
5. **A move with no newer security release (case 1.2 only).** `security_releases` is empty. `fix_published_at` is null, with the existing reason ("php.net lists no security release newer than the Dockerfile's version", and nodejs.org's equivalent), because no official day is known for the OS fixes that the rebuilds carry. The commit's second paragraph, in place of the list of security releases, is: `No official <PHP|Node.js> security release is newer than <old>; <new> is the newest release of its line, the only tag of the line Docker's official image still rebuilds.` The PR job (`ludion deliver open`) accepts such a receipt for an image, rebuilds that message from the checked fields, and writes in the PR body that the tag is no longer the line's newest release instead of "found a published security fix". It never names the move a security release.
6. **`ludion scan`** reports the update and exits as it does for any update it finds.
7. **Unchanged.** The sources and their limits (php.net's `?json&version=<X.Y>&max=100`, 1 MiB, 15 s; nodejs.org's `dist/index.json`, 4 MiB, 30 s), what is sent (the same requests, and nothing about the project), the line, the flavor or variant kept, the tag and digest pinning, the version check, the branch name (`ludion/php/<version>`, `ludion/node/<version>`), the receipt's schema, the PR job's other checks, the gates and their number, the wait table and the scope.

## Not covered

- A rebuild of the same tag in place (LDG, which is fixed after this record is merged).
- Whether OS fixes were actually published while a tag was not rebuilt (not counted, 不明).
- docker-library's lag. A newest release that Docker Hub does not publish yet makes `docker pull` fail, and that fix fails. It is not replaced by an older tag, and the next run tries again. In that window, which the audit puts at one to two days (its guess), a project that needs a security fix gets a failed fix instead of the security release.
- LR3 and decision 4's definition of "protected" (a separate lane), and the CLAUDE.md sentence (LC0a).
- The rest of the earlier records' "Not covered": gate 1's matching, gate 2's checks and the waits, end-of-life lines, and minor or major upgrades.
