# 2026-10-31 — The official Node.js image, same release line: definitions (LNODE)

**Lane LNODE**, asked by the coordinator's brief (ludion-ops#1, comment 6529705640, item 5): Node.js's official image, updated to a security release of the same line, in the same form as the PHP image. docs/status.md, "Missing before complete", item 4. Written and committed before the code, as the lane rules require.

## Why

PHP in Docker is the only runtime Ludion updates (docs/status.md, item 4). A Node.js security release is announced on nodejs.org and marked in its release index, and a project pinned to an older official `node` image keeps the hole until someone moves the tag. The PHP path already finds the release, pins the official image by digest, builds and tests old and new offline, and commits the one FROM change on its own branch; the scheduled workflow's PR job checks the Dockerfile and Docker Hub's digest again. Node.js gets the same path.

## Decided

Nothing here changes a gate's numbers, a row of the wait table or another ecosystem's behaviour. The Node.js image goes through what the PHP image goes through today, no more: gate 3 (the project's own test, old and new, built and run offline in Docker) and gate 4 (one fix, one commit, its own branch, the image pinned by digest). Like the PHP image, it does not go through the judge: no provenance, publisher, install-script, deprecation or withdrawal check, and no wait.

1. **The policy.** `ludion.security.json` with `"ecosystem": "node"` and the PHP policy's other keys (`schema`, `dockerfile`, `test`, `timeout_seconds`). Without `ecosystem`, or with `"php"`, a Dockerfile policy stays PHP's, as today. `ludion init` offers `node` when the project's `Dockerfile` has a `FROM` line naming the `node` image (`FROM node:`, `FROM library/node:` or `FROM docker.io/library/node:`); its default test is `node tests/smoke.js` (PHP's is `php tests/smoke.php`). `ludion scan` checks the image when the policy is `node`, when `--ecosystem node` is given, or, with no ecosystem chosen, when the Dockerfile has such a `FROM` line.
2. **The image Ludion reads.** Exactly PHP's limits on the Dockerfile (one `FROM`, no `ARG` in it, no parser directive or line continuation, no `ADD`, `COPY --from` or `RUN --network/--mount`), and the one `FROM` names the official image `node:X.Y.Z` or `node:X.Y.Z-<variant>`, optionally as `library/node` or `docker.io/library/node`, optionally pinned `@sha256:<64 hex>`. `X.Y.Z` is an exact release (three numbers). The variant is the rest of the tag after a hyphen (`alpine`, `alpine3.22`, `slim`, `bookworm`, `bookworm-slim`, `trixie-slim` and so on): a lower-case letter, then lower-case letters, digits, dots and hyphens, at most 64 characters. A floating tag (`node:22`, `node:lts`, `node:22-alpine`), another repository, or anything else is refused with that reason; it is not guessed.
3. **The same line.** The release line is the major version, `X`: Node.js publishes each line's releases as `vX.*`. Only releases of the Dockerfile's line count. Ludion never moves to another major, whether or not the line has reached its end of life (end of life is not checked or certified).
4. **The source and the security mark.** `https://nodejs.org/dist/index.json`, the release index nodejs.org publishes, read whole (it lists every line; nothing about the project is sent). The request follows no redirect, times out after 30 seconds, and stops at 4 MiB (it was 336,201 bytes on 2026-10-31). It must be a JSON list. Entries whose `version` is not exactly `vX.Y.Z` (prereleases such as `v27.0.0-alpha.0.0.0`) are left out. For every entry of the line: `date` must be a real day `YYYY-MM-DD` and `security` must be `true` or `false`; any entry of the line that is not, a version listed twice, or no release of the line at all, makes the lookup fail, and no update decision is made (as PHP's incomplete metadata does). A release is a security release when its `security` is `true`. A fix is needed when a security release of the line is newer than the Dockerfile's version.
5. **The version taken: the smallest that holds every published fix.** The newest security release of the line, among those newer than the Dockerfile's version. A line's releases are cumulative, so that is the smallest version that holds every security fix the line has published; later releases not marked `security` are not taken. (PHP takes the newest release of its branch; that is not changed here.) Example from the 2026-10-31 index: a project on `node:24.20.0-alpine` moves to `24.22.1` (security, 2026-10-20), not `24.22.2` (2026-10-27, not marked).
6. **The tag and the digest.** The candidate keeps the variant: `node:<version><variant>`. A variant the new release does not publish makes `docker pull` fail, and that fix fails; nothing else is tried. As for PHP, each image is pulled by its tag, and the digest pinned is the `node@sha256:` entry Docker records for it (`RepoDigests`, the manifest list's digest). The baseline is built from the Dockerfile's own image, pinned the same way. The new `FROM` is `node:<version><variant>@sha256:<digest>`.
7. **The version check.** As PHP's `php -r` check, the built image (not only its base) must run `node -e` and report exactly `v<version>` (`process.version`), for the baseline and for the candidate, offline in the sandbox; otherwise that run fails.
8. **The branch and the commit.** `ludion/node/<version>` (with the project folder's prefix, as for PHP), subject `ludion: Node.js <old> -> <new> in <dockerfile>`, and the body names the line's security releases newer than the old version. The receipt is PHP's (schema 1, scope `dockerfile_only_not_deployed`), and its `scan` carries `"runtime": "node"`; a PHP receipt carries no `runtime`, as before.
9. **The exposure-time start.** `fix_published_at` is the `date` of the first (smallest) security release of the line newer than the Dockerfile's version, recorded as 00:00 UTC that day, since the index gives a day only; null, with the reason, when it cannot be read.
10. **The PR job (`ludion deliver open`).** The policy at the base commit says `node`, and the receipt's `scan.runtime` must say `node` too (and a PHP policy's receipt must have none). The checks are PHP's, for `node`: the branch name, the commit message rebuilt from checked fields, the Dockerfile changing only its `FROM` to the official `node:<version><variant>` of a newer release of the same line pinned by digest, and that digest equal to the one Docker Hub gives for the tag now (an anonymous pull token from auth.docker.io for `repository:library/node:pull`, then the `docker-content-digest` of `registry-1.docker.io/v2/library/node/manifests/<tag>`). A lookup that fails, or a tag rebuilt in between, fails the fix; nothing is pushed.
11. **What it sends.** A GET of nodejs.org's index (no project data), and the official image pulls and Docker Hub lookups PHP makes, for `library/node`.

## Not covered

Gate 1's matching to the project's OS, configuration or use of the fixed component (a security release is taken whether or not its fixes reach the project); gate 2's checks and the waits (as for PHP); a rebuild of the same tag (OS packages in the image); end-of-life lines; images that are not `node` (another base image, a multi-stage build, a Node.js installed by the Dockerfile itself); the `engines` field or `.nvmrc`; and Windows images.

## Addendum, 2026-10-31 07:3x JST (LNODE3, after R231c's review, PR #231 comment 6534443349)

Item 1's detection is widened, and nothing else changes. `init` and an unconfigured `scan` now take any `FROM` line that names a `node` image (after any `--flag` arguments, with any registry or namespace prefix, by tag, by digest or with neither; `node` must be followed by `:`, `@`, a space or the end of the line), still only on a `FROM` line, so `COPY --chown=node:node` and `USER node` do not count. What item 2 reads is unchanged: only the official image at an exact version, so each newly detected form (`--platform`, `docker.io/node`, `index.docker.io/library/node`, `ghcr.io/…/node`, `node@sha256:…`, `node`) is reported as a check that could not be made (exit 2), where before it was left out and `scan` could exit 0 beside an npm lockfile. No form is accepted that was refused before.

## Addendum, 2026-10-31 09:0x JST (LNODE4, after R231d's review, PR #231 comment 6535222762)

A Dockerfile is read as Docker (BuildKit) reads it: one UTF-8 byte-order mark (U+FEFF) at the start of the file is removed first, for detection (init and scan) and for reading (item 2, PHP's image included). An update leaves the mark in the file and changes only the `FROM` image. Before, a Dockerfile that starts with the mark was read but not detected, so an unconfigured `scan` could leave the node image out and exit 0. Nothing that was refused is accepted.
