## 原則

**偽れない証拠だけが、待ちを縮めてよい。偽れる証拠は、待ちを延ばして知らせるだけ。止めるのは事実だけ。Ludion は中央に権限を持たない。**

| 証拠 | 偽れるか | 使い道 |
| --- | --- | --- |
| 前の版と同じリポジトリ・workflow からの provenance | 盗んだ npm トークンでは作れない | 縮めてよい（リリースの後に作る） |
| 公開の時刻に、リポジトリにタグや commit がある | トークンだけでは作れない | 同上 |
| tarball の中身が、そのリポジトリの commit と一致する | 同上 | 同上 |
| 差分の信号（publisher の変化、新しい依存） | 攻撃者が隠せる | 延ばして知らせる（CLAUDE.md の延長：待ちの 2 倍か 72h の長い方） |
| NN・LLM の点数 | 攻撃者が合わせ込める | v1 では使わない。使う時も延ばすだけ |

- **止めるのは事実だけ：** MAL-、取り下げ、廃止、provenance の後退、install script の追加。止めた版は二度と自動では当てず、次の修正へ移る。
- **止めるにも代償がある（露出が続く）。** 全体を無期限に止めてよいのは、Ludion のリポジトリの停止ファイルだけ。
- **中央に権限を持たない。** Ludion は利用者のリポジトリへの書き込みも、Actions の操作も、中央からは持たない。全部、利用者のリポジトリの中の workflow がやる。
- 理由：Ludion は公開されるので、攻撃者は手元で通るまで調整できる。修正の木に入った攻撃は歴史全体で 3 つで、学ぶ教材が無い。受け取りには「なぜ」が要る。LLM は読ませた文に操られる。

## 範囲：npm だけ

**最初のリリースで対応と書くのは npm だけ。** lockfile は 1 日の測定で一番多いものに決める（今読めるのは package-lock.json だけ）。PHP・Node.js の公式イメージと Composer は、コードと試験を残し、リリースの後に 1 つずつ同じ線で足す。出す Action では npm 以外を既定で動かさず、動いたら落ちる試験を足す。

## 待ちの規則（1 本）

**守りの主役は構造。V 以外の版は「範囲を満たす最古」を選ぶので、出たばかりの悪性の版は定義上選ばれない。** 過去に修正の木へ入った悪性 7 版は、全部 V 以外の版だった。

> Ludion が出す diff に入る全部の版は、T（勧告を最初に見た時刻）で解決され、push の時点で待ち以上の年齢を持ち、待ちの終わりの再照会で MAL-・廃止・取り下げが無い。V は最小の修正版。V 以外で動かざるをえない版は、範囲を満たす最古で、勧告・廃止・取り下げの無いもの。既存の lockfile の版は、範囲を満たす限り動かさない。

| 緊急度 | 待ち（CLAUDE.md のまま） |
| --- | --- |
| exploited（KEV） | 12h（比べられる provenance が無ければ 24h） |
| high | 24h |
| normal | 72h |

- 年齢は版ごとに「公開時刻＋待ち ≤ push」で判定する。diff の中で一番若い版が線を決める。
- 試験で assert：解決の時刻 ≤ push − 待ち。diff の各版の年齢。廃止で飛ばした先が待ちより若ければ待つ。
- **作れるかを最初の 2 日で試作する。** npm には「最古を選ぶ」仕組みが無い（推測）。無理なら「T の時点で解決し、V 以外に年齢 72h の下限」で代える。
- backtest では、勧告が出た時点ですでに待ちが終わっている修正が 200 件中 73 件（36%）。残りは、待ちの終わりにもう一度起こす（C9）。

| 危険 | 対処 |
| --- | --- |
| 最古の版に未知の不具合。重複や peer の不整合 | 関門 3 で落ちる。件数を出す |
| 最古が既知の脆弱 | 勧告を見て、次に古いものへ |
| V 自身の新しい範囲が、公開されたばかりの版を強制する | その版の年齢が待ちを決める。頻度を測る（推測：1% 未満） |
| 攻撃者が古い版を全部廃止して、自分の版へ誘導する | 着地先の年齢が待ちより若ければ待つ。provenance の継続も通す |

### C5 壊れたら戻す・C13 自動マージ — 止める

- **壊れた：** 本番のデプロイが置き換わった後に、古い版で動いていたものが動かないこと。ビルドの失敗は、前のデプロイが生きているので数えない（Vercel・Netlify。推測 90%）。
- **マージ：** 確かめた SHA を指定する。直前に再照会し、停止ファイルを読む。プレビューのデプロイが成功してから。適用の設定は auto と pr で、既定は auto。利用者のブランチ保護で通らなければ、PR のまま知らせる。
- **本番を見る：** デプロイの状態に書かれた environment\_url を、マージの前と後に関門 3 と同じ型（GET だけ）でクロールして比べる。
- **戻す：** デプロイの状態、main の check、本番のクロールのどれかが失敗なら、1 回だけ再実行する。また失敗なら、その 1 commit を戻す PR を自動でマージする（lockfile は元とバイト単位で同じ）。修正は人への PR に回し、そのリポジトリの自動マージは人が再開するまで止める。
- **利用者の CI：** 利用者が設定で名指しした workflow だけを、マージの後に main で workflow\_dispatch する（GITHUB\_TOKEN でも run が作られる）。既定は起こさない。
- **全体の止め：** Ludion のリポジトリの停止ファイル 1 つ。止める条件は「戻せなかった 1 件」。書くのはオーナーと、証拠（戻せなかった PR の URL）つきの自動。各 Ludion はマージの前に読むだけで、何も送らない。
- **試験：** 試験用リポジトリで、CI が落ちる、デプロイが失敗する、本番のページが壊れる、戻せない（続けて push）を作り、全部の振る舞いを確かめる。

| 危険 | 対処 |
| --- | --- |
| 戻すと脆弱な版に戻る | 赤で知らせ、修正は人への PR |
| 戻す PR が衝突する | 赤で知らせ、自動マージを止める |
| 本番のクロールが、ログインの後ろのページを見られない | 見えたページの割合を受け取りに書く |
| 停止ファイルを使いすぎる | 書く時に証拠の URL を添える。無期限の停止はこのファイルだけ |
| プレビューで、候補が秘密のある所で走る | push は待ちの後だけ |

### C9 勝手に動く — 止める

**時計を作らない。中央に権限を持たない。** 起こすのは全部、利用者のリポジトリの中の workflow と、GitHub 自身の仕組み。

- **層 1：予定。** 公開リポジトリは毎時、非公開は 4 時間ごと（Actions の分を月 200 分以内に）。毎時 0 分を避ける。
- **層 2：Dependabot の合図。** Dependabot security updates の PR で起きる、予定を持たない workflow が、checkout せず、actions: write だけを上げ（GitHub の文書にある）、dispatch だけの discovery を起こす。予定ではないので、60 日の規則に掛からない。Dependabot の PR はその場で draft にして「Ludion が保留中」と書き、Ludion の PR が出たら理由を書いて閉じる。止まった予定を自動で戻すのは、GitHub Support の文書での確認まで出さない。
- **層 3：50 日目の issue。** 公開リポジトリで 50 日活動が無ければ、issue で知らせる。Ludion は push しない。
- **入口：** filename と value を埋めた新規ファイルの URL（workflow を 1 クリックで置く）と、Dependabot security updates を on にする手順。
- **試験（60 日は待たない）：** 予定を手で止めても層 2 が動くこと。試験用リポジトリで Dependabot に PR を開かせる。
- **限界：** 静かな公開リポジトリで、Dependabot を使わず、50 日目の知らせにも応えなければ、GitHub が予定を止める。待ちの途中で予定が止まっていると、待ちの終わりは次の活動まで拾われない。

| 危険 | 対処 |
| --- | --- |
| GitHub の起こし遅れ（q≈0.18） | 待ちの終わりの遅れは平均 5 時間ほど（推測、公開リポジトリの毎時）。C8 に入れる |
| Dependabot の PR と Ludion の PR が二重になる | draft にして保留を書き、Ludion の PR が出たら閉じる |

### C16 公開するもの — 止める

- **Action：** SHA で固定し、CLI を同梱。npm のパッケージは出さない。

- **Renovate・Dependabot との差を 1 段落、数つきで：** テストの無いリポジトリで古い版を仕様にして確かめる、本番を見て戻す、マージの瞬間に再照会する、中央に権限を持たない。数は backtest（Renovate の 3 日の年齢だけで通る悪性の数と、Ludion がそこから止める数）。

## 製品の天井

バイブコーディングのアプリが破られる原因は、依存の CVE より自分のコード（RLS の穴、鍵の露出、認証）の方が多い（推測、数は無い）。React2Shell は例外的な大波だった。だから v1 の価値には上限があり、関門を厚くするより、早く出して波を 1 つ捕まえる方が大きい。これが「薄く、速く、ただし安全の線は譲らない」の根拠。
