# 2026-10-30 — The PR job's checks read a commit and a lockfile differently from Git and from the receipt

- **What happened.** #210 (LB, the scheduled workflow) was merged with checks in `ludion deliver open` that a forged artifact could pass (cloud review 6516135819, N1 to N9):
  - It counted a commit's parents from the raw text, where Git counts only the `parent` lines right after `tree`. A commit with `parent <base>` after `author` was accepted as a fix on the base; Git reads it as a root commit, and `git fsck` reports it. The design said fsck was not needed because "every object the PR job acts on is read back and checked", and every PR body said "its only parent is the base commit": neither held for that commit.
  - For npm, nothing tied package-lock.json to the receipt's change: a receipt naming `minimist 1.2.5 -> 1.2.6` passed with a lockfile that moved no minimist and added another package.
  - An advisory ID `GH-1` passed and went into the pushed commit's "Fixes GH-1." line; a changed file had no size limit (40 MB of spaces packed into a 41 KB bundle); a self-hosted runner was not refused; setup-node's cache was left on; `@foo/bar` and `foo-bar` got the same branch, so one fix's PR silenced the other; a closed PR silenced its fix with no warning.
  - The mutation script had a mutation that never applied (`\d` in an ordinary string), and no time limit: the ReDoS mutation made vitest spin without end, and the lane's report put the stopped run down to low memory. The design's claim that each check had a test failing without it was untrue for "the entry's own name trusted".
  - The npm PR body's "Fix published" row said "the publish time of the fixed version" for the latest among the fix's planned versions (diff review 6516416032), the wording docs/mistakes/2026-10-30-fix-published-at-is-the-latest.md had corrected elsewhere.
- **Why.** The checks were written from what the commit's text and the receipt say, not from how Git and the lockfile read them, and only the forms the validation job writes were tested, not forged ones. The mutation run's "NOT APPLIED" line and its stop were not looked into, and a cause no one had checked was written down as fact.
- **Fixed in LB2a.** Parents and tree from Git, headers only in Git's order, fsck on each fix commit; the npm lock must move the receipt's package from `from` to `to`; advisory IDs only as GHSA, CVE, MAL or PKSA; a size limit per changed file; GitHub-hosted runners only; no setup-node cache; branch names that cleaning could merge end with a hash; a warning annotation for a closed PR's fix; mutate.mjs fixed, with a 300 s limit per run reported apart; "the latest among the fix's planned versions" in the PR body.
- **Not closed by that fix, for npm (cloud review 6518582507 at b6a7c88, B1 and N-a).** LB2a's lockfile check named each `packages` key by the text after its last `node_modules/`, so a key without one, `"aaaaaaaaaaaaminimist"`, which npm installs nothing at and the judge and `fromPackageLock` skip, counted as minimist: with the real judge, a PR "minimist 1.2.5 -> 1.2.6" opened for a lock that installs no minimist. It also compared versions by name, not by install path, so a package nothing requires could be added, and the top-level copy could be removed with the fixed version only nested. The same cause as above: the lock was read differently from how npm and the judge read it. Fixed in the same PR: keys are read by the judge's own `lockKey`, and any key that is not the root or an install path refuses the artifact; the check is by install path (each planned path moves from `from` to `to` in place, each added path is required by a moved or added one, every other entry is as at the base); fsck runs once. The lane's review of that fix (comment 6519780482 at 7d25696) found the same cause once more: "required" was read from the forged entries' own `dependencies`, and an added copy could change what an unmoved package loads, so a stray package and another package's move still got PRs with the real judge. Now each moved or added entry's requirements, `os` and `cpu` must be the registry's, and the root and every unmoved entry must resolve each requirement to the same path as at the base. The automated security pass at 8b4856d added that an added copy must be the named package (no alias) at a version in its requirer's range. (Since the identity rule, docs/decisions/2026-10-31-lock-corpus-alias.md, an added alias is taken where its requirer's spec is an `npm:` alias for that package; review 6538813186, N4.)
- **Also merged before this PR: package-lock.json read only in part (lane reviews 6521445720 at aa5d75b and 6524150863 at 1e6f705).** Main's `readLock` (judge.ts), which `ludion judge` and #210's PR job use, read only the `packages` section. A lockfile v2 also holds the nested `dependencies` tree, which npm 6 installs from, so a v2 lock's npm 6 tree was never judged. With the real judge and registry, the PR job opened PRs for a forged v2 lock whose tree gave another tarball (npm 6.14.18 installed left-pad as minimist), and then, after the first fix, for one whose tree's `requires` named left-pad by URL, which npm 6 `install` added; a tree could also be added to a v3 base. Why: the same as above, at a larger scale. The property the PR job keeps ("whatever version of npm installs from the PR's lockfile, it installs the receipt's change and nothing else changes") was not written down, so each review found another part of the file that some npm reads. Fixed in the same PR: `readLock` refuses another lockfileVersion and a top-level key npm does not write, and requires a v2 lock's npm 6 tree to name the same install paths as `packages`, each with the same version, resolved, integrity, flags and `requires` (a link's from its folder), with no key npm does not write; the PR job keeps the base's top-level keys and refuses a tree the base did not have, and both it and `ludion judge` refuse npm-shrinkwrap.json.
- **A fix that narrowed what Ludion reads (R lane's review 6529858505 at 217a6f8, B1).** The sixth round made `readLock` refuse any lock with an unmet requirement. That also refused lockfiles npm 11 writes and main reads: `overrides` outside a range, and `--legacy-peer-deps`. So `ludion judge`, npm `patch` and the PR job did less than main for those projects, and no user-facing text said so. Why: the check was written for a forged change and tested only on forged changes and on locks without either setting. It was not tried on the lockfiles real projects write with npm's other settings, and a narrowing was made without the owner's sentence. Fixed in the same PR (docs/decisions/2026-10-31-lock-requirements-against-the-base.md): the requirement check compares the change with the base and counts the project's `overrides`, and locks npm 11 wrote with each setting are test fixtures.
- **Check:** `packages/cli/test/deliver.test.ts` — each forged artifact above (a `parent` after `author`, headers out of order, a commit fsck refuses, a padded lockfile, a lockfile that does not move the receipt's package, a lock key that is not an install path, a package nothing requires, the planned copy moved elsewhere, `GH-1`, an alias in the base's lock, requirements other than the registry's, including forged optional and peer dependencies, an added copy that shadows an unmoved package's dependency, an added alias or a version outside its range, an npm 6 tree with another tarball or with forged `requires`, a changed lockfileVersion, a tree added to a v3 base, a base with npm-shrinkwrap.json) is refused with nothing pushed or opened, and `deliver open` prints the closed PR's warning.
- **Check:** `packages/cli/test/judge.test.ts` — "reads npm 11's locks with overrides and with --legacy-peer-deps, and still refuses a change that adds an unmet requirement".
- **Check:** `packages/cli/test/judge.test.ts` — "package-lock.json as every npm reads it": four v2 locks npm 11.19.1 wrote are read, and each disagreement between the two views (tarball, version, integrity, alias, a path only one view has, a workspace's or link's children, `requires`, flags, keys npm does not write, another lockfileVersion, a top-level key) is refused.
- **Check:** `packages/cli/test/judge-cli.test.ts` — `ludion judge` refuses a checkout with npm-shrinkwrap.json.
- **Check:** `packages/cli/test/branch.test.ts` — names that cleaning merges get different branches.
- **Check:** `packages/cli/test/action-patch.test.ts` — start.sh refuses a runner that is not GitHub-hosted, and the template turns setup-node's cache off in both jobs.
- **Check:** `docs/bench/2026-10-30-lb-design/scripts/mutate.mjs` — every check above has a mutation that its test must catch; a mutation that does not apply, or a run that does not end within 300 s, is reported, not counted as quiet.
- **Rule:** "Receipts show what was checked, not more (and, once implemented, the exposure-time timestamps)."
