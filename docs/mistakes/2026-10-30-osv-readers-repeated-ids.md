# 2026-10-30 — The two OSV batch readers disagreed on a repeated id

- **What happened.** LV3 (#213) made `osvIds` (packages/cli/src/security/npm-facts.ts), the judge's OSV batch reader, refuse every item `OsvClient.ids` (osv.ts) refuses, and added a test that the two "read the same ids". `OsvClient.ids` keeps each id once (`[...new Set(ids)]`); `osvIds` kept an id as often as OSV repeated it. So the agreement held only for items with no repeated id, and docs/mistakes/2026-10-30-osv-batch-item-read-as-no-record.md's "cannot drift apart unseen" said more than the test showed. No judgement changed: a repeated MAL- id still stopped. The cloud review of #213 found it (https://github.com/Ludion-ai/ludion/pull/213#issuecomment-6515878521, finding 3). LV4 fixed it: `osvIds` keeps each id once, in OSV's order, as `OsvClient.ids` does.
- **Why.** The shared list of items in the agreement test had no item with a repeated id, so the one difference left between the two readers was never fed to both.
- **Check:** `packages/cli/test/judge.test.ts` — "OSV's batch answers for the judge": the shared list now has items that repeat an id, and `osvIds` must read the same ids as `OsvClient.ids` on them; "keeps a repeated id once, in OSV's order".
