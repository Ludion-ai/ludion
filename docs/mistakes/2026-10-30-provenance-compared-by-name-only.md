# 2026-10-30 — Provenance was compared by the repository's name only

- **What happened.** Gate 2's provenance comparison (judge.ts), rule 1's same-release exception (time-cap.ts) and the next fix's publisher check (next-fix.ts, #213) took two releases for one source when their provenance named the same repository and workflow (and, for the exception, the same commit). They read only `externalParameters.workflow.repository` and `workflow.path` (or v0.2's config source). A name can be registered again: in SlugFest (reported 2026-06-06, more than 1,500 packages), npm's trusted publishing was tied to owner/repo until the first publish, so whoever took a freed name could publish someone else's package correctly, with provenance naming the same repository and workflow. All three places would have let such a version through. The statement also records GitHub's numeric repository id and the event that started the run, and Ludion did not read them, so a publish from `pull_request_target` or `issue_comment` was not told apart either. The owner's Claude chat found it on 2026-10-30 from current GitHub and npm material; LI fixes it (docs/decisions/2026-10-30-provenance-immutable-id.md).
- **Why.** Each place compared what a person reads as the identity of a repository, its name, and none asked whether that name always points to the same repository. The provenance format was read for the fields the first use needed, and later uses reused that reading without going back to the format.
- **Check:** `packages/cli/test/judge.test.ts` — the SlugFest shape (same name and workflow, another id) stops in gate 2 and in the same-release exception; an id on one side only stops; `pull_request_target`, `issue_comment`, `workflow_run` and `schedule` stop, and so does an id without an event; two records without an id are compared as before with an info finding; provenanceFrom reads the id and event from v1 and v0.2 and refuses malformed ones.
- **Check:** `packages/cli/test/dependencies.test.ts` — the same in the next fix's publisher check, on either side, and in `ludion patch`'s same-release check from the registry's statements.
