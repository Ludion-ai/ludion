# 2026-10-31 — The protection record wrote "Trap" in the class column of a row no published record backed

- **What happened.** In PR #236 up to 42e30b6, `renderRecord` (packages/cli/src/security/impact.ts) wrote the row's class as given. A row whose class was `trap` showed 「罠」 / "Trap" in the class column even when its stop was another reason (`install-scripts`) or when it was not stopped at all (`fixed`). docs/decisions/2026-10-31-impact-classes-trap-published-record.md, point 2, says "trap" is written only when a published record says the version is malicious. The stop cell and the summary line followed that; the class column did not. The tests pinned the wrong output: a fixture row (ua-parser-js 0.7.29, class trap, stop install-scripts) expected "Trap" and 「罠」. Found by the review of 42e30b6 (PR #236 comment 6541677765, point 1).
- **Why.** LMR1b changed the stop cell and the summary for point 2 and checked those two. Nobody asked which other cells say "trap": the class column comes from the receipt, which is not trusted, and was not traced back to the record.
- **Fixed** in LMR1f: `renderRecord` refuses a row whose class is trap unless its stop is a trap whose record `classify()` gives trap. The fixture row is now takeover; tests cover a trap class with each other kind of row, in both languages, and the backed rows that still show it. Three mutations that loosen the check are caught (docs/bench/2026-10-31-lmr1-impact-classes/logs/mutate.log).
- **Check:** `packages/cli/test/impact.test.ts` — "writes the class trap only on a row stopped as a trap that a published record backs, and refuses any other (R236, point 1)".
