# 2026-10-31 — Every receipt's scan note named two destinations; Ludion's code sends requests to many more

- **What happened.** The note `OsvClient.scan()` puts in every scan result, and so in every receipt's `before` and `after`, said: "Package names and versions are sent to OSV, and Composer package names to Packagist; source is not." Since #145 (2026-10-28) that was the whole list. The same receipts record lookups at other hosts: the npm registry's publish time and publisher (`fix_published_note`, `version_choice`), the EPSS list's `epss_date`, and, for PHP, the digest of the image pulled from Docker Hub. The first audit to point it out read it in LB2b's npm receipt (docs/bench/2026-10-30-lb2b-trial/logs/receipt-npm-41076186488.json).
- **Why.** The note was written when the scan was the only network step, and nothing tied it to the code. Each lane that added a host (npm facts, KEV and EPSS, Composer archives, Packagist metadata, Docker Hub, php.net, Maven Central) changed the code and its own docs, not the note in osv.ts, and no test read the note.
- **What changed.** The note is `SCAN_NOTE` in packages/cli/src/security/osv.ts. It says what Ludion sends, across all its commands, and names each host: OSV, the npm registry, Packagist, the Composer archive hosts, Maven Central, php.net, Docker Hub, CISA and the EPSS list (downloaded whole), and the project's own GitHub repository for `ludion deliver open`.
- **Check:** `packages/cli/test/osv-note.test.ts` — "names every host of packages/cli/src" fails when a host written after https:// in packages/cli/src, or a key of the Composer archive policy, is not in the note (unless it is listed with the reason it is not a request); "names no host the code does not request" fails on a host the note names that the code no longer has; "is the note scan() puts in its result" fails when scan() returns any other text.
