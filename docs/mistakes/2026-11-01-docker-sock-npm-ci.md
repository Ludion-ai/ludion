# 2026-11-01 — The bench e2e scripts ran `npm ci` with install scripts in a container given the host's Docker socket

- **What happened.** Six bench scripts (docs/bench/2026-10-29-la-per-fix-apply, 2026-10-30-lb-design, 2026-10-30-lv-next-fix-version, 2026-10-30-lv3-osv-publisher, 2026-10-31-limgv and 2026-10-31-lnode, each `scripts/e2e.sh`) began with `npm ci --no-audit --no-fund`, with no `--ignore-scripts`, and ran in a container started with `-v /var/run/docker.sock:/var/run/docker.sock` so that the built CLI could reach Docker. A container that holds the socket can start a new container that bind-mounts any host folder Docker can reach (on the machine used, everything under the user's home, `.claude` included), so the install scripts in the lockfile (esbuild's and workerd's) ran with the host's power, as if `npm ci` had run on the host. Between 2026-10-29 and 2026-10-31 the e2e ran this way 35 times, all but one with the network on. No harm is known; the versions were the ones the lockfile already pinned. A first-principles audit of the session records found it on 2026-11-01. Fixed by adding `--ignore-scripts` to the six lines; the READMEs and the two run.sh files that pass the socket now say what the socket gives.
- **Why.** "Run it in Docker" was taken to make anything safe, and the socket was mounted for the CLI's own sandbox without asking what else it hands to the code in that container. The rule against running dependency code on the host, and the hook that enforces it, look only at the host's command line; nothing looked at which containers can reach Docker. The scripts' READMEs said the socket was mounted, not what it allows.
- **Check:** `tools/records/test/bench-socket.test.ts` — under docs/bench/, follows every container started with the socket (a docker run line in a script or a README's code block, or a shell function holding one), the scripts it runs, and every script that uses the docker CLI without starting containers, and fails on an `npm ci`, `npm install` or similar without `--ignore-scripts`, or on `npx`, `npm exec`, `pnpm` or `yarn`, in any of them.
- **Rule:** "Never run project-controlled or downloaded code or commands on the host."
- **Not fixed here.** After `npm ci --ignore-scripts`, e2e.sh still runs `npm run build -w ludion-ai` in the socket container, so the build tools from the lockfile (esbuild, TypeScript) still run with the host's power. Splitting the build (no socket) from the e2e (socket, only the one-file CLI and the e2e's own scripts, read-only) removes that; it was not done here because the e2e cannot be run to show that the split scripts still work.
