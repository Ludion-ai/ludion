# 2026-11-01 — The exposure-time record could not notice that GitHub's stored times had moved an hour

- **What happened.** On 2026-11-01 GitHub's API gave some stored times exactly 3600 seconds later than the real time, reported by audit 6555614920 (item 1). Seen: PR #253's `created_at` 09:23:44Z in an answer whose own Date header said 08:32:10 GMT, with 08:23:44Z in the events API for the same PR; and a workflow run's `run_started_at` and `completed_at`. A later audit, 6556836129 (item 4), compared such times with commit dates and runners' stamps: the shift began between 07:45:39Z and 08:01:17Z and ended between 08:36:57Z and 09:16:20Z (bounds; the exact times are not known). A time can change after it is first read: comment 6555614920's POST answer said 08:36:57Z, and a GET at about 10:19Z says 09:36:57Z. About two hours later the values still read an hour late; whether they are ever corrected is not known. PR #252 (LEXP, not merged) at e623489 compared such times with a runner's clock as if they were one clock, so while they were shifted it could have done two things in silence. Every record's `checked_at` would have lain before its run's `run_started_at`, so every record would have been dropped as not valid, and the PR's Found row would have said "`0` records read", with nothing about clocks. And a `merged_at` an hour later would have been recorded, once and for good, as the end of the fix's exposure time, so the exposure time would have been an hour longer. Neither happened to a real user: the audit read the code, and #252 had not run on GitHub. Whether `merged_at` was shifted too was not observed (a guess, from the same API's `created_at` and `updated_at`). The cause is not known, and GitHub has not explained it. A guess, from the later audit: Pacific time's 01:00 to 02:00 happens twice that day (08:00 to 09:00Z, then 09:00 to 10:00Z), and values written in the first pass read back as the second. That guess predicts that no value from these stores reads back in hour 08; of the 177 values that audit read back, 0 were in hour 08 and 92 in hour 09. If the guess is right, it comes back on 2027-11-07; this is not verified.
- **Why.** The shift was on GitHub's side. Not noticing it was Ludion's mistake. The definitions (docs/bench/lexp/definitions.md, sections 2 and 3) took the runner's clock, GitHub's Actions times and GitHub's pulls API as one clock, so a disagreement between them had no way to appear: the record's window check treated it as an invalid record, and `merged_at` was not compared with anything. The Date header of the same answer was there and was never read. The tests' stand-ins gave times from one clock and no Date header, so no test could show the difference. Exposure time is Ludion's first measure (CLAUDE.md, Product), and a wrong one looks the same as a right one.
- **What changed** (same PR; definitions.md, sections 7 and 8). The walk is not done when GitHub's start of this run is later than the runner's clock or than the Date of its answer. A run whose times do not agree stops the walk instead of being passed over. A `merged_at` later than the Date of its answer or than the job's clock is recorded with `merged_at_doubt`, and no hours end at it. The merge record and the PR's Found row keep GitHub's time and the runner's, not only their difference, and each disagreement is written out with both.
- **Check:** `packages/cli/test/exposure.test.ts` — "does not walk when GitHub's start of this run is later than the runner's clock, and says by how much (X7)" (`run_started_at` an hour past now, then a second before it) and "a merged_at later than the Date of GitHub's own answer, or than this job's clock, is recorded with its doubt, and no hours end at it (X7)" (`merged_at` past the answer's Date, then in the same second).
- **Check:** `packages/cli/test/exposure.test.ts` — "keeps GitHub's time and the runner's: the run that saw the fix, and this run, whatever the row says (section 8)".
- **Check:** `packages/cli/test/deliver.test.ts` — "says in the Found row, and does not stay silent, when GitHub's times and the runner's do not agree (X7)".
- **Rule:** "Receipts show what was checked, not more (and, once implemented, the exposure-time timestamps)."
- **Not fixed here.** Three comparisons with a runner's clock have no margin (this run's start, the window of a record's `checked_at`, `merged_at` against the job's clock). A margin would loosen the bound on a forged `checked_at`, and the difference between the runners' clocks and GitHub's has not been measured. A small difference therefore reads as a disagreement: the walk stops or is not done, or a merge's hours are not computed, and each says so with both times. GitHub's times that are earlier than they should be, by less than the time between the event and the answer, are not noticed; the merge record keeps `recorded_at` so that a reader can count such a record apart. The Date of an answer shows a shifted time only while that time is still in the future: once real time has passed it, a run is still caught by the window of its record's `checked_at`, but a `merged_at` is not noticed when the merged job runs that much late. A run started in the shifted hour stops the walk until it leaves the list (100 runs or 90 days), so found_at stays later for that long, and the row says so. Every time a record keeps is as it read then; it may read differently later. Nothing has run against GitHub's real answers.
