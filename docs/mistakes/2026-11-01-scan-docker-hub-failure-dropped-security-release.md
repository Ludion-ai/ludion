# 2026-11-01 — `ludion scan` still dropped a newer security release when Docker Hub failed other than with a 404

- **What happened.** #246 (LSCAN404) made an official PHP or Node.js image check keep the line's newer security releases when Docker Hub answered 404 for the move's tag (`MissingImageTag`). Every other failure of the same check still lost them: packages/cli/src/security/php.ts `dockerHubTag` throws a plain error when the pull token cannot be had (an error status from auth.docker.io, no token, a failed request), when the tag's HEAD answers an error status (429, 5xx) or no digest, and when a request fails, times out or is redirected. `imageMove` let that error through after `fixes` was counted, so `ludion scan` printed `php: unavailable — Docker Hub gave no digest for ... (HTTP 503).` (or `node:`), exited 2, and `scan --json` had no `security_releases`, while both READMEs (line 123) say scan exits 1 when it finds "a PHP or Node.js security release newer than the Dockerfile's version". It happens whenever Docker Hub is down or rate-limits, and for as long as a network blocks Docker Hub alone. A first-principles audit on 2026-11-01 found it.
- **Why.** LSCAN404 fixed the case the audit before it described (the 404) and its tests covered only that case: no test made Docker Hub fail in another way with a security release between. The rule underneath, that whether a newer security release exists is read from the official list alone and Docker Hub decides only whether the image can move, was not written down in the code, so the fix was shaped by the one failure in view rather than by where `fixes` is counted.
- **What changed.** php.ts wraps the tag check in `imageMove`: with `fixes`, any failure throws `ImageMoveStopped`, which keeps them and names them first, then gives Docker Hub's error (`PHP 8.4.29 is a security release newer than 8.4.28; Docker Hub could not be checked for php:8.4.30-cli, the newest release of PHP 8.4 in the Dockerfile's variant: Docker Hub gave no digest for php:8.4.30-cli (HTTP 503). Ludion does not move the image without that check. No update decision was made.`). `MissingImageTag` is now a kind of `ImageMoveStopped`, with its reason unchanged. scan.ts keeps any `ImageMoveStopped`'s releases in the failed check, so `found()` counts it toward exit 1. With no newer security release, Docker Hub's error is thrown as before (exit 2, `unavailable`). Neither the wait nor the choice of the version a move goes to changes; `patch` still stops in these cases.
- **Check:** `packages/cli/test/scan-exit.test.ts` — for the PHP and the Node.js image, with a security release between, eight Docker Hub failures (HTTP 503, 429 and no digest for the tag; a failed request and a timeout for the tag; HTTP 503, no token and a failed request for the pull token) each make scan exit 1 with `attention_required`, the text line names the release and Docker Hub's error, and nothing says "unavailable"; `scan --json` keeps `security_releases`; with none, after the wait, each failure exits 2 with Docker Hub's error as before and no `security_releases`.
- **Check:** `packages/cli/test/node-image.test.ts` — with Docker Hub answering 503, the stop is an `ImageMoveStopped` (not a `MissingImageTag`) with the exact reason and both newer security releases; with none, it is Docker Hub's error, word for word, and not an `ImageMoveStopped`.
