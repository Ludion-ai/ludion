# 2026-11-01 — `ludion scan` dropped a newer security release when Docker Hub had no tag for the move

- **What happened.** Since #239 (LIMGV), an official PHP or Node.js image check asks Docker Hub for the tag of its line's newest release in the Dockerfile's variant before a move. When Docker Hub answered 404 (Docker has not published the tag yet, or no longer builds the variant), packages/cli/src/security/php.ts `imageMove` threw a plain error, and the line's security releases newer than the Dockerfile's version, already counted in `fixes`, were lost. packages/cli/src/security/scan.ts turned the error into `{ ecosystem, error }`, so `ludion scan` printed `php: unavailable — Docker Hub has no ...` (or `node:`), exited 2, and `scan --json` had no `security_releases`. Since #243 (LSCANX), both READMEs say scan exits 1 when it finds "a PHP or Node.js security release newer than the Dockerfile's version"; in this case it did not, and the output never said such a release existed. It happens right after a release, before Docker publishes its tag, and for as long as a variant pinned to an OS release is no longer built. A first-principles audit on 2026-11-01 found it.
- **Why.** The tag check (LIMGV) was added as a stop after `fixes` was counted, with the same plain error as the lookup failures, so the stop could not carry what had already been found. LSCANX then defined scan's exit 1 by `securityMove()`, which reads only a check's result; a failed check has none. No test looked at scan's exit code or text with a security release between and the tag missing: security.test.ts and node-image.test.ts checked only the stop's reason from `scanPhp` and `scanNode`.
- **What changed.** php.ts throws `MissingImageTag`, which keeps `fixes` as `security_releases` and, when there is one, names it first in the reason (`PHP 8.4.29 is a security release newer than 8.4.28; Docker Hub has no php:8.4.30-cli, ...`). scan.ts keeps those releases in the failed check, and `found()` counts such a check toward exit 1; cli.ts uses `found()` and prints the reason on standard output without "unavailable". With no newer security release, the stop is as before (exit 2, `unavailable`). Neither the wait nor the choice of the version moved to changes. `patch` still stops in this case; its reason now names the security releases too.
- **Check:** `packages/cli/test/scan-exit.test.ts` — for the PHP and the Node.js image, with a security release between and Docker Hub missing the tag, scan exits 1 with `attention_required`, the text line and `scan --json` name the release and the missing tag, and nothing says "unavailable"; with none and the tag missing after the wait, scan exits 2 with the reason as before and no `security_releases`.
- **Check:** `packages/cli/test/node-image.test.ts` — the stop is a `MissingImageTag` whose reason names one or two newer security releases ("is a security release", "22.23.4 and 22.23.2 are security releases") or none, and whose `security_releases` lists them.
