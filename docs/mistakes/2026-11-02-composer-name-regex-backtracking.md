# 2026-11-02 — The Composer name check took exponential time on a name from Packagist

- **What happened.** `COMPOSER_NAME` in packages/cli/src/security/time-cap.ts, which `packagistReleases` tests every name against before asking Packagist, nested a `+` inside a `*` on both sides of the `/`. A name of `n` letters followed by `-/x` makes it try about 2^n ways to match before it refuses: in Docker, on Node 24.22.2, `n` = 24 took 234 ms, 28 took 3.7 s, 30 took 14.8 s, and 32 was stopped at 45 s; `x/` followed by `n` letters and `-` took 326 ms, 4.7 s and 18.6 s at 24, 28 and 30. The check runs on Node's main thread, so nothing else in the run moves until it ends, the 30-second fetch limit included. Such a name can come from outside: `candidateTimeCap` takes the names a planned version requires from Packagist's metadata, which `packagistReleases` only asks to contain a `/`, and a Composer lock entry's name passes inventory.ts's pattern, which looks at its characters and length and not at its shape. CodeQL reported both places on line 175 as `js/redos` (alerts 3 and 4, high) on 2026-10-29, and they stayed open until a first-principles audit found them and measured the time. `ludion patch` was not run end to end on such a name; the times are of the expression alone.
- **Why.** #148 added the expression to keep a name from changing the Packagist URL, and its test tried one refused name, `../etc/passwd`; nothing looked at how long a refusal takes. The alerts were on the code scanning page only: nothing in the way of working reads that page, and an open alert fails no check (on main at c9be544, CodeQL's `Analyze (javascript-typescript)` is `success` with alerts 3 and 4 open).
- **What changed.** The expression has one way to match any name: each repeated step takes one letter or digit, with its optional separator before it, and no `+`. It accepts the same names. `isComposerName` also refuses a name over 240 characters before the expression runs, inventory.ts's limit on a package's name; before this, a longer name that had the right shape went on to Packagist. The length limit does not replace the expression's fix: the old expression took 14.8 s on a name of 33 characters, so the test also times names under the limit.
- **What this does not catch.** The check holds this one expression. A new open code scanning alert still fails nothing, and four others are open today (`js/incomplete-sanitization` in scripts under docs/bench, run by hand).
- **Check:** `packages/cli/test/time-cap-composer-name.test.ts` — under a 50 ms limit Node's VM enforces, `packagistReleases` refuses `a` × 10,000 + `-/x`, `a` × 236 + `-/x` and `x/` + `a` × 236 + `-` without a request; `isComposerName` gives the old expression's answers, recorded as digests by running it, on 200,000 random names (fixed seed) and on all 335,923 strings of up to 7 characters over `a`, `-`, `_`, `.`, `/` and a line feed; a name of 240 characters is taken and one of 241 refused. The old expression stays in that file as a comment only: the PR's first version kept it as code to compare with, and CodeQL reported it there as two new high `js/redos` alerts.
