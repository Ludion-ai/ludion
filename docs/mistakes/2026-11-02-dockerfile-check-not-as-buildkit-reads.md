# 2026-11-02 — The Dockerfile check did not read a file as BuildKit does, and two readers took more than linear time

- **What happened.** `officialImage` in packages/cli/src/security/php.ts, which `phpImage`, `nodeImage` and the PR job's `contentProblem` all use, ran expressions over the whole file to refuse a continuation, a second FROM, ADD, COPY --from and RUN --network. BuildKit reads a line differently, so these passed the check and `docker build --network=none --pull=false` acted on them: U+0085 before ADD (JavaScript's `\s` lacks it; Go's `unicode.IsSpace`, which BuildKit uses, has it), a backslash followed by spaces or tabs at a line's end (BuildKit continues the line; the expression wanted a line feed right after the backslash), and an `# escape=` directive after U+0085. In Docker 29.9.2 the URL was fetched for ADD, and the second stage was built for FROM. Looking further in this lane found three more that passed: a flag's name in quotes or with a backslash (`COPY --fr"om"=x` is `--from=x` to BuildKit, and it went to resolve the image), and a syntax directive written `//syntax=x`, which BuildKit sends the build to before reading anything else. So the receipt's and the commit's "offline in Docker", and the README's and docs/status.md's sentences on it, said more than the check held. No project was reported to have used these forms. Separately, the same expressions were quadratic or cubic and `LOCK_PATH` in judge.ts was quadratic: on Node 24.22.2, COPY after 4,000 line feeds with 4,000 spaces took 21 s, 64 KiB of line feeds 3.6 s, and a `packages` key of 1 MiB 29 s, on the main thread with nothing else moving. A first-principles audit found the U+0085, backslash and escape forms and the times.
- **Why.** The check was written as a list of what to refuse, in JavaScript's idea of a line and of whitespace; nothing compared it with what BuildKit reads, and its tests held only plain forms. `\s` and Go's `IsSpace` are not the same set. A file that BuildKit reads differently from the check is exactly where the two disagree on what is built. For the times, as in docs/mistakes/2026-11-02-composer-name-regex-backtracking.md, nothing looked at how long a refusal takes.
- **What changed.** `instructions` in php.ts reads a file in BuildKit's order: it cuts at line feeds, drops the carriage returns at a line's end and the left's whitespace (U+0085 included), then looks at directives and continuations, and then at the first word. It refuses a directive anywhere (so the escape is always a backslash), any line ending in a backslash and spaces, and a carriage return, U+2028 or U+2029 inside a line. A flag's name is read with its quotes and backslashes out. `lockKey` refuses a key over 4,096 characters, without repeating it, and `LOCK_PATH` has one way to match any key, as the earlier node_modules segments it spelled out were already folders. `namesNodeImage` also cuts lines at line feeds, takes off the whitespace at each end of a line (U+0085 included, so CRLF is one line end), reads a vertical tab, form feed or carriage return as a separator, and joins continuations under either line end, so an unconfigured scan reports a Node.js image in those forms as a check, which `nodeImage` then reads or refuses.
- **What this does not catch.** The check follows BuildKit as Docker 29.9.2 ships it; a later BuildKit that reads more forms is seen only if a form is added here. The PHP side's detection, `/\bphp:/` in cli.ts, check.ts and scan.ts, still looks at the raw text: `FROM ph\ ` and `p:8.4.25-cli` on the next line is not offered or checked when no policy names it, and `phpImage` refuses it when one does. `namesNodeImage` does not find every FROM BuildKit reads either: an image in quotes (`FROM "node:22"`, `FROM no"de":22`) or with a backslash in its name (`FROM no\de:22`), one from an ARG or `${X:-node:22}`, and one after `--` (`FROM -- node:22`) or after a flag ended by a raw byte 0x85 or 0xA0, which a file read as UTF-8 turns into U+FFFD, are not offered or checked when no policy names node, and `nodeImage` refuses them when one does; `docker build` took these forms with `scratch`. This list is what was tried, not a proof that there are no others. Neither gap opens a way outside the build. `packageLockInputs` on 1,000 valid install paths of about 4,096 characters (4 MiB), with one dependency each, took 3.9 s; by the code, not a profile, in `resolveFrom`, which is unchanged here. That is no bound on it: a review of this PR measured 37,105 ms on one key of about 4,096 characters with 10,000 dependencies, and 35,959 ms on main's code.
- **Check:** `packages/cli/test/dockerfile-check.test.ts` — every form above is refused, for both images, with its own reason (names with `dockerfile-check-u0085`, `dockerfile-check-backslash-space`, `dockerfile-check-flags-and-directives`, `dockerfile-check-across-lines`); `dockerfile-check-names-node`, `dockerfile-check-names-node-separator`, `dockerfile-check-names-node-crlf`, `dockerfile-check-names-node-line-end` and `dockerfile-check-names-node-gap` hold what `namesNodeImage` finds and what it does not; the examples' Dockerfiles, CRLF and a byte-order mark are taken, at the same place in the file; `gate-reader-linear` holds each reader to 50 ms on 64 KiB, each reader of a 4 MiB lock to 1 s and `packageLockInputs` on one to 4 s, under a limit Node's VM enforces; digests pin `lockKey`'s answers on 299,593 short keys and the 434 locks of the npm corpus, recorded by running the old code, and what the check takes on 43,275 short files.
