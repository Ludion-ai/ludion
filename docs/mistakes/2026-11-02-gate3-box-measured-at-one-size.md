# 2026-11-02 — Gate 3's box was measured at one size, and what it measured was read as the box's limit

- **What happened.** The first form of gate 3's new type (#263) was measured on an example of 4 pages, on next 15.5.6, and written up. Three things were wrong with what that was taken to show, and an audit and a review found each before the PR was merged. Webpack's persistent cache filled the box's 64 MiB /tmp, so a project of a few dozen one-line pages failed to build (on old, `undecidable`). The first fix's record then said "Memory is the next wall" from a swap figure, with no look at where that memory went; the main cause was that Next.js makes its build's workers from the machine's CPUs and does not see the box's `--cpus 1`, so on 16 CPUs it started 15 workers in 512 MiB. On next 15.5.6 at 50 pages swap went from 413,659,136 bytes to 0 with one worker. On next 16.4.4, the latest, which nothing had been run on, the same 24 pages passed once and were killed once with one OOM kill. And Next.js 16's default build, Turbopack, has its cache in another folder, so webpack's fix did not touch it, and extending it would have stopped every build within a second. The test added with the first fix was named `gate3-fits-box-at-50-pages` and did not show that anything fits: it runs the driver with Node.js's modules stood in for.
- **The same fault, in the PR's sentences.** "A larger project may not build, which is `undecidable`" holds only for old: on new it is `broken`, and no sentence said so. "Every run reached the 512 MiB limit and used swap, up to 450,080,768 bytes in one run" holds only for the 4 cases' runs, where the same PR's own table had runs with swap 0 and a run with 452,980,736. "Only hashes are accepted" left out page paths, which `parseRun` takes as text of up to 2,000 characters. "73 passed" was the count from before a test was added; it was 74.
- **Why.** Each number was true of what was run, and each sentence said more than what was run: a size, a version and a machine were read as properties of the box. Nobody asked why the build used that much memory, or tried the version a new project would get, though the definition says the version is "measured, not assumed". The sentences were written from memory of a code path, and not compared with the test or the table beside them.
- **What changed.** The driver sets `CIRCLE_NODE_TOTAL=2` for one worker, and `TURBO_ENGINE_READ_ONLY=1` so that Turbopack writes no cache; a project's `.env.example` can set neither. Every result holds `host_cpus`, so a figure is read knowing what it ran on. `examples/nextjs-security-cases/next-16.4.4` and case (e) keep the latest version in reach. The test is now `gate3-webpack-cache-read-only-before-build`, named for what it holds. The sentences are corrected, and the box's limits and packages/sandbox are unchanged.
- **What this does not catch.** These tests do not show that a build fits: they hold that the driver sets the values and makes one folder read-only, with Node.js's modules stood in for. What shows a build fits is the table in docs/progress/2026-11-02-lg3-gate-3-type.md, by hand, on one machine. Neither value is a public setting, and if Next.js stops reading one nothing fails, except case (e) of `gate3-docker.test.ts`, which CI does not run. A new `broken` from a lack of memory can still stop a fix that breaks nothing: the verdict reads no memory figure, and that is undecided.
- **Check:** `packages/cli/test/gate3.test.ts` — `gate3-webpack-cache-read-only-before-build`, `gate3-one-worker-whatever-the-host`, `gate3-turbopack-cache-not-written`, "broken: new's build failing for lack of memory" and "a page path is the one text it lets through". Each fails with its line of the fix taken out. These tests do not show that a build fits.
