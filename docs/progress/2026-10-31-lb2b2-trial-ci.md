## What Ludion's template would need (not changed tonight)

1. **Hourly with an early exit.** action.yml gains `mode: check` (the diff, trial-files/ludion-action-5f740a5..6162b79.diff, the version after the review fixes); action/patch-workflow.yml gains the `check` job (`contents: read`, `pull-requests: read`), `cron: "23 * * * *"`, and on `patch`: `needs: check` and `if: ${{ !cancelled() && needs.check.outputs.work != 'false' }}` (trial-files/ludion-php.yml). Better in the CLI than in shell, with tests: a forged earlier receipt does not quiet a new advisory (the check reads none), a PR on a folder that main has changed is not counted, an error, an empty answer, an unnormalised folder or a rename out of the folder answers work=true (the review's N1–N3 and the grep trap). For Maven the check runs Docker too (N4). Known costs: a fix that waits, fails or is blocked has no PR, so each hourly run does the full Docker run; a closed Ludion PR does not count.
2. **CI.** Form C needs one permission (`statuses: write`) and one step, and says only what Ludion checked. Seeing the project's CI on the PR needed B2: the PR job starts CI (`actions: write`) and the project's CI posts a status. Other ways, not tried: the PR job waits for the dispatched run and posts its result as the status (`actions: read`, `statuses: write`, the job waits minutes); a person approves the `action_required` run (form A); a GitHub App's token, whose events start workflows (the owner's decision, a new App).
