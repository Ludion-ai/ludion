## What changed

- `ludion check` (packages/cli/src/security/check.ts): for the saved policy's ecosystem only, each fix's key and whether it waits (t*), is due, or is quiet. Other inventories in the folder are named, not scanned. A Maven policy, a scan error, an incomplete scan or a policy that cannot be read is undecided (exit 2).
- action.yml mode `check` and action/check.sh: the prototype from the private trial (docs/bench/2026-10-31-lb2b2), now reading `ludion check` instead of a full `ludion scan`. work=false only when every fix waits, is quiet, or is fixed by an open Ludion PR (the prototype's rule B, unchanged).
- action/patch-workflow.yml: a first job `check` (`contents: read`, `pull-requests: read`); patch `needs: check` and runs unless check answered work=false. The cron is unchanged (`23 */6 * * *`).
- npm-facts.ts exports boundedJson; time-cap.ts's npmReleases also returns the registry document's `time.modified`.

## Limits found while building it

- Composer: Packagist returns its own advisory ids (PKSA-) beside OSV's; the check does not send those to OSV, so a Composer fix with one is always due, as before this change. Reading the PKSA record's GHSA alias would let the anchor be known; not done.
- A KEV addition moves t* earlier but not the anchor, so a waiting npm fix whose urgency rises late is due at the next due slot after the new t*, not at once (within the first 36 hours after t* it is due at once).
- A fix whose wait the judge extends beyond t*, a commit whose time is older than its push, an OSV change that leaves `modified` alone, and a due slot GitHub does not run all wait for the next due slot (definitions, 5).
