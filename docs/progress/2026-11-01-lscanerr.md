# 2026-11-01 — LSCANERR: `ludion scan` keeps a newer security release when Docker Hub fails in any way, not only with a 404

**Lane LSCANERR**, from main a4610d1, for a fact error found by a first-principles audit on 2026-11-01: #246 (LSCAN404) kept the line's newer security releases only when Docker Hub answered 404 for the move's tag. When Docker Hub failed otherwise after those releases were counted (no pull token, an error status such as 429 or 5xx, no digest, a failed, timed-out or redirected request), `ludion scan` still said `unavailable`, exited 2 and did not name the security release, while both READMEs (line 123) say scan exits 1 for "a PHP or Node.js security release newer than the Dockerfile's version". Mistake: docs/mistakes/2026-11-01-scan-docker-hub-failure-dropped-security-release.md. No decision record: the wait and the choice of the version a move goes to are unchanged.

## What changed

- packages/cli/src/security/php.ts: `imageMove` wraps its call of `dockerHubTag`. With newer security releases (`fixes`), any error throws `ImageMoveStopped`, which keeps them (`security_releases`, newest first), names them first, then gives Docker Hub's error as one sentence (a trailing "No update decision was made." is not repeated, a missing full stop is added): `PHP 8.4.29 is a security release newer than 8.4.28; Docker Hub could not be checked for php:8.4.30-cli, the newest release of PHP 8.4 in the Dockerfile's variant: Docker Hub gave no digest for php:8.4.30-cli (HTTP 503). Ludion does not move the image without that check. No update decision was made.` With none, Docker Hub's error is thrown unchanged. `MissingImageTag` (the 404) is now a subclass of `ImageMoveStopped`; its reason is word for word as before.
- packages/cli/src/security/scan.ts: a failed image check keeps the releases of any `ImageMoveStopped` (before: only `MissingImageTag`), so `found()` counts it toward exit 1. `attention_required` is unchanged (a failed check already counted).
- packages/cli/src/security/cli.ts: one comment; the output path is #246's (the stop's line on standard output, without "unavailable").
- README.md and packages/cli/README.md, line 123: checked, not changed. With this fix, a scan that finds a newer security release in the official list exits 1 whatever Docker Hub answers. The failures that still exit 2 (an official list that cannot be read, a Dockerfile version newer than every listed release) happen before any security release is found, so the sentence's "finds none" holds for them.
- docs/status.md: item 4 and its date line.
- `patch` still stops in these cases (no move is decided); with a newer security release, its reason now names it before Docker Hub's error.
- Not changed: the site (apps/site), the wait table, the gates, how a move's version is chosen, and deliver.ts's own Docker Hub check.

## Tests (packages/cli/test, written first, commit 35a886d)

- scan-exit.test.ts, 36 new (18 each for PHP and Node.js). Eight Docker Hub failures as stand-ins: HTTP 503, HTTP 429 and HTTP 200 without a digest for the tag's HEAD; a failed request (`TypeError: fetch failed`, which is also what a redirect gives under `redirect: "error"`) and a timeout (`TimeoutError`) for the tag; HTTP 503, a body without a token and a failed request for the pull token.
  - With a security release between, after the other move's wait: each failure exits 1, the text line is exactly `<ecosystem>: <the stop's reason>` naming the release and Docker Hub's error, nothing says "unavailable", and the check is exactly `{ ecosystem, error, security_releases: [the release] }` with `attention_required` (8 each).
  - `scan --json` with a 503 for the tag gives exit 1, `attention_required`, the error and `security_releases` (1 each).
  - With none, after the wait: each failure exits 2 with `<ecosystem>: unavailable — <Docker Hub's error as before>` and the check is exactly `{ ecosystem, error }` (8 each).
  - With none, while the wait runs: Docker Hub is not asked and scan exits 0 (1 each).
- node-image.test.ts, 2 new: with a 503, the stop is an `ImageMoveStopped`, not a `MissingImageTag`, with the exact reason and both newer security releases; with none, it is the plain error `Docker Hub gave no digest for node:22.23.5 (HTTP 503).`, not an `ImageMoveStopped`.
- The existing tests are unchanged and pass: security.test.ts:120 ("stops when Docker Hub cannot be read") checks a part of the reason that is still there.
