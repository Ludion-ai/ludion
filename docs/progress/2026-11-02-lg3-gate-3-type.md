## The number of workers, and Next.js 16 (a fix after a review and an audit)

Next.js makes its build's workers from `CIRCLE_NODE_TOTAL` minus one or, without it, from `os.cpus()` minus one (`dist/server/config-shared.js`). It does not see the box's `--cpus 1`, and Node.js counts the machine's CPUs inside it. So on this machine's 16 CPUs the build started 15 workers in a box of 512 MiB, and what fit depended on the machine it ran on. The driver now sets `CIRCLE_NODE_TOTAL=2`, which gives one worker, after the project's `.env.example` keys, and that file cannot set it. Every run's result now holds `host_cpus`, the count Node.js gives. packages/sandbox and the box's limits are unchanged.

**Turbopack.** Next.js 16's default build writes its own cache to `.next/cache/turbopack`, about 25 MiB of the box's 64 MiB /tmp at 4 pages. Read-only is not the answer as it was for webpack: with that folder read-only, 16.4.4 stops with exit 1 within a second (`Failed to open database`). So webpack's fix was not extended to it. The driver sets `TURBO_ENGINE_READ_ONLY=1`, and Turbopack then writes none. **That name is not a public setting**: it was found in 16.4.4's native file, no document for it was read, and what is known of it is the runs below. The other switch found is `experimental.turbopackFileSystemCacheForBuild` in `next.config`. In `next build` alone at 24 pages, /tmp was 39,568 KiB with neither, 11,024 KiB with the variable and 11,020 KiB with that setting off. But it is the project's file, which the box does not change. `next build` has no flag for it. Neither value does anything on a version that does not read it: the build goes on, as next 15.5.6 did with the Turbopack one.

Measured with `next@16.4.4`, the latest on the registry on 2026-11-02 (`examples/nextjs-security-cases/next-16.4.4`), and 15.5.6: the example plus one-line pages of our own, the real driver from the code, runContainer's flags with its two scratch folders, the project from a read-only volume, no network, no Docker socket, one box at a time. **`host_cpus` or, before the fix, the same count read beside it, was 16 on every run.**

**What this does not fix or show.**

- A project's `next.config` can set its own `experimental.cpus` or `memoryBasedWorkersCount`, and those win. A project's own tests can start workers by the machine's CPUs (Jest does by default): not measured, and not changed by these values.
- If Next.js stops reading either value, nothing fails by itself, as only case (e) under `gate3-docker.test.ts` would show it, and CI does not run that. The unit tests hold that the driver sets them. They do not show that a build fits.
- One machine. A machine with other CPU counts was stood in for by a preload, on `next build` alone.
- Next.js versions other than 15.5.6, 15.5.7 and 16.4.4, third-party projects and pages heavier than one line.

## New running out of the box (a decision after the fixes above)

The rule, its threshold and the reasons' names are in the definition's Limits, committed before the code that reads them. When new's build fails, or it builds and its server does not start, new runs once more in a fresh box. An OOM kill or /tmp nearly full (under 1,048,576 bytes free at the run's lowest reading) on either run is `undecidable`, `box_resources`. A failure and then a run that builds and starts is `undecidable`, `flaky_new`. Only two failures with room in the box are `broken`. A figure that could not be read is `undecidable`, `box_figures_missing`.

**Shown by unit tests, with Docker stood in for:** gate3.test.ts's `oom-is-undecidable-not-broken`, `flaky-new-is-undecidable`, `two-failures-with-room-are-broken` and `tmp-nearly-full-is-undecidable`, on `compareRuns` and through `judgeGate3`, and `tmp-min-free` on the driver with Node.js's modules stood in for. Each of 28 changes that takes a line of this out made at least one test fail, with the unchanged code passing first.

**One real box, once.** The driver as committed, on examples/nextjs-security (next 15.5.6), with the box's flags, a read-only volume, no network and no Docker socket, `node` v24.20.0, and 62 MiB of the 64 MiB /tmp filled by `dd` before it started, so the failure was made on purpose:

| Build | Exit | Build s | ENOSPC lines | `tmp_min_free_bytes` | `memory_oom_kills` | `memory.swap.peak` | `memory.peak` | `host_cpus` |
|---|---|---|---|---|---|---|---|---|
| `failed` | 1 | 9.85 | 2 | 0 | 0 | 0 | 492,896,256 | 16 |

That output, read by the real `parseRun` and given to the real `compareRuns` as both runs of new against a run of old written by hand, gave `undecidable`, `box_resources`. **This shows that the figure is real in the box's image and how it is read. It is not a judgement:** `judgeGate3` was not run, old was not run, and one run stood for both runs of new. No real build was killed for memory under this code, a real flaky build was not seen, and `tmp_min_free_bytes` on a run that passes was not read in the box.

**What it costs.** A judgement whose new fails to build or start has one more box run. On this example a whole run was about 30 s; a run can take up to the box's timeout of 20 minutes.

**What this does not change.** Only new's build and start run again. A test that fails on new for lack of /tmp is still `broken`, and so is a page that answers nothing because the box killed the server, since neither reads these figures.

## Where the first form differs from the definition

The definition says "Only hashes, counts and levels leave the box". **Page paths leave it too**: `parseRun` takes a page's path as a string of up to 2,000 non-space characters, for up to 200 pages a run, and old's paths appear in the `broken`, `undecidable` and `notes` sentences. So a candidate can carry that much text out in a result. A page's hashes, console levels and memory figures have a shape that holds no text. The definition is fixed, so this is written here.

## How the box is kept

Nothing in packages/sandbox changed; every run goes through its `runContainer`: no network, a read-only root, no capabilities, user nobody, 1 CPU, 512 MiB, 256 processes and a 64 MiB /tmp. One box does all of a run, because /tmp goes when the box ends. `.next` and, in a TypeScript project, tsconfig.json and next-env.d.ts are links into /tmp, made when the image is built. The browser is the Chromium headless shell in Playwright's image, spoken to over a pipe, so no port opens for it and no client library is needed. It runs with Chromium's own sandbox off (`--no-sandbox`), inside the box.

Images: `mcr.microsoft.com/playwright:v1.63.0-noble@sha256:eff16c30e6f3f4af0a03fa4b706120d5e9b0891c344a27d64559aff5900a4a27` for the box, and `node:24@sha256:e7add2a490bb17d97b485b8641bd88455fff7839ade0f5eba493c3508124d413` for acquiring dependencies.
