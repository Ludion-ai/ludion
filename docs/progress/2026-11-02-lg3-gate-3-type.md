# LG3: a first form of gate 3's new type, and what one case costs (2026-11-02)

Definition, committed before any of this was built or run: docs/decisions/2026-11-02-gate-3-type-definition.md. The code is packages/cli/src/security/gate3.ts and gate3-box.ts. Nothing calls it yet, so this says nothing about what `ludion patch` does.

## What was asked and what came out

| Case on examples/nextjs-security | Expected | Result |
|---|---|---|
| (a) next 15.5.6 -> 15.5.7 | `not_broken` | `not_broken`, 4 specification pages |
| (b) lodash 3.10.1 -> 4.17.21: `/report` calls `_.pluck` | `broken` | `broken`: `/report` answered 500, 2 exceptions, 1 console error, DOM 7 elements against 17; no other page |

| (d) added: a type error the build is told to ignore, and a failing test | `not_broken`, with both seen | `not_broken`; types and tests `failed` on all three runs, and the notes say they took no part |

Case (d) was added because the types step (about 2 s) and the tests step (about 0.2 s) looked too short to be real. They fail when they should, so they run.

The pages found were `/`, `/about`, `/legacy` and `/report`, from both routers' lists. The two API routes and the dynamic route `/items/[id]` were not opened. `/report` draws the time, a random number and an id: with the clock stopped, exactly 1 of its elements (the id) differed between the two runs of old. The build passed only through `.env.example`'s dummy values: lib/env.ts stops it without them.

These ran through packages/cli/test/gate3-docker-run.ts, with stand-ins for the acquisition policy and the snapshot, since that script runs where the Docker socket is and imports no package. The real policy and snapshot on the same example are in gate3.test.ts, without Docker. **gate3-docker.test.ts, the same cases under vitest with the real ones, has not been run**: it would run vitest with the socket.

### Memory in the box

Every run's `memory.peak` was 536,870,912 bytes, packages/sandbox's limit of 512 MiB exactly. That counts the page cache, so it says little alone, and no run had an OOM kill. But each one used swap: `memory.swap.peak` was 93 MB to 221 MB in nearly all runs, and 450,080,768 bytes in one (case (a), new, with the build cache). **So the example's build does not fit in 512 MiB without swap.** A machine with no swap for the box has not been tried, and a larger project may not build at all, which is `undecidable`. packages/sandbox was not changed. Whether it should give gate 3 more memory is a question for after C4's first samples.

## The box's /tmp: webpack's cache (a fix after the measurements above)

An audit found that webpack's persistent cache fills the box's 64 MiB /tmp, so a Next.js project of a few dozen plain pages did not build, and on old that is `undecidable`. Each box is new, so that cache is written and never read. The driver now makes `/tmp/next/cache/webpack` read-only before the build (gate3-box.ts). Webpack prints a warning for each of its three compilers (`Caching failed for pack: Error: EACCES`) and goes on. Only that folder: the audit tried all of `cache`, and the build then stops on its `.tsbuildinfo`. packages/sandbox and the box's limits are unchanged, and so is the definition's table.

Measured on examples/nextjs-security (next 15.5.6) plus one-line pages of our own, with runContainer's flags from a read-only volume, no network and no Docker socket. **24 pages did not fail before the fix on this reproduction**: it built on all 3 runs, with 348 KiB of /tmp left, where the audit's 24 pages failed with ENOSPC. Why the two differ is not known; it first fails here at 26.

## How the box is kept

Nothing in packages/sandbox changed; every run goes through its `runContainer`: no network, a read-only root, no capabilities, user nobody, 1 CPU, 512 MiB, 256 processes and a 64 MiB /tmp. One box does all of a run, because /tmp goes when the box ends. `.next` and, in a TypeScript project, tsconfig.json and next-env.d.ts are links into /tmp, made when the image is built. The browser is the Chromium headless shell in Playwright's image, spoken to over a pipe, so no port opens for it and no client library is needed. It runs with Chromium's own sandbox off (`--no-sandbox`), inside the box.

Images: `mcr.microsoft.com/playwright:v1.63.0-noble@sha256:eff16c30e6f3f4af0a03fa4b706120d5e9b0891c344a27d64559aff5900a4a27` for the box, and `node:24@sha256:e7add2a490bb17d97b485b8641bd88455fff7839ade0f5eba493c3508124d413` for acquiring dependencies.
