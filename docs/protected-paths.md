# Protected paths

PRs that change any of these paths are not auto-merged (CLAUDE.md, "Every change goes through a PR"):

- agent instructions: `CLAUDE.md` and `AGENTS.md` at any depth, `.cursorrules`, `.claude/`, `.cursor/`
- `CODEOWNERS` at any depth
- `.github/`
- `tools/verify/`
- the security commands' sandbox (Docker runner, public-address fetch and the guard on starting containers): `packages/sandbox/`
- the schema: `packages/*/src/schema.ts`, `packages/*/schema/`, any `*.schema.json`
- `lessons/`
- `ludion.config.json`, `wrangler.jsonc`
- the GitHub Action users run: `action/` and the root `action.yml`
- this file, `docs/protected-paths.md`

Dependency files (`package.json`, lockfiles) outside the paths above are not protected paths, so this check does not block dependency updates. Instead, every new dependency is checked by security before it is added. Agents still never merge, or enable auto-merge on, a dependency-update PR (Dependabot, Renovate and the like), whatever its checks say, nor any PR an agent did not open (CLAUDE.md, "Every change goes through a PR").

The required check `protected-paths` (`.github/workflows/protected-paths.yml`) fails such a PR until **both** are true for the PR's current head:

- the PR has the `review-approved` label, and
- the latest review of that head approves. The check reads only comments by the repository's owner, a member or a collaborator (`author_association` `OWNER`, `MEMBER` or `COLLABORATOR`); others, bots' included, are ignored. Of those, a review of the head is a comment whose **last line** (trailing blank lines, spaces and `\r` aside) is `reviewed-sha: <full 40-character lowercase head SHA>` and nothing more; a `reviewed-sha:` line anywhere else does not count. One footer is removed before the last line is read: if the comment ends with exactly the two lines `---` and `_Generated by [Claude Code](https://claude.ai/code)_`, one after the other with only trailing spaces or `\r` after each, those two lines and any blank lines before or after them are removed. Nothing is removed when any other line follows the footer, when its two lines are apart, indented or worded otherwise, or when only one of them is there, so such a comment is no review. It approves when its **first line**, with `*`, `_` and `` ` `` read as spaces and leading spaces, `#` and `>` removed, **begins** with the word `APPROVE` and contains neither the word `NOT` nor `REQUEST`. These words match in any case. So `**APPROVE**: …` and `approve` approve; `Review of #7: APPROVE`, `do NOT APPROVE`, `APPROVE, but not yet`, `APPROVED` and `~~APPROVE~~` do not. A review that does not approve the current head, posted after one that did, fails the check again. A comment with no body is no review, and any failed API call fails the check.

## How a protected PR gets approved

1. A reviewer other than the author, with fresh context, reads the full diff at the current head and posts the review as a PR comment. Its first line begins with the verdict (`APPROVE` or `REQUEST CHANGES`), and its last line is `reviewed-sha: <head SHA it reviewed>`. Put the reasons on later lines: a first line such as `APPROVE: … (follow-up, not blocking)` has the word `not` and does not approve.
2. The owner (or 社長 on the owner's behalf) approves the merge.
3. After both, the `review-approved` label is added, with a comment naming the reviewer, the verdict comment, and who approved.

Any push changes the head SHA, so an earlier `reviewed-sha:` stops counting by itself. Steps 1 and 2 must be repeated for the new head; the label can stay, since only an approval in the latest review of the current head passes the check. Comments do not start the check, so after posting the new `reviewed-sha:` line, re-run the failed `protected-paths` run (or remove and re-add the label).

## Every review is recorded on its PR

Every review, of a protected PR or not and whatever its verdict, is posted as a comment on that PR and ends with the line `reviewed-sha: <the head SHA it reviewed>`. A review made after a merge is posted on the merged PR. A review with no such comment on GitHub is never reported as a review. For a PR that touches no protected path, a later review may cover only what changed since the last one, when it says so; a protected PR's review always reads the full diff at the current head, as above.

## What this does and does not guarantee

Every agent pushes from the same GitHub account, and GitHub does not let an account approve its own PR, so a required "Code Owner review" would block every merge. This check is therefore a **process gate, not a technical one**: anyone with write access can add the label or the comment. What it does guarantee:

- The check's definition comes from the base branch (`pull_request_target`), so a PR cannot change it to pass itself.
- The check never checks out or runs PR code, and its token can only read.
- An approval written for an older head never counts for a newer one, and a later review of the same head that does not approve undoes it.
- A comment from an account that is not the owner, a member or a collaborator neither approves nor undoes an approval. Every agent posts as the owner's account, so this keeps outside accounts out; it does not tell the agents apart.
