## What is built

Moved word for word from CLAUDE.md on 2026-10-29, where it opened the file, and kept current since: on 2026-10-29 the production/dev split was removed (docs/decisions/2026-10-29-every-change-counts-as-production.md).

What exists today is a source preview: it scans PHP Docker, npm, Composer and Maven, validates candidates offline in Docker and, only with --apply, commits each validated fix on its own Git branch (the working tree is not changed). It does not deploy production or inventory live servers.

**Not built yet** (as of 2026-10-29): gate 1's OS/SAPI/configuration matching anywhere; outside `ludion judge` and npm `ludion patch` candidates, gate 2's provenance, publisher, install-script, deprecation and withdrawal checks and the waits over every package in the lockfile diff (Composer and Maven patch receipts list them; patch checks them with rules 1 and 2 below, its OSV re-scan, which also finds MAL- records, its removal and major-version checks, and its acquisition policy's checks on where each package comes from); gate 2's inspection for obfuscated code and new network or process calls, anywhere; gate 3's check that a changed package loads, and gate 3 in `ludion judge`; gate 4's one fix per PR on GitHub (the scheduled workflow below opens one, but has run only locally against a stand-in for GitHub); the exposure-time end (when a fix reaches the project's configuration: `applied_at` is when its branch was made, and nothing merges it), Maven's `fix_published_at`, and a `found_at` from the first run that saw the fix; a project's own stricter wait (`judge()` takes one as an input, but no caller passes it and nothing reads it from the project); opening PRs on GitHub; automatic merge; and a project apply setting. Today the default only validates, and without Docker the run fails. Until each exists, do not describe the preview, its receipts or its updates as gated, waited or "passed the four gates". Update this list as they land. Built: `patch` validates each fix on its own against one baseline (a fix is every planned change of one package, or PHP's one image update): its candidate moves only that package. With --apply it commits the fix as one commit on HEAD, on its own branch (`ludion/<ecosystem>/<package>-<version>`, `ludion/php/<version>`), after checking, before any build or test (for Maven, after its dependency graph is resolved), that the project's files are HEAD's; Git runs only plumbing commands, started by absolute path from outside the project's folder, with core.hooksPath, fsmonitor, signing, replace refs and every transport turned off; a repository whose configuration names hooks (`hook.*`, which newer Git runs whatever core.hooksPath says) is refused, and so is a partial clone. A file checked out only with CRLF ends is committed with HEAD's LF ends. A branch name that holds another change stops that fix. A fix that fails is left out, with its reason in the receipt, and stops no other; a finding without a supported fix no longer stops the run (as it did before per-fix validation), but stops that package's fix, and the run ends `partial`; a fix whose branch exists is skipped. A project can validate but not apply unless it is a Git repository whose files are byte for byte those of its last commit: not with uncommitted, untracked or ignored files (a build output counts, except in the names never compared: `.git`, `.ludion`, `node_modules`, `.ssh`, `.aws` and `.env*` at any depth, and for npm, Composer and Maven the top-level `vendor`, `target`, `.npmrc`, `auth.json` and `.mvn`), an executable bit other than the commit's (not on Windows), files Git stores through a filter (Git LFS, git-crypt), a sparse checkout that leaves out project files, a symbolic link or submodule in the commit, no commit, a work tree Git places elsewhere, a partial clone, Git configuration that names hooks, refs kept in a storage other than files (reftable), objects borrowed from other folders (alternates), or a symbolic link inside `.git` where Git would write the branch. `--apply` needs `git` in one of PATH's absolute folders other than the working directory, the repository, `node_modules` folders and Yarn's shim folder, and runs it by that absolute path, so a `git` that npx, npm scripts, Composer's `vendor/bin` or a `.venv` put first on PATH never runs. Fixes that pass only together are not applied. An OSV MAL- record on an installed package stops the whole run, every fix included, before any Docker work (for Maven, after its dependency graph is resolved). After a fix's candidate, OSV must show nothing left on that package and no finding on a package version the baseline did not have, in every ecosystem: a fix that passes only together with another (Maven's commons-text, which alone brings a still-vulnerable commons-lang3) is not applied until the other is merged. Before each branch is made, Git reads back the commit, its tree and the changed files, so an object the repository already holds at the new content's id cannot stand in for it. The fixes are not validated together: branches that change the same lockfile can conflict when they are merged one after another, and each must then be made again from the new HEAD. Receipts carry fix_published_at (php.net's release day of the first newer security release, the npm registry's publish time, or Packagist's release date, which its author sets; null with the reason for Maven or when it cannot be read), found_at (this run's advisory lookup: a fix found in an earlier run is found again, so detection time is not measured yet) and applied_at (when the branch was made). Built: npm and Composer candidates are resolved for the planned packages at their smallest fixed version, and stop if any other installed version disappears; a fixed version can still bring new dependencies (receipts list every changed package). Since 2026-10-30 (LV), when an npm package's smallest fixed version is deprecated, no longer listed by the registry, or named by an OSV record (a MAL- record or an advisory), `patch` takes the next smallest version of the same major (0.x: the same minor) that the registry lists, that is not deprecated and that no OSV record names, looking at up to 50 later versions; the fix's receipt entry (`fixes[].version_choice`) lists each version passed over and why, its `changes` and branch name carry the version taken, `before.plan` keeps the smallest, and its `fix_published_at` is the version taken's publish time. Without such a version the smallest stays and the fix stops, as before; when that lookup fails, the smallest also stays, and the judge checks it as before. Composer and Maven are out of scope for this: Packagist marks a whole package abandoned, not a version, and Maven Central lists versions only, so neither has per-version deprecation to read. Maven edits only planned versions, but its transitive graph is not held fixed. Rules 1 and 2 check every version a change adds besides the fix itself, in `ludion judge` and on npm and Composer `ludion patch` candidates: it must be in the current lockfile or published before T, the fix's publish time, and a new dependency whose package first appeared less than the urgency's base wait (168h in `ludion patch`) before T stops (for Composer, both dates are Packagist's release dates, which the author sets, so a backdated release passes either rule). The same-release exception (npm registry packages, not Composer) lets a version published at or after T past rule 1 only as a target's own release: both have provenance naming the same repository, workflow and commit (each statement must name its version and tarball hash), or neither has provenance and they share the publisher account (trusted publishing's shared user never matches) and the version number, published at most 15 minutes after that target. Composer planning also reads Packagist's advisories and takes the later fix. Also built, for npm only, in `ludion judge` (comments on an existing update, changes nothing) and, since 2026-10-29 (LC), on npm `ludion patch` candidates (below): gate 2's checks and gate 1's downgrade and advisory checks on every install path whose package or version changes and on every package a dependent loads for an existing requirement that it did not load before (shadowing, moved or upgraded dependents, removed copies, aliases; a newly added requirement that lands on an already-installed copy is not compared), gate 4's file, package.json, tarball and integrity checks on every changed entry, and the waits of CLAUDE.md's wait table (exploited, high and normal). So the judge v0 is these parts of gates 1, 2 and 4, and those waits. Nothing schedules the re-query at the end of the wait: it happens only if the judge is run again then. The judge never says "apply" because it does not run gate 3. On npm, `patch` and `watch` call it (packages/cli/src/security/candidate-judge.ts): once for each fix, after that fix's time cap, the same `judge()` and the same live lookups judge the change from the project's package-lock.json to that fix's candidate (the folder its branch commit's files are read from), every package in that diff, every changed version counting as production as in `ludion judge` (docs/decisions/2026-10-29-every-change-counts-as-production.md). So a candidate waits the table's 12 to 72 hours, extended to at most 144 hours (a publisher change, a new dependency or a replaced version the registry no longer lists doubles the wait, to at least 72 hours). The baseline is built and tested once first, as before; then, for each fix, only a judgement with nothing to stop and the wait over goes on to the OSV re-scan and that candidate's build and tests; a fix whose candidate must wait fails with the time its wait ends and gets no branch, and one that stops or cannot be judged fails. Only that fix fails: the run's other fixes go on, and the run ends `failed` when every fix failed and `partial` otherwise (exit 2 either way). Each fix's entry in the receipt keeps its own judgement (`fixes[].judgement`), including what it did not check. Its `judgement.exposure` has two times: `fix_published_at`, the latest registry publish time among the versions in that fix's lockfile diff that fix an advisory OSV returned to the judge, and `detected_at`, when the judge ran, which is after the fix's `found_at` (this run's advisory lookup) and before its `applied_at` (when its branch was made). The fix's own `fix_published_at` is the latest registry publish time of its planned versions, read in a separate lookup. The two publish times are usually the same but can differ: the judge reads its own lockfile diff and OSV's answer to it, the plan comes from the run's scan, and either lookup can fail on its own (its time is then null). Neither is the exposure-time end listed above as not built. Nothing reruns the patch when a wait ends: someone runs it again, or `watch` does on its next round. Composer, Maven and PHP Docker updates do not go through the judge. The judge comments on this repository's own dependency PRs (judge.yml) and is packaged as a GitHub Action (action.yml; a preview, not released). Both read each changed `*/package.json` as data, and the judge leaves one out of gate 4's changed-files stop when it agrees with the lockfile (docs/decisions/2026-10-29-l9-workspace-package-json.md); one that does not agree stops, and one it cannot read is undecidable. Its backtests, up to v5 (docs/bench/2026-10-28-backtest-v5), do not meet the backtest gate: one malicious version is still missed (v5 also counts it as disputed) and unknowns remain. The noise rerun (docs/bench/2026-10-28-noise-v2) meets neither its count gate nor its miss gate, and neither does the count on a new sample (docs/bench/2026-10-29-l1c). Details: docs/design.md and docs/decisions/.

Not in the text above:

- **The scheduled workflow** (LB, docs/bench/2026-10-30-lb-design; preview, not released, not run on GitHub). action.yml has two more modes, and action/patch-workflow.yml is the workflow a user copies: on `schedule` (every 6 hours) and `workflow_dispatch`, on the default branch only. Its validation job (mode patch: `contents: read`, no secret, refused when it could request an OIDC token) checks out the run's commit without keeping a credential, runs `ludion patch --apply` and uploads the receipt and a Git bundle of the applied fixes' branches (`ludion deliver pack`); a failed or waiting fix fails the job (every run, until it changes), and the fixes that passed go on. Its PR job (mode pull-request: `contents: write`, `pull-requests: write`) runs no dependency code: `ludion deliver open` checks the artifact as untrusted data and refuses all of it when anything differs (the bundle's branches are exactly the receipt's applied fixes; each is one commit, by Ludion, whose only parent is the run's commit, whose branch name and whole message are the ones Ludion writes for the receipt's fix, and which changes exactly the receipt's files, each already in the base commit with the same mode, each one the plan may change, with the receipt's bytes; the manifest is exactly what `changedManifest` makes from the base for the receipt's changes; the Dockerfile changes only its FROM image, to the official PHP image of a newer release pinned by digest; composer.lock moves only the planned package (from the same archive repository and source as at the base), keeps every other as at the base apart from descriptive metadata (not notification-url), adds only packages the fixed version requires, from a pinned public archive and none a Composer plugin or installer; an npm fix carries the judge's `ready_except_build`; every value used matches a strict pattern). Composer and Maven changes must go to a higher version, Composer's from the version the base locks; for npm no other package may lose a version in package-lock.json. Then, for each fix: for Composer and Maven, OSV must list no advisory for the version moved to; for npm, the judge runs again on the base's and the fix's lockfile, and anything but `ready_except_build` fails that fix; for Composer, each lock entry that differs from the base's (apart from descriptive metadata) must say what Packagist lists for that version in every key Composer installs or runs from (dist, source, require, autoload, bin, type, extra and the like), no entry may have a key outside a fixed list, and no name may appear twice; for PHP, the pinned digest must be the one Docker Hub gives for the tag now (a lookup that fails, or a tag rebuilt in between, fails the fix); a PR from its branch (open or closed) means no new one; a branch an earlier run pushed with the same tree on the same base is reused, and any other branch of that name is left alone and the fix fails; the commit is pushed to its new branch (never forced, the token passed to Git in its environment) and one PR is opened into the default branch, its body built from the checked receipt fields (the change, the advisories, fix_published_at, found_at, applied_at, the judge's verdict for npm, and what was not checked). Not checked by the PR job: what Composer archives hold beyond Packagist's reference; Maven's transitive graph; and, in package-lock.json, fields of entries whose version does not change (such as `dev` or `bin`), which the judge does not compare. The PR body's times and advisory IDs are the validation job's receipt's, checked for form only. Between the PR job's check that a branch is absent and its push, a branch someone creates at an ancestor of the fix would be fast-forwarded (the push is never forced). Not built: the exposure-time end (the merge is not recorded); CI on these PRs (GitHub starts no workflow for a PR made with the workflow's token); rebuilding a PR whose base moved, and closing one a newer fix replaces; skipping the validation of a fix whose PR is open (each run validates it again); telling a waiting fix from a failed one in the job's result. A candidate that escaped the sandbox in the validation job would be on a runner that can write the repository's Actions caches. GitHub's schedule can be hours late (on 2026-10-29 the shadow's hourly schedule did not fire for five hours).

- Every changed version counts as production in `ludion judge` and in npm `ludion patch`: no dependency is told apart as dev-only, and there is no 7-day wait.
- `ludion scan` also reads Python, Go and Rust projects, read-only: it reports known advisories and plans or applies nothing (README, "Read-only scans").
- What `ludion judge` sends: package names and versions to OSV and the npm registry, and the IDs of the advisories OSV returns back to OSV. No CVE ID is sent and no source is sent. It downloads CISA's catalog of exploited vulnerabilities whole, and, when a fix has a CVE ID, FIRST's daily list of EPSS scores whole, and looks the CVE IDs up in them (docs/decisions/2026-10-29-epss-downloaded-whole.md). The EPSS list comes from the one URL first.org/epss/data gives (epss.empiricalsecurity.com). It follows at most one redirect, and only to a file on the same host named for a day (`epss_scores-YYYY-MM-DD.csv.gz`); any day's name is accepted, not only today's. The list is at most 16 MiB compressed and 64 MiB expanded, and must arrive within 120 seconds; a list that cannot be downloaded, has a score_date that is not a date, or has any line that is not a score makes the judgement undecidable. The list's own score_date (its first line) is shown in the judgement and its JSON (`epss_date` on each fix with a CVE ID; null when the list gives none). An old list is used, not refused. `ludion patch` and `watch` send and download the same for each npm fix's candidate, through the judge: a run with several npm fixes downloads CISA's catalog (when the fix's diff fixes an advisory) and the EPSS list (when one of those has a CVE ID) once per fix, and nothing keeps them between fixes or rounds. The urgency rule is unchanged (an EPSS of 0.1 or more is high), and of a fix's CVE IDs the highest score counts.

## Missing before complete (working list)

A proposal from the owner's Claude chat, to be fixed with the owner (CLAUDE.md, Goal). Each item is something the Goal needs that "What is built" says is not there.

1. **Runs without being asked.** `scan` and `patch` run when someone runs them, and `watch` repeats only in a foreground terminal. The scheduled workflow (above) runs `patch --apply` every 6 hours in a user's repository and opens PRs, but it has run only locally against a stand-in for GitHub, not on GitHub, and nothing is released. GitHub's schedule can be hours late or skip runs.
2. **Delivers each fix as a PR.** One fix per PR (gate 4), with a receipt that carries the exposure-time timestamps, and a project apply setting. Today `--apply` validates each fix alone and commits it on its own branch, with fix_published_at, found_at and applied_at in its receipt, and the scheduled workflow's PR job opens one PR per fix (not run on GitHub yet). Missing: the exposure-time end (the merge is not recorded), found_at from the first run that saw the fix rather than the run's lookup, a project apply setting, and CI on Ludion's PRs.
3. **All four gates on Ludion's own updates.** `patch` and `watch` call the judge's checks on each npm fix's candidate only (gates 1, 2 and 4 as the judge has them, and the waits); Composer, Maven and PHP Docker updates do not go through them. Outside `ludion judge` and npm `patch`: gate 2's provenance, publisher, install-script, deprecation and withdrawal checks, and the waits. Everywhere: gate 1's OS/SAPI/configuration matching, gate 2's inspection for obfuscated code and new network or process calls, gate 3's check that a changed package loads, and the re-query when a wait ends. While an npm fix waits, each `watch` round (every 900 seconds by default) builds and tests the baseline again, judges each npm fix again, downloading KEV and the EPSS list whole once per fix per round (as above), and writes a new receipt (27,867 bytes in docs/bench/2026-10-29-lc-gate2-patch's run, which stopped), so a 72-hour wait leaves at most about 288 receipts (watch waits its interval after each round ends).
4. **Runtimes and images beyond PHP.** Node.js and other runtime releases, and base images. PHP in Docker is the only runtime today (README: "runtime upgrades beyond PHP ... remain unsupported").
5. **The measurement gates the owner picks.** The design's gates are a backtest, a noise measurement and five users for two weeks (docs/design.md, ロードマップと検証ゲート). Which of them "complete" requires is the owner's call.

## Waiting for the owner

Decided on 2026-10-29: every changed version counts as production (docs/decisions/2026-10-29-every-change-counts-as-production.md), and EPSS scores are downloaded whole (docs/decisions/2026-10-29-epss-downloaded-whole.md).

1. **What "complete" means.** The working list above is a proposal.
2. **Shorter waits for official runtime releases.** The owner's point (2026-10-29): once a fix is public the race is short. Whether a fix from a runtime's own official channel (php.net, the official Docker image) waits less than the table says changes the wait table, so it is the owner's.
3. **Gates and learned models.** The owner, 2026-10-29 18:24 JST: 「ニューラルネットワーク式にやったらいいじゃない？関門は全てアルゴで まぁ設計はまた後で深掘りする」. Taken for now as: improve the way of working like training, each mistake fed back into a rule or a check, and every checkpoint as code (docs/decisions/2026-10-29-way-of-working.md). Whether any of Ludion's gates should use a learned model is for the design deep-dive. A note for it from the Claude chat: a learned score could add a reason to wait or to notify, but should not lift a stop, because a release can be tuned against a model and a receipt has to say why.
4. **The design.** docs/design.md's roadmap puts the judge first, and its open decision on where to start says 「推奨は判定役から」; the Goal now wins over both, and the owner redoes the design.
5. **The shadow's dev-only row.** The replay still judges each captured version in a dev-only row at 168h, which the wait table no longer has, and (b) is counted on all four rows as fixed before the shadow started (docs/decisions/2026-10-29-shadow-counting.md). Whether (b)'s count drops that row is the owner's call.
