## What is built

Moved word for word from CLAUDE.md on 2026-10-29, where it opened the file, and kept current since: on 2026-10-29 the production/dev split was removed (docs/decisions/2026-10-29-every-change-counts-as-production.md).

What exists today is a source preview: it scans PHP Docker, npm, Composer and Maven, validates candidates offline in Docker and updates source dependency files only with --apply. It does not deploy production or inventory live servers.

**Not built yet** (as of 2026-10-29): gate 1's OS/SAPI/configuration matching anywhere; outside `ludion judge` and npm `ludion patch` candidates, gate 2's provenance, publisher, install-script, deprecation and withdrawal checks and the waits over every package in the lockfile diff (Composer and Maven patch receipts list them; patch checks them with rules 1 and 2 below, its OSV re-scan, which also finds MAL- records, its removal and major-version checks, and its acquisition policy's checks on where each package comes from); gate 2's inspection for obfuscated code and new network or process calls, anywhere; gate 3's check that a changed package loads, and gate 3 in `ludion judge`; gate 4's one fix per commit or PR (one apply writes every planned fix); exposure-time timestamps in receipts; a project's own stricter wait (`judge()` takes one as an input, but no caller passes it and nothing reads it from the project); opening PRs; automatic merge; and a project apply setting. Today the default only validates, and without Docker the run fails. Until each exists, do not describe the preview, its receipts or its updates as gated, waited or "passed the four gates". Update this list as they land. Built: npm and Composer candidates are resolved for the planned packages at their smallest fixed version, and stop if any other installed version disappears; a fixed version can still bring new dependencies (receipts list every changed package). Maven edits only planned versions, but its transitive graph is not held fixed. Rules 1 and 2 check every version a change adds besides the fix itself, in `ludion judge` and on npm and Composer `ludion patch` candidates: it must be in the current lockfile or published before T, the fix's publish time, and a new dependency whose package first appeared less than the urgency's base wait (168h in `ludion patch`) before T stops (for Composer, both dates are Packagist's release dates, which the author sets, so a backdated release passes either rule). The same-release exception (npm registry packages, not Composer) lets a version published at or after T past rule 1 only as a target's own release: both have provenance naming the same repository, workflow and commit (each statement must name its version and tarball hash), or neither has provenance and they share the publisher account (trusted publishing's shared user never matches) and the version number, published at most 15 minutes after that target. Composer planning also reads Packagist's advisories and takes the later fix. Also built, for npm only, in `ludion judge` (comments on an existing update, changes nothing) and, since 2026-10-29 (LC), on npm `ludion patch` candidates (below): gate 2's checks and gate 1's downgrade and advisory checks on every install path whose package or version changes and on every package a dependent loads for an existing requirement that it did not load before (shadowing, moved or upgraded dependents, removed copies, aliases; a newly added requirement that lands on an already-installed copy is not compared), gate 4's file, package.json, tarball and integrity checks on every changed entry, and the waits of CLAUDE.md's wait table (exploited, high and normal). So the judge v0 is these parts of gates 1, 2 and 4, and those waits. Nothing schedules the re-query at the end of the wait: it happens only if the judge is run again then. The judge never says "apply" because it does not run gate 3. On npm, `patch` and `watch` call it (packages/cli/src/security/candidate-judge.ts): after the time cap, the same `judge()` and the same live lookups judge the change from the project's package-lock.json to the candidate's, every package in that diff, every changed version counting as production as in `ludion judge` (docs/decisions/2026-10-29-every-change-counts-as-production.md). So a candidate waits the table's 12 to 72 hours, extended to at most 144 hours (a publisher change or a new dependency doubles the wait, to at least 72 hours). The baseline is built and tested first, as before; then only a judgement with nothing to stop and the wait over goes on to the candidate's build and tests; a candidate that must wait fails with the time its wait ends and nothing applied, and one that stops or cannot be judged fails. The receipt keeps the judgement (`judgement`), including what it did not check. Its `judgement.exposure` holds the fix's publish time and the time the judge ran; it is not the exposure-time record listed above as not built. Nothing reruns the patch when a wait ends: someone runs it again, or `watch` does on its next round. Composer, Maven and PHP Docker updates do not go through the judge. The judge comments on this repository's own dependency PRs (judge.yml) and is packaged as a GitHub Action (action.yml; a preview, not released). Both read each changed `*/package.json` as data, and the judge leaves one out of gate 4's changed-files stop when it agrees with the lockfile (docs/decisions/2026-10-29-l9-workspace-package-json.md); one that does not agree stops, and one it cannot read is undecidable. Its backtests, up to v5 (docs/bench/2026-10-28-backtest-v5), do not meet the backtest gate: one malicious version is still missed (v5 also counts it as disputed) and unknowns remain. The noise rerun (docs/bench/2026-10-28-noise-v2) meets neither its count gate nor its miss gate, and neither does the count on a new sample (docs/bench/2026-10-29-l1c). Details: docs/design.md and docs/decisions/.

Not in the text above:

- Every changed version counts as production in `ludion judge` and in npm `ludion patch`: no dependency is told apart as dev-only, and there is no 7-day wait.
- `ludion scan` also reads Python, Go and Rust projects, read-only: it reports known advisories and plans or applies nothing (README, "Read-only scans").
- What `ludion judge` sends: package names and versions to OSV and the npm registry, and the IDs of the advisories OSV returns back to OSV. No CVE ID is sent and no source is sent. It downloads CISA's catalog of exploited vulnerabilities whole, and, when a fix has a CVE ID, FIRST's daily list of EPSS scores whole, and looks the CVE IDs up in them (docs/decisions/2026-10-29-epss-downloaded-whole.md). The EPSS list comes from the one URL first.org/epss/data gives (epss.empiricalsecurity.com), following only its redirect to that day's file on the same host, at most 16 MiB compressed and 64 MiB expanded, within 120 seconds; a list that cannot be downloaded or has any line that is not a score makes the judgement undecidable. `ludion patch` and `watch` send and download the same for each npm candidate, through the judge. The urgency rule is unchanged (an EPSS of 0.1 or more is high).

## Missing before complete (working list)

A proposal from the owner's Claude chat, to be fixed with the owner (CLAUDE.md, Goal). Each item is something the Goal needs that "What is built" says is not there.

1. **Runs without being asked.** `scan` and `patch` run when someone runs them, and `watch` repeats only in a foreground terminal. Nothing watches a project's official sources on its own (on a schedule, in an Action or as an agent) and acts when a fix appears.
2. **Delivers each fix as a PR.** One fix per PR (gate 4), with a receipt that carries the exposure-time timestamps, and a project apply setting. Today `--apply` edits the source files in place, and one apply writes every planned fix.
3. **All four gates on Ludion's own updates.** `patch` and `watch` call the judge's checks on npm candidates only (gates 1, 2 and 4 as the judge has them, and the waits); Composer, Maven and PHP Docker updates do not go through them. Outside `ludion judge` and npm `patch`: gate 2's provenance, publisher, install-script, deprecation and withdrawal checks, and the waits. Everywhere: gate 1's OS/SAPI/configuration matching, gate 2's inspection for obfuscated code and new network or process calls, gate 3's check that a changed package loads, and the re-query when a wait ends. While an npm candidate waits, each `watch` round (every 900 seconds by default) builds and tests the baseline again, reads the facts again (KEV downloaded whole each time) and writes a new receipt (27,867 bytes in docs/bench/2026-10-29-lc-gate2-patch's run, which stopped), so a 72-hour wait leaves at most about 288 receipts (watch waits its interval after each round ends).
4. **Runtimes and images beyond PHP.** Node.js and other runtime releases, and base images. PHP in Docker is the only runtime today (README: "runtime upgrades beyond PHP ... remain unsupported").
5. **The measurement gates the owner picks.** The design's gates are a backtest, a noise measurement and five users for two weeks (docs/design.md, ロードマップと検証ゲート). Which of them "complete" requires is the owner's call.

## Waiting for the owner

Decided on 2026-10-29: every changed version counts as production (docs/decisions/2026-10-29-every-change-counts-as-production.md), and EPSS scores are downloaded whole (docs/decisions/2026-10-29-epss-downloaded-whole.md).

1. **What "complete" means.** The working list above is a proposal.
2. **Shorter waits for official runtime releases.** The owner's point (2026-10-29): once a fix is public the race is short. Whether a fix from a runtime's own official channel (php.net, the official Docker image) waits less than the table says changes the wait table, so it is the owner's.
3. **Gates and learned models.** The owner, 2026-10-29 18:24 JST: 「ニューラルネットワーク式にやったらいいじゃない？関門は全てアルゴで まぁ設計はまた後で深掘りする」. Taken for now as: improve the way of working like training, each mistake fed back into a rule or a check, and every checkpoint as code (docs/decisions/2026-10-29-way-of-working.md). Whether any of Ludion's gates should use a learned model is for the design deep-dive. A note for it from the Claude chat: a learned score could add a reason to wait or to notify, but should not lift a stop, because a release can be tuned against a model and a receipt has to say why.
4. **The design.** docs/design.md's roadmap puts the judge first, and its open decision on where to start says 「推奨は判定役から」; the Goal now wins over both, and the owner redoes the design.
5. **The shadow's dev-only row.** The replay still judges each captured version in a dev-only row at 168h, which the wait table no longer has, and (b) is counted on all four rows as fixed before the shadow started (docs/decisions/2026-10-29-shadow-counting.md). Whether (b)'s count drops that row is the owner's call.
