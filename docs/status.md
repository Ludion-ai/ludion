## What is built

Moved word for word from CLAUDE.md on 2026-10-29, where it opened the file.

What exists today is a source preview: it scans PHP Docker, npm, Composer and Maven, validates candidates offline in Docker and, only with --apply, commits each validated fix on its own Git branch (the working tree is not changed). It does not deploy production or inventory live servers.

**Not built yet** (as of 2026-10-29): gate 1's OS/SAPI/configuration matching anywhere, and outside `ludion judge` its production/dev split; outside `ludion judge`, gate 2's provenance, publisher, install-script, deprecation and withdrawal checks and the waits over every package in the lockfile diff (patch receipts list them; patch checks them with rules 1 and 2 below, its OSV re-scan, which also finds MAL- records, its removal and major-version checks, and its acquisition policy's checks on where each package comes from); gate 2's inspection for obfuscated code and new network or process calls, anywhere; gate 3's check that a changed package loads, and gate 3 in `ludion judge`; gate 4's one fix per PR (nothing opens a PR); a project's own stricter wait (`judge()` takes one as an input, but no caller passes it and nothing reads it from the project); opening PRs; automatic merge; and a project apply setting. Today the default only validates, and without Docker the run fails. Until each exists, do not describe the preview, its receipts or its updates as gated, waited or "passed the four gates". Update this list as they land. Built: `patch` validates each fix on its own against one baseline (a fix is every planned change of one package, or PHP's one image update): its candidate moves only that package. With --apply it commits the fix as one commit on HEAD, on its own branch (`ludion/<ecosystem>/<package>-<version>`, `ludion/php/<version>`), after checking, before any Docker work, that the project's files are HEAD's; Git runs only plumbing commands, with the repository's hooks, fsmonitor and signing turned off. A fix that fails is left out, with its reason in the receipt, and stops no other; a fix whose branch exists is skipped. A project that is not in a Git repository can validate but not apply. Receipts carry fix_published_at (php.net's release day of the first newer security release, the npm registry's publish time, or Packagist's release date, which its author sets; null with the reason for Maven or when it cannot be read), found_at (this run's advisory lookup: a fix found in an earlier run is found again, so detection time is not measured yet) and applied_at (when the branch was made). Built: npm and Composer candidates are resolved for the planned packages at their smallest fixed version, and stop if any other installed version disappears; a fixed version can still bring new dependencies (receipts list every changed package). Maven edits only planned versions, but its transitive graph is not held fixed. Rules 1 and 2 check every version a change adds besides the fix itself, in `ludion judge` and on npm and Composer `ludion patch` candidates: it must be in the current lockfile or published before T, the fix's publish time, and a new dependency whose package first appeared less than the urgency's base wait (168h in `ludion patch`) before T stops (for Composer, both dates are Packagist's release dates, which the author sets, so a backdated release passes either rule). The same-release exception (npm registry packages, not Composer) lets a version published at or after T past rule 1 only as a target's own release: both have provenance naming the same repository, workflow and commit (each statement must name its version and tarball hash), or neither has provenance and they share the publisher account (trusted publishing's shared user never matches) and the version number, published at most 15 minutes after that target. Composer planning also reads Packagist's advisories and takes the later fix. Also built, for npm only and only in `ludion judge` (comments on an existing update, changes nothing): gate 2's checks and gate 1's downgrade and advisory checks on every install path whose package or version changes and on every package a dependent loads for an existing requirement that it did not load before (shadowing, moved or upgraded dependents, removed copies, aliases; a newly added requirement that lands on an already-installed copy is not compared), gate 1's production/dev split for urgency (it leaves out only a copy it can show dev-only: a test runner, linter, formatter or `@types` package, or, with `--source <dir>`, one the source, the build and the production image do not use), gate 4's file, package.json, tarball and integrity checks on every changed entry, and the waits of the design's wait table (not its weekly batching). So the judge v0 is these parts of gates 1, 2 and 4, and those waits. Nothing schedules the re-query at the end of the wait: it happens only if the judge is run again then. The judge never says "apply" because it does not run gate 3, and `patch`/`watch` do not call it yet. The judge comments on this repository's own dependency PRs (judge.yml, with no `--source`) and is packaged as a GitHub Action (action.yml; a preview, not released). Both read each changed `*/package.json` as data, and the judge leaves one out of gate 4's changed-files stop when it agrees with the lockfile (docs/decisions/2026-10-29-l9-workspace-package-json.md); one that does not agree stops, and one it cannot read is undecidable. Its backtests, up to v5 (docs/bench/2026-10-28-backtest-v5), do not meet the backtest gate: one malicious version is still missed (v5 also counts it as disputed) and unknowns remain. The noise rerun (docs/bench/2026-10-28-noise-v2) meets neither its count gate nor its miss gate, and neither does the count on a new sample (docs/bench/2026-10-29-l1c). Details: docs/design.md and docs/decisions/.

Not in the text above:

- `ludion scan` also reads Python, Go and Rust projects, read-only: it reports known advisories and plans or applies nothing (README, "Read-only scans").
- What `ludion judge` sends: package names and versions to OSV and the npm registry, the IDs of the advisories OSV returns back to OSV, and their CVE IDs to FIRST's EPSS service. It downloads CISA's catalog of exploited vulnerabilities whole. No source is sent. CLAUDE.md's rule says OSV gets package names and versions only; the two lookups by ID are an open decision below.

## Missing before complete (working list)

A proposal from the owner's Claude chat, to be fixed with the owner (CLAUDE.md, Goal). Each item is something the Goal needs that "What is built" says is not there.

1. **Runs without being asked.** `scan` and `patch` run when someone runs them, and `watch` repeats only in a foreground terminal. Nothing watches a project's official sources on its own (on a schedule, in an Action or as an agent) and acts when a fix appears.
2. **Delivers each fix as a PR.** One fix per PR (gate 4), with a receipt that carries the exposure-time timestamps, and a project apply setting. Today `--apply` validates each fix alone and commits it on its own branch, with fix_published_at, found_at and applied_at in its receipt; nothing opens the PR, found_at is the run's lookup rather than the first one that saw the fix, and there is no project apply setting.
3. **All four gates on Ludion's own updates.** `patch` and `watch` do not call the judge's checks. Outside `ludion judge`: gate 1's production/dev split, gate 2's provenance, publisher, install-script, deprecation and withdrawal checks, and the waits. Everywhere: gate 1's OS/SAPI/configuration matching, gate 2's inspection for obfuscated code and new network or process calls, gate 3's check that a changed package loads, and the re-query when a wait ends.
4. **Runtimes and images beyond PHP.** Node.js and other runtime releases, and base images. PHP in Docker is the only runtime today (README: "runtime upgrades beyond PHP ... remain unsupported").
5. **The measurement gates the owner picks.** The design's gates are a backtest, a noise measurement and five users for two weeks (docs/design.md, ロードマップと検証ゲート). Which of them "complete" requires is the owner's call.

## Waiting for the owner

1. **What "complete" means.** The working list above is a proposal.
2. **Gate 1's dev-only split in `ludion judge`.** Held from the 2026-10-29 11:29 review: count every changed version as production, because the noise measurement's miss gate was not met (docs/bench/2026-10-28-noise-v2) and the count gate was not met on a new sample either (docs/bench/2026-10-29-l1c). The trade: with the split, a shipped dependency wrongly shown dev-only waits 7 days at lower priority; without it, a real dev-only update waits 12 to 72 hours instead of 7 days. This changes gate 1, so it waits for the owner. A draft of the change (one WIP commit, on top of the guard and a publish.yml fix) is on the branch claude/split-and-rules, not opened as a PR.
3. **Shorter waits for official runtime releases.** The owner's point (2026-10-29): once a fix is public the race is short. Whether a fix from a runtime's own official channel (php.net, the official Docker image) waits less than the table says changes the wait table, so it is the owner's.
4. **The judge's lookups by ID.** Keep fetching OSV advisories by ID and sending their CVE IDs to FIRST's EPSS service, and write that into CLAUDE.md's rule, or stop.
5. **Gates and learned models.** The owner, 2026-10-29 18:24 JST: 「ニューラルネットワーク式にやったらいいじゃない？関門は全てアルゴで まぁ設計はまた後で深掘りする」. Taken for now as: improve the way of working like training, each mistake fed back into a rule or a check, and every checkpoint as code (docs/decisions/2026-10-29-way-of-working.md). Whether any of Ludion's gates should use a learned model is for the design deep-dive. A note for it from the Claude chat: a learned score could add a reason to wait or to notify, but should not lift a stop, because a release can be tuned against a model and a receipt has to say why.
6. **The design.** docs/design.md's roadmap puts the judge first, and its open decision on where to start says 「推奨は判定役から」; the Goal now wins over both, and the owner redoes the design.
