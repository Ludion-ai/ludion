## What is built

Moved word for word from CLAUDE.md on 2026-10-29, where it opened the file, and kept current since: on 2026-10-29 the production/dev split was removed (docs/decisions/2026-10-29-every-change-counts-as-production.md).

What exists today is a source preview: it scans PHP and Node.js Docker images, npm, Composer and Maven (Maven read-only, below), validates candidates offline in Docker and, only with --apply, commits each validated fix on its own Git branch (the working tree is not changed). It does not deploy production or inventory live servers.

**Not built yet** (as of 2026-10-29): gate 1's OS/SAPI/configuration matching anywhere; outside `ludion judge` and npm `ludion patch` candidates, gate 2's provenance, publisher, install-script, deprecation and withdrawal checks and the waits over every package in the lockfile diff (Composer patch receipts list them; patch checks them with rules 1 and 2 below, its OSV re-scan, which also finds MAL- records, its removal and major-version checks, and its acquisition policy's checks on where each package comes from); gate 2's inspection for obfuscated code and new network or process calls, anywhere (since 2026-11-02 not part of v1, CLAUDE.md, gate 2, and so no longer something v1 waits for); gate 3's check that a changed package loads, and gate 3 in `ludion judge`; gate 4's one fix per PR on GitHub beyond trials (the scheduled workflow below opened one PR for each of two fixes on GitHub, in one run by hand of each of two copies in a private trial repository on 2026-10-30; that day six copies there in all, ludion-npm, ludion-php and ludion-ci-a to ludion-ci-d, had run and opened PRs 1 to 6, docs/bench/2026-10-31-lb2b2; on 2026-11-03, at main 3d143fe, one more copy's first run by hand opened one PR for its one npm fix, and its second opened none, because the check job answered that the open PR fixes it and the other two jobs were skipped, docs/progress/2026-11-03-ltrial-two-runs.md); the exposure-time end (when a fix reaches the project's configuration: `applied_at` is when its branch was made, and nothing merges it), and a `found_at` from the first run that saw the fix; a project's own stricter wait (`judge()` takes one as an input, but no caller passes it and nothing reads it from the project); the PR job's check that an npm lock entry's flags are the ones npm computes from the lock's graph (an entry the fix does not move may change its `dev`, `optional`, `devOptional` or `peer`, so a forged artifact can have a production install take a package the base locks for development only, or leave a production one out; no new code comes in, since version, resolved and integrity stay the base's; docs/decisions/2026-10-31-lock-flags-only.md; the graph-computed flags are a separate lane, docs/decisions/2026-10-31-lock-flags-from-graph.md, section 2; since #240 gate 2 gives an entry whose flags alone changed its checks of that version, OSV's MAL- records and advisories, deprecation and withdrawal, and nothing else, docs/decisions/2026-10-31-flag-only-entries-gate2.md); a released way to open PRs on GitHub (the scheduled workflow is an unreleased preview); automatic merge; and a project apply setting. Today the default only validates, and without Docker the run fails. Until each exists, do not describe the preview, its receipts or its updates as gated, waited or "passed the four gates". Update this list as they land. Built: `patch` validates each fix on its own against one baseline (a fix is every planned change of one package, or PHP's or Node.js's one image update): its candidate moves only that package. With --apply it commits the fix as one commit on HEAD, on its own branch (`ludion/<ecosystem>/<package>-<version>`, `ludion/php/<version>`, `ludion/node/<version>`; since LB2a the name ends with a hash of the fix when a folder, a name that cleaning changes, several versions or a version with "-" could make two fixes' names alike), after checking, before any build or test (for Maven, after its dependency graph is resolved), that the project's files are HEAD's; Git runs only plumbing commands, started by absolute path from outside the project's folder, with core.hooksPath, fsmonitor, signing, replace refs and every transport turned off; a repository whose configuration names hooks (`hook.*`, which newer Git runs whatever core.hooksPath says) is refused, and so is a partial clone. A file checked out only with CRLF ends is committed with HEAD's LF ends. A branch name that holds another change stops that fix. A fix that fails is left out, with its reason in the receipt, and stops no other; a finding without a supported fix no longer stops the run (as it did before per-fix validation), but stops that package's fix, and the run ends `partial`; a fix whose branch exists is skipped. A project can validate but not apply unless it is a Git repository whose files are byte for byte those of its last commit: not with uncommitted, untracked or ignored files (a build output counts, except in the names never compared: `.git`, `.ludion`, `node_modules`, `.ssh`, `.aws` and `.env*` at any depth, and for npm, Composer and Maven the top-level `vendor`, `target`, `.npmrc`, `auth.json` and `.mvn`), an executable bit other than the commit's (not on Windows), files Git stores through a filter (Git LFS, git-crypt), a sparse checkout that leaves out project files, a symbolic link or submodule in the commit, no commit, a work tree Git places elsewhere, a partial clone, Git configuration that names hooks, refs kept in a storage other than files (reftable), objects borrowed from other folders (alternates), or a symbolic link inside `.git` where Git would write the branch. `--apply` needs `git` in one of PATH's absolute folders other than the working directory, the repository (under each spelling of its path; on Windows also as the system resolves it, through subst drives and short names), `node_modules` folders and Yarn's shim folder, and runs it by that absolute path, so a `git` that npx, npm scripts, Composer's `vendor/bin` or a `.venv` put first on PATH never runs. Fixes that pass only together are not applied. An OSV MAL- record on an installed package stops the whole run, every fix included, before any Docker work (for Maven, after its dependency graph is resolved). After a fix's candidate, OSV must show nothing left on that package and no finding on a package version the baseline did not have, in every ecosystem: a fix that passes only together with another (Maven's commons-text, which alone brings a still-vulnerable commons-lang3) is not applied until the other is merged. Before each branch is made, Git reads back the commit, its tree and the changed files, so an object the repository already holds at the new content's id cannot stand in for it. The fixes are not validated together: branches that change the same lockfile can conflict when they are merged one after another, and each must then be made again from the new HEAD. Receipts carry fix_published_at (php.net's release day of the first newer security release, nodejs.org's day of the first newer security release of the line, the npm registry's publish time, or Packagist's release date, which its author sets; null with the reason for Maven or when it cannot be read), found_at (this run's advisory lookup: a fix found in an earlier run is found again, so detection time is not measured yet) and applied_at (when the branch was made). Built: npm and Composer candidates are resolved for the planned packages at their smallest fixed version. A Composer candidate stops if any other installed version disappears; since LOLD2 an npm candidate stops if a path moves although every package that loads it still takes its old version, or goes away while something that stays loaded it (the oldest version in range, below). A fixed version can still bring new dependencies (receipts list every changed package). Since 2026-10-30 (LV), when an npm package's smallest fixed version is deprecated, no longer listed by the registry, or named by an OSV record that is not a MAL- record (a MAL- record on it stops the fix, below), `patch` takes the next smallest stable version (not a prerelease) of the same major (0.x: the same minor) that the registry lists, that is not deprecated and that no OSV record names (a record OSV marks withdrawn does not count), looking at up to 50 later versions, and asking OSV about them only when the smallest cannot be used; the fix's receipt entry (`fixes[].version_choice`) lists each version passed over and why, its `changes` and branch name carry the version taken, `before.plan` keeps the smallest, and its `fix_published_at`, which is also the T of the time cap's rules 1 and 2, is the latest publish time among the fix's planned versions, the version taken included (with two changes of one package in a fix, that can be the change that was not replaced). Since 2026-10-30 (LV3, docs/decisions/2026-10-30-next-fix-same-publisher.md), the version taken must come from the same publisher as the smallest it passes over: both with provenance from the same repository, workflow and GitHub repository id (the commit is not compared; the id as below), or neither with provenance and the same publisher account (trusted publishing's shared user never matches); anything else (another account, repository or workflow, provenance on one side only, a smallest the registry no longer lists, a read of the two releases' publisher or provenance that fails) stops that fix at gate 2 before any build or test, with what was compared in `version_choice` and the fix's reason. A takeover that publishes from the same account, or through the same repository and workflow (by push, release or workflow_dispatch), still passes; only the wait and the re-query catch it. Since 2026-10-30 (LV5, docs/decisions/2026-10-30-mal-smallest-stops-the-fix.md), a smallest fixed version that OSV names in a MAL- record it does not mark withdrawn stops that fix at gate 2 before any build or test, whatever else names it or is true of it (another record, a deprecation, no longer listed): no later version is looked at or compared, and `version_choice` has `chosen: null`, the MAL- ids in `malicious`, and every reason found; OSV is now asked about the smallest even when it is deprecated or no longer listed. A later version with a MAL- record is passed over, as before. In a fix with two smallest fixed versions of one package (two installed copies), the first stop, for a MAL- record or the publisher check, ends that fix's lookups, and its `changes` keep every smallest. Here, as in the judge, a record counts as MAL- by its own id: one whose id is not MAL- but whose aliases name a MAL- id is read as an ordinary advisory, so the next version can be taken, while the run-wide check on installed packages counts such an alias; bringing the two readings in line waits for a decision. Without such a version the smallest stays and the fix stops, as before; when that lookup fails (a registry or OSV answer that cannot be read included), the smallest also stays, and the judge checks it as before. Composer and Maven are out of scope for this: Packagist marks a whole package abandoned, not a version, and Maven Central lists versions only, so neither has per-version deprecation to read. Maven edits only planned versions, but its transitive graph is not held fixed. Rules 1 and 2 check every version a change adds besides the fix itself, in `ludion judge` and on npm and Composer `ludion patch` candidates: it must be in the current lockfile or published before T, the fix's publish time, and a new dependency whose package first appeared less than the urgency's base wait (168h in `ludion patch`) before T stops (for Composer, both dates are Packagist's release dates, which the author sets, so a backdated release passes either rule). The same-release exception (npm registry packages, not Composer) lets a version published at or after T past rule 1 only as a target's own release: both have provenance naming the same repository, workflow, commit and GitHub repository id (as below; each statement must name its version and tarball hash), or neither has provenance and they share the publisher account (trusted publishing's shared user never matches) and the version number, published at most 15 minutes after that target. Composer planning also reads Packagist's advisories and takes the later fix. Also built, for npm only, in `ludion judge` (comments on an existing update, changes nothing) and, since 2026-10-29 (LC), on npm `ludion patch` candidates (below): gate 2's checks and gate 1's downgrade and advisory checks on every install path whose package or version changes and on every package a dependent loads for an existing requirement that it did not load before (shadowing, moved or upgraded dependents, removed copies, aliases; a newly added requirement that lands on an already-installed copy is not compared), gate 4's file, package.json, tarball and integrity checks on every changed entry, and the waits of CLAUDE.md's wait table (exploited, high and normal). So the judge v0 is these parts of gates 1, 2 and 4, and those waits. Nothing schedules the re-query at the end of the wait: it happens only if the judge is run again then. The judge never says "apply" because it does not run gate 3. On npm, `patch` and `watch` call it (packages/cli/src/security/candidate-judge.ts): once for each fix, after that fix's time cap, the same `judge()` and the same live lookups judge the change from the project's package-lock.json to that fix's candidate (the folder its branch commit's files are read from), every package in that diff, every changed version counting as production as in `ludion judge` (docs/decisions/2026-10-29-every-change-counts-as-production.md). So a candidate waits the table's 12 to 72 hours, extended to at most 144 hours (a publisher change, a new dependency or a replaced version the registry no longer lists doubles the wait, to at least 72 hours). The baseline is built and tested once first, as before; then, for each fix, only a judgement with nothing to stop and the wait over goes on to the OSV re-scan and that candidate's build and tests; a fix whose candidate must wait fails with the time its wait ends and gets no branch, and one that stops or cannot be judged fails. Only that fix fails: the run's other fixes go on, and the run ends `failed` when every fix failed and `partial` otherwise (exit 2 either way). Each fix's entry in the receipt keeps its own judgement (`fixes[].judgement`), including what it did not check. Its `judgement.exposure` has two times: `fix_published_at`, the latest registry publish time among the versions in that fix's lockfile diff that fix an advisory OSV returned to the judge, and `detected_at`, when the judge ran, which is after the fix's `found_at` (this run's advisory lookup) and before its `applied_at` (when its branch was made). The fix's own `fix_published_at` is the latest registry publish time of its planned versions, read in a separate lookup. The two publish times are usually the same but can differ: the judge reads its own lockfile diff and OSV's answer to it, the plan comes from the run's scan, and either lookup can fail on its own (its time is then null). Neither is the exposure-time end listed above as not built. Nothing reruns the patch when a wait ends: someone runs it again, or `watch` does on its next round. Composer, Maven, PHP Docker and Node.js Docker updates do not go through the judge. The judge comments on this repository's own dependency PRs (judge.yml) and is packaged as a GitHub Action (action.yml; a preview, not released). Both read each changed `*/package.json` as data, and the judge leaves one out of gate 4's changed-files stop when it agrees with the lockfile (docs/decisions/2026-10-29-l9-workspace-package-json.md); one that does not agree stops, and one it cannot read is undecidable. Its backtests, up to v5 (docs/bench/2026-10-28-backtest-v5), do not meet the backtest gate: one malicious version is still missed (v5 also counts it as disputed) and unknowns remain. The noise rerun (docs/bench/2026-10-28-noise-v2) meets neither its count gate nor its miss gate, and neither does the count on a new sample (docs/bench/2026-10-29-l1c). Details: docs/design.md and docs/decisions/.

A candidate that escaped the sandbox in the validation job would be on a runner that can write the repository's Actions caches. GitHub's schedule can be hours late (on 2026-10-29 the shadow's hourly schedule did not fire for five hours).

- **Provenance by the repository's id** (since 2026-10-30, LI, docs/decisions/2026-10-30-provenance-immutable-id.md). Wherever npm provenance is compared (gate 2 in `ludion judge` and on npm `ludion patch` candidates, rule 1's same-release exception, and the next fix's publisher check), the two statements must also record the same GitHub repository id, which npm writes in the statement (v1's `internalParameters.github`, v0.2's `invocation.environment`): ids that differ under the same name and workflow (a re-registered name that writes its own id), or an id on one side only, stop. When neither records an id (an older or other format, GitLab's included), the two are compared by name and workflow as before, and the judgement's findings, the same-release line or the publisher check's detail say they were not compared by ID. A statement whose GitHub event is not push, release or workflow_dispatch (`pull_request_target`, `issue_comment`, `workflow_run`, `schedule` and the rest), or that records an id but no event, stops: in gate 2 for the version an update installs, in the other two for either side. A name that differs with the same id (a rename or a transfer) still stops; whether to let it through is not decided. The id and the event are the statement's own claims: npm writes them from the build's environment variables, which the publishing workflow can set (npm's own description calls the statement falsifiable this way, https://github.com/npm/provenance), Ludion has not established that the registry matches them against the signing certificate, and it does not read or verify the certificate itself. So a re-registered name (SlugFest) whose publisher writes the old id and an allowed event passes these checks, and only the wait and the re-query catch it; these checks stop only a publisher that writes its real id or event. Reading the certificate's own repository id and trigger is not built.
- **Gate 3's new type, a first form** (since 2026-11-02, LG3; docs/decisions/2026-11-02-gate-3-type-definition.md, measured in docs/progress/2026-11-02-lg3-gate-3-type.md). `judgeGate3` (packages/cli/src/security/gate3.ts) takes a project's package.json and package-lock.json before and after a fix and gives `not_broken`, `broken` or `undecidable`, with the old version as the specification: build, types, start, a crawl of every GET page in a browser (status, exceptions, console, DOM, screenshot) and the tests, old twice and new once (twice when it fails to build or start) with the clock stopped, each in packages/sandbox's box, which is not changed. Nothing calls it: no command, `patch`, `watch` or receipt reaches it, so nothing Ludion does today has passed it. Run for real only on examples/nextjs-security and one-line pages added to it, on Next.js 15.5.6, 15.5.7 and 16.4.4 (Turbopack, its default), on one machine of 16 CPUs, and not yet through `judgeGate3` since the box's fixes. **Missing:** calling it from `patch` and writing its limits in the receipt; any project that is not Next.js (`undecidable`); a check that notices when Next.js stops reading the two values the box relies on, `CIRCLE_NODE_TOTAL` and `TURBO_ENGINE_READ_ONLY`, neither a public setting (only a case of `gate3-docker.test.ts` would show it); the project's own Node.js version (the box runs the browser image's); what a project larger than the example needs (on old, a failure to build or start is `undecidable`; when new's build or start fails, new runs once more, and an OOM kill, a `heap out of memory` or `ENOSPC` line on stderr, or /tmp under 1 MiB free, on either run, is `undecidable`; two failures that none of those shows are `broken`, and that includes the process limit and the wait for the server to start, which are not read; each `undecidable` has a named reason for C4 to count, with new running out alone marked as that, and new's types, tests and pages read no such figure, so a test that fails on new for lack of /tmp is still `broken`); comparing tests one by one (the step is compared as a whole, so with one test failing on old, a test that then fails on new is not seen); C4's sample, its check against hidden tests and its deeper check; crawling production (C5). `gate3-docker.test.ts` is the real run under vitest and CI does not run it: it needs `LUDION_GATE3_DOCKER=1` and a browser image of several GB. `.github/dependabot.yml` has no entry for examples/nextjs-security yet.
- Every changed version counts as production in `ludion judge` and in npm `ludion patch`: no dependency is told apart as dev-only, and there is no 7-day wait.
- `ludion judge`, npm `ludion patch`'s judge and the PR job read package-lock.json through one reader (judge.ts's readLock, since LB2a, #215): lockfileVersion 2 or 3, no top-level key npm does not write, and a v2 lock's npm 6 `dependencies` section saying the same as `packages`. A change that leaves a requirement unmet that the base meets (missing, or outside its range, so npm install would fetch it unpinned) is refused, and the project's package.json `overrides` count as npm 8.3 and later apply them: where one applies, the copy is checked against its spec only. A lock the project itself already leaves so is read: a `--legacy-peer-deps` lock without its peers, an override outside a dependent's range (docs/decisions/2026-10-31-lock-requirements-against-the-base.md). A git or URL dependency in the change, which cannot be shown to be met, is refused. A moved or added entry's `peerDependenciesMeta` is compared with the registry; not compared: its `hasShrinkwrap`, flags, `bin`, `hasInstallScript` and `engines`. The package at a location must be the one the spec that requires it names (the location's own name, or an alias's target), at the top and nested: another package there refuses the change (docs/decisions/2026-10-31-lock-corpus-alias.md); an optional peer is held to it too wherever the lock has a copy for it (docs/decisions/2026-10-31-flag-only-entries-gate2.md, section 3). The reader is checked against 72 locks npm 7.10.0 to 12.2.1 wrote, aliases under another package's name included, and npm 12.2.1's own `npm ls --package-lock-only` (and npm 11.19.1's, which says the same) on 320 one-change variants (docs/bench/2026-10-31-lb2a-npm-corpus): every lock is read and nothing main reads is refused, and the requirement check agrees with npm 12.2.1 on every variant but the 72 that put another package at a required location, which Ludion refuses by that rule and `npm ls` does not report (it does not look at which package a location holds). Bundled entries: the 12 locks npm 7.10.0 to 12.2.1 wrote at lockfileVersion 2 and 3 for a project that requires npm 10.9.2 (215 `inBundle` entries each) are read by main's reader and this one and leave no requirement unmet (fixtures/npm-corpus/extra; npm 12.2.1 writes them only with `--allow-remote=all`, since its default refuses the registry tarball npm reads to list what a package bundles).
- `ludion scan` also reads Python, Go and Rust projects, read-only: it reports known advisories and plans or applies nothing (README, "Read-only scans").
- What `ludion judge` sends: package names and versions to OSV and the npm registry, and the IDs of the advisories OSV returns back to OSV. No CVE ID is sent and no source is sent. It downloads CISA's catalog of exploited vulnerabilities whole, and, when a fix has a CVE ID, FIRST's daily list of EPSS scores whole, and looks the CVE IDs up in them (docs/decisions/2026-10-29-epss-downloaded-whole.md). The EPSS list comes from the one URL first.org/epss/data gives (epss.empiricalsecurity.com). It follows at most one redirect, and only to a file on the same host named for a day (`epss_scores-YYYY-MM-DD.csv.gz`); any day's name is accepted, not only today's. The list is at most 16 MiB compressed and 64 MiB expanded, and must arrive within 120 seconds; a list that cannot be downloaded, has a score_date that is not a date, or has any line that is not a score makes the judgement undecidable. The list's own score_date (its first line) is shown in the judgement and its JSON (`epss_date` on each fix with a CVE ID; null when the list gives none). An old list is used, not refused. `ludion patch` and `watch` send and download the same for each npm fix's candidate, through the judge: a run with several npm fixes downloads CISA's catalog (when the fix's diff fixes an advisory) and the EPSS list (when one of those has a CVE ID) once per fix, and nothing keeps them between fixes or rounds. The urgency rule is unchanged (an EPSS of 0.1 or more is high), and of a fix's CVE IDs the highest score counts.
